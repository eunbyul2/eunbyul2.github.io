# MLOps 개념과 kind 기반 Kubernetes 애플리케이션 배포

## 1. 학습 목표와 범위

이번 주에는 MLOps의 개념과 머신러닝 시스템의 운영 과정을 살펴보고, 컨테이너와 Kubernetes가 그 과정에서 담당하는 역할을 학습했다. 이후 MacBook 로컬 환경에 `kind` 클러스터를 구성하고, 간단한 FastAPI 애플리케이션을 Docker 이미지로 빌드하여 Kubernetes에 배포했다.

학습 범위는 다음과 같다.

- **Chapter 1~2:** MLOps와 ML 엔지니어링, ML Lifecycle, 운영 과정에서의 재현성·자동화·모니터링

- **실습:** OrbStack + kind + Kubernetes v1.37.0 환경에서 FastAPI 애플리케이션 배포 및 HTTP 응답 확인

## 2. MLOps와 ML 엔지니어링

### 2.1 MLOps가 필요한 이유

머신러닝 개발을 단순하게 생각하면 데이터를 준비하고 모델을 학습한 다음 추론 결과를 확인하는 과정으로 볼 수 있다. 그러나 실제 서비스에 모델을 적용하려면 학습 이후에도 관리해야 할 요소가 많다.

예를 들어 동일한 코드라도 학습 데이터, 라이브러리 버전, 모델 파라미터가 달라지면 결과가 달라질 수 있다. 모델을 배포한 뒤에는 API가 정상 동작하는지뿐 아니라 모델의 예측 성능과 입력 데이터의 변화를 지속적으로 살펴야 한다.

**MLOps(Machine Learning Operations)** 는 이러한 머신러닝 시스템의 개발·배포·운영 과정을 체계화하고 자동화하기 위한 접근 방식이다.

### 2.2 DevOps와 MLOps의 차이

| 구분 | DevOps | MLOps |
|---|---|---|
| 주요 관리 대상 | 애플리케이션 코드, 인프라, 배포 | 코드뿐 아니라 데이터, 학습 실험, 모델 아티팩트, 추론 서비스 |
| 변경 요인 | 소스 코드·설정 변경 | 소스 코드·설정·데이터·모델 변경 |
| 테스트 | 빌드, 단위·통합 테스트 등 | 애플리케이션 테스트 + 데이터 품질·모델 평가 등 |
| 운영 모니터링 | 가용성, 오류율, 지연 시간, 자원 사용량 | 시스템 지표 + 예측 품질, 데이터/모델 드리프트 등 |
| 재현성 | 실행·배포 환경 재현 | 실행 환경과 학습 조건·데이터·모델 버전 재현 |

MLOps가 DevOps와 별개의 운영 원칙을 처음부터 다시 만드는 것은 아니다. 기존 소프트웨어 운영 방식에 **데이터와 모델이라는 추가적인 변경·관리 대상**이 생긴 것으로 이해했다.

### 2.3 ML Lifecycle

이번에 정리한 머신러닝 운영 흐름은 다음과 같다.

```text
문제 정의
   ↓
데이터 수집·검증·전처리
   ↓
모델 학습·실험·평가
   ↓
모델 아티팩트 저장 및 버전 관리
   ↓
모델 패키징·배포
   ↓
온라인/배치 추론
   ↓
서비스·모델 모니터링
   ↓
데이터와 모델 개선·재학습
```

이 과정에서 중요한 것은 각 단계가 한 번씩 실행되는 데 그치지 않고, 결과를 추적할 수 있으며 변경이 발생했을 때 반복 가능한 형태로 구성되는 것이다.

### 2.4 주요 MLOps 구성요소

| 구성요소 | 역할 | 예시 기술 |
|---|---|---|
| 실험 추적·모델 레지스트리 | 학습 파라미터, 지표, 모델 버전 관리 | MLflow |
| 파이프라인 | 전처리·학습·평가 등의 작업 연결과 실행 | Kubeflow Pipelines |
| Feature Store | 학습과 추론에 사용하는 피처 관리 | Feast |
| 모델 서빙 | 모델을 API 형태로 배포하고 추론 요청 처리 | KServe |
| CI/CD 및 GitOps | 빌드·검증·배포 자동화 및 선언적 상태 관리 | Gitea Actions, Argo CD |
| 관측성 | 시스템 메트릭과 상태 관찰 | Prometheus, Grafana |

이번 주에는 각 기술의 **역할만 구분**했으며, 위 플랫폼 전체를 설치하지는 않았다.

## 3. MLOps에서 Docker와 Kubernetes가 필요한 이유

### 3.1 Docker: 애플리케이션 실행 환경 패키징

모델 서빙 애플리케이션에는 일반적으로 API 코드뿐 아니라 Python 런타임, 추론 라이브러리, 모델 파일 등 여러 의존성이 필요하다. 환경 차이로 인해 개발 PC에서는 동작하지만 배포 환경에서는 실행되지 않는 문제가 발생할 수 있다.

컨테이너 이미지는 애플리케이션과 실행에 필요한 의존성을 함께 패키징해 **일관된 실행 환경**을 만드는 데 도움을 준다.

이번 실습에서는 Python 기반 FastAPI 애플리케이션을 Docker 이미지로 빌드했다.

### 3.2 Kubernetes: 컨테이너의 배포와 운영

컨테이너를 하나 실행하는 것과 서비스를 안정적으로 운영하는 것은 다른 문제다. Kubernetes는 원하는 Pod 개수, 배포 상태, 네트워크 접근 지점 등을 선언적으로 관리한다.

이번 실습에서 사용한 리소스는 다음과 같다.

- **Pod:** 애플리케이션 컨테이너가 실행되는 기본 단위
- **Deployment:** 원하는 Pod 개수를 유지하고 애플리케이션 배포 상태 관리
- **ReplicaSet:** Deployment가 관리하는 Pod 복제본 유지
- **Service:** Pod의 변경과 무관하게 접근할 수 있는 내부 네트워크 진입점 제공
- **Readiness Probe:** 애플리케이션이 트래픽을 받을 준비가 되었는지 확인

### 3.3 kind를 선택한 이유

`kind(Kubernetes IN Docker)`는 Docker 컨테이너를 Kubernetes 노드로 사용하는 로컬 테스트 도구다.

이번 실습의 목적은 물리 서버나 VM 기반 클러스터 설치가 아니라 **애플리케이션을 Kubernetes에 배포하고 동작을 검증하는 것**이므로, MacBook에서 클러스터를 빠르게 생성할 수 있는 kind를 사용했다.

`Kubespray`는 Ansible을 이용한 Kubernetes 클러스터 구축·관리 도구로, 별도 인프라 학습에서 활용할 예정이다. 두 도구는 같은 Kubernetes를 다루더라도 목적과 관리 범위가 다르다.

| 구분 | 구성 |

| 호스트 OS | macOS Sonoma 14 |
| 컨테이너 실행 환경 | OrbStack |

OrbStack의 Docker 엔진에서 kind 노드 컨테이너를 실행하고, **그 노드 내부의 containerd**가 Kubernetes 워크로드 컨테이너를 관리하는 구조다. Docker Engine의 containerd 버전과 Kubernetes 노드가 보고하는 containerd 버전은 서로 다를 수 있다.

```text
MacBook Air M3 (macOS)
 ├── Docker CLI / kubectl / kind
 └── OrbStack (Linux 컨테이너 실행 환경)
      └── Docker 컨테이너: mlops-control-plane
           └── Kubernetes v1.37.0
                ├── Control Plane / etcd
                ├── kindnet / kube-proxy / CoreDNS
                └── Pod: FastAPI (containerd 관리)
```

확인 결과 Docker Context는 `orbstack`이었고, Docker Server에 정상 연결되었다.

기존 kind 클러스터와 Kubernetes 컨텍스트를 확인한 뒤 새 클러스터를 생성했다.

## 5. FastAPI 애플리케이션 컨테이너화

### 5.1 작업 디렉터리

```bash
mkdir -p ~/mlops-study/week1/k8s
cd ~/mlops-study/week1
```

파일 구성:

```text
week1/
├── main.py
├── Dockerfile
└── k8s/
    ├── deployment.yaml
    └── service.yaml
```

### 5.2 FastAPI 코드 작성

`main.py`

```python
from fastapi import FastAPI

app = FastAPI()


@app.get("/")
def root():
    return {
        "message": "Hello MLOps!",
        "environment": "kind",
        "status": "running"
    }


@app.get("/health")
def health():
    return {"status": "ok"}
```

`/`는 기본 응답, `/health`는 애플리케이션의 준비 상태를 확인하기 위해 사용한다. `environment: kind`는 예제 코드에 고정해 넣은 문자열로, 실행 환경을 자동 감지한 결과는 아니다.

### 5.3 Dockerfile 작성

`Dockerfile`

```dockerfile
FROM python:3.12-slim-bookworm

WORKDIR /app

RUN pip install --no-cache-dir fastapi uvicorn

COPY main.py /app/main.py

EXPOSE 8080

CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8080"]
```

주요 설정의 의미:

| 명령 | 의미 |
|---|---|
| `FROM` | Python 3.12 기반 이미지 사용 |
| `WORKDIR` | 컨테이너 내부 작업 디렉터리 지정 |
| `RUN` | FastAPI와 Uvicorn 설치 |
| `COPY` | 호스트의 소스 코드를 이미지 내부로 복사 |
| `EXPOSE` | 애플리케이션이 사용하는 포트를 문서화 |
| `CMD` | 컨테이너 시작 시 API 서버 실행 |

`EXPOSE`만으로 호스트 포트가 공개되지는 않는다. 로컬 Docker 실행에서는 `-p` 옵션으로 포트를 매핑했다.

### 5.4 이미지 빌드

```bash
docker build -t mlops-fastapi:v1 .
docker images mlops-fastapi
```

실제 빌드 결과:

```text
REPOSITORY      TAG       IMAGE ID       SIZE
mlops-fastapi   v1        fda835f971be   246MB
```

이미지를 정상 빌드했으며, 현재 로컬 Docker 이미지로 저장되어 있다.

### 5.5 Docker 단독 실행 검증

```bash
docker run -d \
  --name mlops-fastapi-test \
  -p 18080:8080 \
  mlops-fastapi:v1

curl -s http://localhost:18080/
curl -s http://localhost:18080/health
```

실제 HTTP 응답:

```json
{"message":"Hello MLOps!","environment":"kind","status":"running"}
```

```json
{"status":"ok"}
```

테스트 이후 실행한 컨테이너를 제거했다.

```bash
docker rm -f mlops-fastapi-test
```

이 단계에서 확인한 것은 **FastAPI 애플리케이션이 Docker 컨테이너에서 정상 실행되고 HTTP 요청에 응답한다는 사실**이다.

## 6. kind Kubernetes에 애플리케이션 배포

### 6.1 로컬 이미지를 kind 노드로 로드

```bash
kind load docker-image mlops-fastapi:v1 --name mlops
```

실제 출력:

```text
Image: "mlops-fastapi:v1" ... not yet present on node "mlops-control-plane", loading...
```

이 작업이 필요한 이유는 **호스트 Docker 이미지 저장소와 kind 노드 내부의 containerd 이미지 저장소가 별개**이기 때문이다. Docker에서 이미지를 빌드했다고 해서 kind 노드에서 바로 사용할 수 있는 것은 아니다.

이번 실습은 레지스트리(Docker Hub, Harbor 등)에 이미지를 Push하지 않고 `kind load docker-image`로 이미지를 전달했다.

### 6.2 Deployment 매니페스트

`k8s/deployment.yaml`

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: mlops-fastapi
  namespace: default
spec:
  replicas: 1
  selector:
    matchLabels:
      app: mlops-fastapi
  template:
    metadata:
      labels:
        app: mlops-fastapi
    spec:
      containers:
        - name: fastapi
          image: mlops-fastapi:v1
          imagePullPolicy: Never
          ports:
            - containerPort: 8080
          readinessProbe:
            httpGet:
              path: /health
              port: 8080
            initialDelaySeconds: 2
            periodSeconds: 5
          resources:
            requests:
              cpu: 50m
              memory: 64Mi
            limits:
              cpu: 500m
              memory: 256Mi
```

주요 항목:

- `replicas: 1`: 원하는 Pod 복제본 1개
- `selector` / `labels`: Deployment가 관리할 Pod를 구분하는 기준
- `imagePullPolicy: Never`: 외부 레지스트리로부터 이미지를 가져오지 않고 노드에 로드한 이미지 사용
- `readinessProbe`: `/health` 응답으로 요청을 받을 준비가 되었는지 확인
- `requests`: 스케줄러가 배치 결정을 할 때 고려하는 자원 요구량
- `limits`: 해당 컨테이너의 자원 사용 상한

`readinessProbe`는 준비되지 않은 Pod가 Service 엔드포인트에 포함되는 것을 방지하는 데 사용한다. 컨테이너 재시작을 판단하는 `livenessProbe`와 역할이 다르다.

### 6.3 Service 매니페스트

`k8s/service.yaml`

```yaml
apiVersion: v1
kind: Service
metadata:
  name: mlops-fastapi
  namespace: default
spec:
  type: ClusterIP
  selector:
    app: mlops-fastapi
  ports:
    - port: 80
      targetPort: 8080
```

Service는 `app: mlops-fastapi` 레이블을 가진 Pod를 선택하고, 서비스 포트 `80`을 컨테이너 포트 `8080`으로 연결한다.

`ClusterIP`는 기본적으로 **클러스터 내부용 서비스**이므로 이 설정만으로 외부에서 직접 접속할 수 있는 것은 아니다.

### 6.4 리소스 생성 및 배포 상태 확인

```bash
kubectl --context kind-mlops apply -f k8s/

kubectl --context kind-mlops get deployment,pod,svc -o wide

kubectl --context kind-mlops rollout status \
  deployment/mlops-fastapi --timeout=120s
```

실제 생성 결과:

```text
deployment.apps/mlops-fastapi created
service/mlops-fastapi created
```

실제 상태 확인 결과(핵심 부분):

```text
NAME                            READY   UP-TO-DATE   AVAILABLE
```

### 7.1 Port Forwarding

Mac 터미널에서 Service로 포트 포워딩을 실행했다.

```bash
kubectl --context kind-mlops port-forward \

```

다른 터미널에서 HTTP 요청을 보냈다.

```bash
curl -s http://localhost:18080/
echo

curl -s http://localhost:18080/health
echo
```

**실제 결과:**

```json
{"message":"Hello MLOps!","environment":"kind","status":"running"}
```

```json
{"status":"ok"}
```

요청 흐름을 단순화하면 다음과 같다.

```text
MacBook
  └── curl localhost:18080
       └── kubectl port-forward (Service를 대상으로 실행)
            └── 선택된 FastAPI Pod:8080
```

> `kubectl port-forward svc/...`는 Service를 대상으로 지정하더라도 실제로는 해당 Service가 선택하는 **Pod 중 하나로 포트 포워딩**한다. 일반적인 Service ClusterIP 경유 트래픽의 로드밸런싱 동작을 검증한 것은 아니다. 이번 실습에서 검증한 것은 Kubernetes에 배포된 애플리케이션에 로컬에서 접근하여 정상 HTTP 응답을 받았다는 점이다.

## 8. 실습하면서 이해한 점

### 8.1 Docker 이미지 빌드와 Kubernetes 배포는 다른 단계

Docker 이미지를 빌드하는 단계에서는 애플리케이션의 **실행 단위**를 만든다. Kubernetes Deployment를 만드는 단계에서는 그 이미지를 **어떤 상태로 실행하고 유지할지** 선언한다.

또한 kind에서는 Docker로 빌드한 이미지를 `kind load docker-image`로 로드해야 했다. 이 과정을 통해 **이미지 저장 위치와 컨테이너 실행 환경이 분리**되어 있다는 점을 확인했다.

### 8.2 Pod가 Running이라고 모든 요청이 정상인 것은 아니다

Pod의 `Running` 상태는 컨테이너가 실행 중이라는 의미다. 그러나 실제 API가 응답할 준비가 되어 있는지는 별도의 확인이 필요하다.

이번에는 `/health`와 Readiness Probe를 설정하고, `curl`로 실제 API 응답을 확인했다. 운영 환경에서는 여기에 Liveness Probe, 로그, 메트릭, 지연 시간 등의 관측성을 추가해야 한다.

### 8.3 Kubernetes 인프라 구성과 MLOps 플랫폼 구성은 구분해야 한다

kind 클러스터 구축은 Kubernetes 실행 환경을 마련한 것이다. 그 자체가 MLOps 플랫폼을 완성했다는 의미는 아니다.

실제 ML 모델을 운영하려면 모델 아티팩트 관리, 모델 평가, 배포 정책, 재현 가능한 파이프라인, 예측 품질 관찰 등이 추가되어야 한다. 이번에는 이 중 **애플리케이션 패키징과 Kubernetes 배포**라는 기초 영역을 검증했다.
