# Chapter 9. GitAIOps, 살아있는 운영 표준의 탄생

인프라 구성 및 배포 With Claude Code 책으로 모각코를 진행하면서 애플리케이션을 배포하고, GitOps를 적용하고, Kafka와 Observability까지 하나씩 추가해 왔다. 
이번 챕터에서는 새로운 기능을 구현하기보다는 지금까지 만들어 온 프로젝트를 AI와 함께 다시 살펴보면서 프로젝트가 어떻게 성장했는지 돌아보는 시간을 가졌다.

처음에는 "AI에게 저장소를 분석시킨다"는 것이 어떤 의미인지 잘 와닿지 않았다. 단순히 디렉터리 구조를 읽어주는 정도라고 생각했는데, 실제로는 프로젝트 구조와 Git 히스토리, Kubernetes 리소스까지 종합해서 현재 프로젝트 상태를 분석해 주는 모습을 보면서 생각보다 훨씬 활용도가 높다는 것을 느꼈다.

---

## 1. Cloud Code에게 프로젝트를 분석시켜 보기

가장 먼저 지금까지 만들어 온 Git 저장소를 Cloud Code에게 분석해 달라고 요청했다.

단순히 "무슨 파일이 있는지"를 알려주는 수준이 아니라 프로젝트 구조를 살펴보고, 어떤 기술을 사용했는지, 어떤 방향으로 프로젝트가 발전해 왔는지까지 함께 분석해 주었다.

특히 저장소의 디렉터리 구조를 보면서 지금까지 진행했던 실습들이 하나의 프로젝트로 연결되어 있다는 점이 인상적이었다.

```text
application/
charts/
manifests/
argocd/
docs/
```

처음 챕터를 시작했을 때는 단순히 애플리케이션 하나를 배포하는 수준이었지만, 챕터가 진행될수록 Helm Chart, Kubernetes Manifest, ArgoCD Application, 운영 문서 등이 계속 추가되면서 하나의 GitOps 프로젝트 형태를 갖추게 되었다.

이번에 다시 살펴보니 그동안 무심코 추가했던 파일들이 각각 역할을 가지고 있었다는 점도 다시 확인할 수 있었다.

---

## 2. Git 히스토리로 프로젝트의 성장 과정 돌아보기

Cloud Code는 현재 상태만 분석하는 것이 아니라 Git Commit 이력도 함께 살펴보며 프로젝트가 어떻게 발전해 왔는지 정리해 주었다.

예전에는 Git Commit을 단순히 코드 백업 정도로만 생각했는데, 이번 실습을 하면서 커밋 자체가 프로젝트의 변경 이력을 설명하는 문서 역할도 한다는 점을 이해하게 되었다.

커밋 로그를 따라가다 보니 처음에는 단순한 애플리케이션 배포부터 시작해서 GitOps 적용, Observability 추가, Kafka 적용까지 프로젝트가 점점 확장되는 흐름을 한눈에 확인할 수 있었다.

GitOps에서는 현재 상태만 중요한 것이 아니라 **어떤 과정을 거쳐 현재 상태가 만들어졌는지**도 매우 중요한 정보라는 것을 다시 느꼈다.

특히 문제가 발생했을 때는 특정 커밋으로 되돌리거나, 어떤 변경 이후 문제가 발생했는지를 빠르게 확인할 수 있기 때문에 Git 자체가 운영 도구의 역할도 함께 수행한다는 점이 인상적이었다.

---

## 3. 코드보다 Manifest가 더 많아진 이유

Cloud Code가 프로젝트를 분석하면서 코드보다 Kubernetes Manifest와 운영 관련 YAML 파일의 비중이 훨씬 크다는 점도 함께 이야기해 주었다.

처음에는 왜 이렇게 YAML 파일이 많은지 의문이 들었다. 하지만 GitOps에서는 애플리케이션 코드만 관리하는 것이 아니라 클러스터가 어떤 상태여야 하는지도 함께 Git으로 관리한다는 점을 생각해 보니 자연스러운 구조라는 것을 이해할 수 있었다.

예를 들어 Deployment를 수정하거나 Service를 변경하는 작업도 직접 `kubectl edit`로 수정하는 것이 아니라 Manifest를 수정하고 Git에 Commit하는 방식으로 진행했다.

```bash
git add .
git commit -m "Update deployment configuration"
git push
```

이후 ArgoCD가 변경 사항을 감지해 자동으로 클러스터와 동기화했다.

처음에는 한 단계가 더 늘어난 것처럼 느껴졌지만, 시간이 지나면서 오히려 누가 어떤 변경을 했는지 모두 Git에 기록되기 때문에 운영하기 훨씬 편하다는 것을 느꼈다.

---

## 4. 프로젝트 문서가 점점 많아진 이유

프로젝트를 분석하는 과정에서 Cloud Code는 `README.md`뿐만 아니라 `CLAUDE.md`, `JOURNEY.md`, `ADR` 같은 문서들도 함께 분석했다.

처음에는 문서가 너무 많아지는 것 같아서 '이 정도까지 작성해야 하나?'라는 생각도 들었다. 하지만 프로젝트가 점점 커질수록 코드만으로는 왜 이런 구조를 선택했는지 설명하기 어렵다는 것을 느끼게 되었다.

예를 들어 ADR(Architecture Decision Record)은 특정 기술을 선택한 이유를 기록하는 문서이다. 단순히 "Kafka를 사용했다."가 아니라, 왜 Kafka를 선택했고 다른 기술은 왜 선택하지 않았는지를 기록한다.

JOURNEY.md는 프로젝트를 진행하면서 어떤 과정을 거쳐 여기까지 왔는지를 정리하는 문서였다. 새로운 기능을 추가할 때도 이전 과정을 쉽게 확인할 수 있었고, AI 역시 이 문서를 기반으로 프로젝트의 흐름을 이해하고 있었다.

CLAUDE.md도 처음에는 단순한 설정 파일 정도로 생각했는데, 실제로는 AI에게 프로젝트의 규칙과 구조를 알려주는 역할을 하고 있었다.

이전에는 사람을 위한 문서만 작성한다고 생각했는데, 이번 실습을 하면서는 AI도 프로젝트의 협업 대상이 될 수 있다는 점이 인상적이었다.

---

## 5. AI가 프로젝트를 이해하는 방식

Cloud Code는 저장소를 분석한 뒤 현재 프로젝트가 어떤 구조인지, 어떤 기술을 사용하고 있는지, 앞으로 어떤 방향으로 발전할 수 있는지까지 정리해 주었다.

단순히 파일을 읽는 것이 아니라 Git 히스토리와 디렉터리 구조, 문서, Kubernetes Manifest를 함께 분석해 프로젝트를 하나의 시스템으로 이해하는 모습이 흥미로웠다.

특히 프로젝트 구조를 설명하기 위해 처음부터 하나하나 설명하지 않아도 된다는 점이 가장 편리했다.

예전에는 새로운 AI 세션을 시작할 때마다 프로젝트 구조를 다시 설명해야 하는 경우가 많았다.

- 어떤 프레임워크를 사용하는지
- Kubernetes는 어떻게 구성되어 있는지
- GitOps는 어떤 방식으로 적용했는지
- Helm Chart는 어디에 있는지

이런 내용을 매번 다시 설명해야 했는데, 문서와 저장소가 잘 정리되어 있으니 AI가 스스로 프로젝트를 파악하는 모습을 볼 수 있었다.

결국 프로젝트를 잘 정리하는 것은 사람뿐 아니라 AI와 협업할 때도 중요한 요소라는 점을 알게 되었다.

---

## 6. GitAIOps라는 개념이 조금씩 이해되기 시작했다

책에서는 GitAIOps라는 용어를 사용했는데, 처음에는 GitOps에 AI를 붙인 새로운 이름 정도로만 생각했다.

하지만 이번 챕터를 진행하면서 느낀 점은 단순히 AI를 사용하는 것이 아니라, Git에 저장된 프로젝트 정보를 AI가 이해하고 함께 운영에 활용하는 방식이라는 것이었다.

Git에는 코드뿐만 아니라 다음과 같은 정보들이 함께 저장되어 있었다.

- 애플리케이션 코드
- Kubernetes Manifest
- Helm Chart
- ADR
- 프로젝트 문서
- Git Commit History

이 정보들을 기반으로 AI가 현재 프로젝트 상태를 분석하고, 개선 방향을 제안하거나 문제를 파악하는 모습을 보면서 Git 저장소 자체가 하나의 지식 저장소처럼 활용될 수 있다는 점을 이해하게 되었다.

물론 AI가 모든 것을 대신해 주는 것은 아니다.

최종적인 판단과 기술 선택은 사람이 해야 하지만, 반복적으로 프로젝트를 분석하거나 구조를 이해하는 작업은 AI가 상당 부분 도와줄 수 있다는 가능성을 확인할 수 있었다.

---

## 7. 4주간 모각코를 마무리하며

이번 챕터는 새로운 기능을 구현하는 내용은 아니었지만, 오히려 지금까지 진행했던 실습들을 다시 돌아보며 전체 프로젝트를 정리할 수 있는 시간이었다.

처음에는 단순히 Kubernetes 위에 애플리케이션을 배포하는 것부터 시작했지만, GitOps를 적용하고 Helm Chart를 구성하고, ArgoCD를 통해 자동 배포를 만들고, Kafka와 Tempo를 추가하면서 프로젝트가 점점 실제 운영 환경과 비슷한 형태로 발전했다.

그리고 마지막에는 AI가 이 프로젝트를 분석하고 이해할 수 있는 수준까지 문서와 저장소를 정리하는 과정을 경험했다.

이번 모각코를 진행하면서 가장 크게 느낀 점은 Git은 단순한 소스코드 저장소가 아니라는 것이다.

프로젝트를 구성하는 코드와 인프라, 운영 문서, 변경 이력까지 모두 Git에 기록되기 때문에 Git 하나만으로도 프로젝트의 현재 상태와 성장 과정을 충분히 이해할 수 있었다.

앞으로 회사 프로젝트를 진행할 때도 단순히 기능을 구현하는 것에서 끝나는 것이 아니라, 문서와 변경 이력까지 함께 관리하는 습관을 들여야겠다는 생각이 들었다.

이번 챕터는 새로운 기술을 배우는 장이라기보다는, 지금까지 배운 기술들을 하나로 연결하고 앞으로 어떻게 활용할지 고민해 볼 수 있었던 마무리 챕터였다.
