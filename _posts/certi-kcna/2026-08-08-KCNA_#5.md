# KCNA #5 --- Cloud Native Architecture: Observability, Cloud Native Principles, CNCF 생태계와 오토스케일링

앞선 내용에서 Kubernetes의 핵심 리소스와 컨테이너 오케스트레이션을
살펴봤다면, 이번에는 시선을 조금 더 넓혀 **Kubernetes가 속한 Cloud
Native 생태계와 설계 원칙**을 정리한다.

여기서 중요한 점이 하나 있다. 기존 KCNA 자료에서는
`Cloud Native Architecture`가 **16%**였고 Autoscaling, Serverless,
Community & Governance, Personas, Open Standards 등이 주요
항목이었다. 하지만 **2025년 11월 24일 이후 적용된 현재 KCNA 시험
기준**에서는 Cloud Native Architecture가 **12%**이며, 공식 competency는
다음 세 가지로 개편되었다.

-   **Observability**
-   **Cloud Native Ecosystem and Principles**
-   **Cloud Native Community and Collaboration**

따라서 기존 자료의 오토스케일링, 서버리스, 오픈 스탠다드도 Cloud
Native를 이해하는 데 필요한 내용으로 함께 보되, 시험에서는 특히
**Observability와 Cloud Native 원칙, CNCF 생태계와 커뮤니티**를 확실히
잡는 것이 중요하다.

> **KCNA 시험 포인트**
>
> KCNA는 특정 도구의 세부 설정을 깊게 묻기보다, **어떤 문제를 어떤
> 개념이나 프로젝트가 해결하는지 구분할 수 있는가**를 확인하는
> 시험이다.

# 2. Cloud Native란 무엇인가

Cloud Native는 단순히 **애플리케이션을 Cloud에서 실행한다**는 의미가
아니다.

CNCF의 현재 Cloud Native Definition v1.1에서는 Cloud Native practices를
public, private, hybrid cloud 같은 컴퓨팅 환경에서 조직의 요구에 맞게
워크로드를 **규모에 맞춰 프로그래밍 가능하고 반복 가능한 방식으로
개발·구축·배포할 수 있게 하는 실천 방식**으로 설명한다.

Cloud Native 시스템은 다음과 같은 특성을 지향한다.

-   **Loosely Coupled**: 구성 요소가 느슨하게 결합되어 독립적으로 변경될
    수 있음
-   **Interoperable**: 서로 다른 시스템과 상호운용 가능
-   **Secure**: 보안을 고려한 구조
-   **Resilient**: 일부 장애가 발생해도 전체 시스템이 쉽게 무너지지 않음
-   **Manageable**: 자동화와 표준화된 방법으로 관리 가능
-   **Sustainable**: 자원과 비용 측면에서 지속 가능한 운영
-   **Observable**: 시스템 내부 상태를 외부 telemetry를 통해 이해할 수
    있음

대표적인 Cloud Native 기술과 아키텍처에는 다음이 있다.

  -----------------------------------------------------------------------
  개념                                의미
  ----------------------------------- -----------------------------------
  **Container**                       애플리케이션과 의존성을 함께
                                      패키징해 일관된 환경에서 실행

  **Microservices**                   애플리케이션을 작고 독립적으로 배포
                                      가능한 서비스로 분리

  **Service Mesh**                    서비스 간 통신, 트래픽 제어, 보안,
                                      관측을 애플리케이션 밖에서 제공

  **Multi-tenancy**                   하나의 플랫폼을 여러 사용자나 팀이
                                      공유하면서 논리적으로 격리

  **Immutable Infrastructure**        실행 중인 시스템을 직접 수정하지
                                      않고 새 이미지로 교체

  **Serverless**                      서버 운영을 플랫폼에 위임하고
                                      애플리케이션 실행에 집중

  **Declarative API**                 수행 절차가 아니라 원하는 최종
                                      상태를 선언
  -----------------------------------------------------------------------

여기서 중요한 것은 이 기술을 모두 사용해야 Cloud Native가 된다는 뜻은
아니라는 점이다. Cloud Native는 특정 제품 목록이 아니라 **확장성,
회복탄력성, 자동화, 관측 가능성, 느슨한 결합을 지향하는 설계와 운영
방식**에 가깝다.

> **시험 포인트**
>
> **Cloud Native = Kubernetes**가 아니다.\
> Kubernetes는 Cloud Native 시스템을 구현하는 대표적인 오케스트레이션
> 플랫폼이다.

# 3. Declarative API와 Reconciliation

Kubernetes를 이해하는 핵심 사고방식은 **Desired State와 Current
State**이다.

사용자가 다음 상태를 원한다고 선언했다고 가정해 봅니다.

``` text
Desired State
Deployment replicas = 3
```

하지만 실제로 실행 중인 Pod가 2개라면 현재 상태는 다음과 같다.

``` text
Current State
Running Pods = 2
```

Kubernetes Controller는 이 차이를 확인하고 새로운 Pod를 생성한다.

``` text
Current State           Desired State
2 Pods        ───────▶   3 Pods
             reconcile
```

이처럼 **현재 상태를 원하는 상태에 지속적으로 맞추는 과정**을
`reconciliation`이라고 한다.

이 개념은 Kubernetes의 여러 기능과 연결된다.

-   Replica 유지
-   Self-healing
-   Deployment rollout
-   Autoscaling
-   Controller 동작
-   Declarative configuration

즉 사용자가 매번 "Pod 하나를 만들어라"라고 명령하는 것이 아니라,

``` text
Pod 3개가 실행되는 상태를 유지해줘
```

라고 원하는 상태를 선언하면 Kubernetes가 계속 현재 상태를 확인하면서 그
상태를 유지한다.

------------------------------------------------------------------------

# 4. Self-Healing과 Resilience

Cloud Native에서 장애가 발생하지 않는 시스템을 만드는 것보다 중요한 것은
**장애가 발생해도 견디고 복구할 수 있는 시스템을 만드는 것**이다.

## Self-Healing

Self-healing은 시스템이 장애를 감지하고 원하는 상태로 자동 복구하는
특성이다.

예를 들어 Deployment가 Pod 3개를 유지하도록 선언되어 있는데 하나가
사라졌다고 가정한다.

``` text
Desired State: 3 Pods

Pod A    Running
Pod B    Running
Pod C    Failed

        ↓ Reconciliation

Pod A    Running
Pod B    Running
Pod D    Running
```

Controller가 새로운 Pod를 생성하면서 다시 원하는 상태를 맞춥니다.

## Resilience

Resilience는 일부 구성 요소가 실패해도 전체 서비스가 계속 동작하거나
빠르게 복구할 수 있는 능력이다.

대표적인 방법은 다음과 같다.

-   Replication
-   Redundancy
-   Failure isolation
-   Load balancing
-   Retry
-   Health check
-   Automated recovery

  -----------------------------------------------------------------------
  개념                                핵심
  ----------------------------------- -----------------------------------
  **Self-Healing**                    장애를 감지한 뒤 시스템이 자동으로
                                      정상 상태를 복구

  **Resilience**                      장애가 발생해도 시스템 전체가
                                      견디고 서비스를 지속할 수 있도록
                                      설계

  **High Availability**               서비스가 가능한 한 지속적으로 사용
                                      가능하도록 중복성과 장애 대응
                                      구조를 구성
  -----------------------------------------------------------------------

세 개념은 서로 연결되지만 완전히 같은 의미는 아니다.

# 5. Scalability와 Elasticity

Cloud Native에서 자주 함께 등장하는 개념이다.

## Scalability

부하가 증가했을 때 시스템의 처리 능력을 확장할 수 있는 능력이다.

예를 들어 요청량이 늘어났을 때 Pod를 추가하여 처리량을 증가시킬 수
있다면 scalable한 시스템이라고 볼 수 있다.

## Elasticity

수요 변화에 따라 필요한 자원을 **동적으로 늘리고 다시 줄이는
능력**이다.

``` text
Scalability
→ 부하 증가에 맞춰 확장할 수 있는가?

Elasticity
→ 수요에 따라 자원을 늘리고 줄일 수 있는가?
```

Autoscaling은 elasticity를 구현하는 대표적인 방법이다.

# 6. Stateless와 Stateful

Cloud Native 애플리케이션을 이해할 때 `stateless`와 `stateful`의 차이도
중요하다.

## Stateless

애플리케이션 인스턴스 자체가 중요한 상태를 로컬에 저장하지 않는
구조이다.

``` text
                    ┌── Pod A
Client ─▶ Service ──┼── Pod B
                    └── Pod C

State ─▶ DB / Object Storage / External Cache
```

Pod 하나가 사라져도 다른 Pod가 동일한 요청을 처리하기 쉬워 수평 확장과
교체에 유리하다.

## Stateful

각 인스턴스의 데이터, 식별자, 순서 등이 중요한 워크로드이다.

Kubernetes에서는 대표적으로 다음 조합을 사용할 수 있다.

``` text
StatefulSet + PersistentVolume
```

> **시험 함정**
>
> Cloud Native라고 해서 모든 애플리케이션이 반드시 Stateless여야 하는
> 것은 아니다. Stateless 구조가 수평 확장과 교체에는 유리하지만
> Kubernetes는 Stateful workload도 지원한다.

------------------------------------------------------------------------

# 7. Microservices와 Loose Coupling

Microservices Architecture는 하나의 큰 애플리케이션을 여러 개의 작고
독립적인 서비스로 나누는 방식이다.

``` text
Monolith

┌──────────────────────────────┐
│ UI + Order + Payment + User │
└──────────────────────────────┘
```

``` text
Microservices

┌──────┐   ┌───────┐   ┌─────────┐
│ User │   │ Order │   │ Payment │
└──────┘   └───────┘   └─────────┘
```

장점은 서비스별로 독립적인 배포와 확장이 가능하다는 점이다.

반대로 서비스가 많아질수록 다음 문제가 증가할 수 있다.

-   서비스 간 네트워크 통신
-   장애 추적
-   분산 로그
-   인증과 암호화
-   데이터 일관성
-   배포 복잡성

그래서 Microservices가 확대될수록 **Observability, Service Mesh,
자동화**가 중요해집니다.

> **시험 포인트**
>
> Microservices의 핵심 장점은 **독립적인 배포와 확장, 느슨한
> 결합**이다.\
> 대신 분산 시스템의 운영 복잡성이 증가한다는 trade-off가 있다.

------------------------------------------------------------------------

# 8. 12-Factor App

12-Factor App은 Cloud 환경에서 배포와 확장이 쉬운 애플리케이션을
설계하기 위한 방법론이다.

KCNA에서는 12개 원칙을 모두 암기하기보다 다음 방향을 이해하는 것이
중요하다.

-   의존성을 명시적으로 선언
-   설정(Config)을 애플리케이션 코드와 분리
-   DB나 메시지 브로커 같은 backing service를 외부 리소스로 취급
-   Build / Release / Run 단계 분리
-   프로세스를 가능한 Stateless하게 설계
-   빠른 시작과 정상 종료 지원
-   개발·스테이징·프로덕션 환경 차이 최소화
-   로그를 이벤트 스트림으로 취급

즉 12-Factor App은 Kubernetes 기능 자체가 아니라 **Cloud Native
애플리케이션을 설계하기 위한 원칙**이다.

------------------------------------------------------------------------

# 9. Autoscaling

Cloud Native의 elasticity를 자동화하는 대표적인 기능이
Autoscaling이다.

Kubernetes 생태계에서는 **무엇을 확장하는지**에 따라 구분해야 한다.

``` text
HPA  → Pod 개수
VPA  → Pod Resource 크기
CA   → Node 개수
KEDA → Event 기반 Pod 확장
```

이 구분은 KCNA에서 매우 중요하다.

------------------------------------------------------------------------

## HPA --- Horizontal Pod Autoscaler

HPA는 **워크로드의 replica 수를 수평으로 조정**한다.

``` text
Before

Pod
Pod

CPU / Traffic 증가
        ↓

After

Pod
Pod
Pod
Pod
```

HPA는 CPU나 Memory뿐 아니라 Custom Metric이나 External Metric을 사용할
수도 있다.

대표 metric 유형은 다음과 같다.

-   Resource metric
-   Container resource metric
-   Pods metric
-   Object metric
-   External metric

Resource metric 기반 HPA에서 CPU와 Memory 정보를 얻을 때는 일반적으로
Kubernetes Metrics API를 사용하며, 보통 `metrics-server`가 이를
제공한다.

### HPA의 계산 방식

개념적으로 HPA는 다음과 같은 비율을 사용해 필요한 replica 수를
계산한다.

``` text
desired replicas
≈ current replicas × current metric / desired metric
```

예를 들어 현재 replica가 2개이고 CPU 사용률이 목표치의 약 2배라면 더
많은 replica가 필요하다고 판단할 수 있다.

### Stabilization

부하가 순간적으로 오르내릴 때 Pod 수가 계속 증가와 감소를 반복하면
오히려 시스템이 불안정해질 수 있다.

이를 줄이기 위해 HPA는 scaling behavior와 stabilization window를 사용할
수 있다.

------------------------------------------------------------------------

## HPA와 Scale-to-Zero

HPA의 `minReplicas` 기본값은 **1**이다.

따라서 KCNA 수준에서는 다음처럼 기억하는 것이 좋다.

``` text
일반적인 HPA
→ 최소 replica 기본값 1

KEDA / Knative
→ Scale-to-Zero를 대표 기능으로 제공
```

다만 Kubernetes API에는 `HPAScaleToZero` alpha feature gate와
Object/External metric 조건을 만족하면 `minReplicas: 0`을 허용하는
예외가 있다.

따라서 다음처럼 절대적으로 외우지는 않는 것이 좋다.

``` text
HPA는 어떤 경우에도 절대 0으로 내려갈 수 없다.  X
```

시험에서는 **기본 HPA와 KEDA/Knative의 대표적인 Scale-to-Zero 동작을
구분**하는 정도가 핵심이다.

------------------------------------------------------------------------

## VPA --- Vertical Pod Autoscaler

VPA는 Pod 개수가 아니라 **Pod가 필요로 하는 CPU/Memory resource
request를 조정하거나 추천**한다.

``` text
HPA
Pod × 2 ─▶ Pod × 5

VPA
CPU 250m / Memory 256Mi
          ↓
CPU 500m / Memory 512Mi
```

VPA의 목적은 다음과 같다.

-   실제 Resource 사용량 분석
-   적절한 Resource Request 추천
-   과도한 Resource Request 감소
-   부족한 Resource Request 조정
-   Cluster Resource 활용 효율 개선

핵심은 다음 한 줄인다.

> **HPA는 Pod 수를 조절하고, VPA는 Pod의 Resource 크기를 조절한다.**

------------------------------------------------------------------------

## HPA와 VPA를 함께 사용할 때

HPA가 CPU utilization을 기준으로 replica 수를 조절하는 동시에 VPA가 CPU
request를 변경하면 두 Autoscaler가 서로 영향을 줄 수 있다.

``` text
VPA
CPU Request 변경
      ↓
HPA
CPU Utilization 계산 변화
      ↓
Replica 수 변경
```

따라서 같은 CPU/Memory 신호를 기준으로 두 Autoscaler를 동시에 사용하는
구성은 주의해야 한다.

하지만 다음처럼 외우면 안 된다.

``` text
HPA와 VPA는 절대로 같이 사용할 수 없다.  X
```

핵심은 **동일한 Resource 신호를 기반으로 서로 다른 방향의 Scaling이
동시에 일어날 때 상호작용이 생길 수 있다**는 것이다.

------------------------------------------------------------------------

## Cluster Autoscaler

Cluster Autoscaler는 **Node 수를 조정**한다.

HPA와 함께 보면 이해하기 쉽다.

``` text
Traffic 증가
     ↓
HPA가 Pod 증가
     ↓
새 Pod를 배치할 Node Resource 부족
     ↓
Pod Pending
     ↓
Cluster Autoscaler
     ↓
Node 추가
```

반대로 일정 조건을 만족하는 저활용 Node는 축소 대상이 될 수 있다.

  Autoscaler           조정 대상
  -------------------- -------------------
  HPA                  Pod replica 수
  VPA                  Pod Resource 크기
  Cluster Autoscaler   Node 수

> **시험 포인트**
>
> HPA가 Pod를 늘린다고 해서 Node까지 자동으로 늘어나는 것은 아니다.\
> **Pod Scaling과 Node Scaling은 서로 다른 계층의 동작**이다.

------------------------------------------------------------------------

## KEDA --- Kubernetes Event-Driven Autoscaling

KEDA는 Kubernetes 기반 **Event-Driven Autoscaler**이다.

CPU나 Memory뿐 아니라 실제 workload를 나타내는 외부 이벤트를 Scaling
Signal로 사용할 수 있다.

예를 들면 다음과 같다.

-   Kafka consumer lag
-   RabbitMQ queue
-   AWS SQS
-   Prometheus metric
-   Database
-   CI/CD queue
-   기타 외부 이벤트

``` text
Kafka / Queue / External Event
              ↓
             KEDA
              ↓
        Scaling Metric
              ↓
             HPA
              ↓
        Workload Scaling
```

KEDA의 동작을 조금 더 정확하게 보면 다음과 같다.

``` text
0 ↔ 1
KEDA가 Activation / Deactivation 담당

1 ↔ N
KEDA가 Metric을 제공하고
Kubernetes HPA가 Scaling 담당
```

즉 KEDA는 HPA와 완전히 별개의 수평 확장 시스템이라기보다 **외부 Event
Source와 Kubernetes Autoscaling을 연결해 주는 역할**을 한다고 이해하면
좋다.

------------------------------------------------------------------------

## KEDA와 Scale-to-Zero

KEDA의 대표 기능 중 하나가 Scale-to-Zero이다.

``` text
Queue = 0
Pods = 0

Message 발생
     ↓
KEDA가 Event 감지
     ↓
0 → 1
     ↓
필요하면 HPA를 통해
1 → N
```

KEDA `ScaledObject`의 `minReplicaCount` 기본값은 0이다.

이 때문에 이벤트가 전혀 없는 동안 Pod를 0개로 줄이고, 이벤트가 발생하면
다시 실행하는 Event-Driven workload에 적합하다.

------------------------------------------------------------------------

## Autoscaler 최종 비교

  -----------------------------------------------------------------------
  메커니즘          조정 대상         대표 신호         핵심
  ----------------- ----------------- ----------------- -----------------
  **HPA**           Pod replica 수    CPU, Memory,      Horizontal
                                      Custom/External   Scaling
                                      Metric            

  **VPA**           Pod Resource      실제 Resource     Vertical Scaling
                    Request           사용량            

  **Cluster         Node 수           Unschedulable     Infrastructure
  Autoscaler**                        Pod, Node 활용    Scaling
                                      상태              

  **KEDA**          Event-Driven      Queue, Kafka lag, Event 기반
                    workload replica  External Event    Scaling,
                                                        Scale-to-Zero
  -----------------------------------------------------------------------

시험에서는 다음 한 줄로 먼저 구분한다.

``` text
HPA  = Pod 개수
VPA  = Pod 크기
CA   = Node 개수
KEDA = Event 기반 + Scale-to-Zero
```

------------------------------------------------------------------------

# 10. Serverless

Serverless는 **서버가 존재하지 않는다는 뜻이 아니다.**

실제 Server와 Infrastructure는 존재하지만 다음과 같은 운영 부담을
플랫폼이나 Cloud Provider에 위임하는 모델이다.

-   Server provisioning
-   Capacity management
-   Scaling
-   Runtime 관리
-   일부 patching과 운영

개발자는 Infrastructure보다 애플리케이션 코드와 비즈니스 로직에 집중할
수 있다.

Serverless의 대표적인 특성은 다음과 같다.

-   Event-Driven Execution
-   Automatic Scaling
-   Infrastructure Abstraction
-   Scale-to-Zero를 지원하는 구현
-   사용량 기반 비용 모델이 흔함

다만 모든 Serverless 서비스가 반드시 동일한 Scale-to-Zero와 과금 방식을
사용하는 것은 아니다.

------------------------------------------------------------------------

## FaaS --- Function as a Service

FaaS는 Serverless를 구현하는 대표적인 형태이다.

개발자가 Function을 배포하면 플랫폼이 이벤트에 따라 함수를 실행한다.

``` text
Event
  ↓
Function
  ↓
Result
```

대표적인 Trigger는 다음과 같다.

-   HTTP Request
-   Message
-   File Upload
-   Timer
-   Database Event

관계는 다음과 같다.

``` text
Serverless
   └── FaaS
```

즉 **Serverless가 더 넓은 개념이고 FaaS는 Serverless의 대표 구현
모델**이다.

------------------------------------------------------------------------

# 11. Knative

Knative는 Kubernetes 위에서 Serverless workload를 구현하기 위한
플랫폼이다.

KCNA에서는 크게 **Serving과 Eventing**을 구분해 두면 좋다.

## Knative Serving

-   Kubernetes 기반 Serverless workload 실행
-   Request-driven autoscaling
-   Revision
-   Traffic management
-   Scale-to-Zero

## Knative Eventing

-   Event Source와 Consumer 연결
-   Event Routing
-   Broker / Trigger
-   Event-Driven Architecture 지원

``` text
Request / Event
      ↓
   Knative
      ↓
Workload = 0
      ↓
Scale Up
      ↓
Pod Ready
      ↓
Request 처리
```

> **시험 포인트**
>
> `Kubernetes + Serverless + Scale-to-Zero + Event-Driven`이라는 문맥이
> 나오면 **Knative**를 연결한다.

------------------------------------------------------------------------

# 12. Cold Start

Scale-to-Zero 상태에서는 실행 중인 인스턴스가 없다.

첫 요청이 도착하면 다음 과정이 필요할 수 있다.

``` text
Request
   ↓
Scale from 0
   ↓
Pod Scheduling
   ↓
Container Start
   ↓
Application Initialization
   ↓
Ready
   ↓
Request Processing
```

이때 발생하는 추가 지연을 **Cold Start**라고 한다.

``` text
Scale-to-Zero
      ↓
Idle Resource 절약
      ↓
비용 효율 향상

하지만

첫 Request
      ↓
Cold Start Latency
```

따라서 Serverless의 대표적인 trade-off는 다음과 같다.

> **Scale-to-Zero로 유휴 Resource를 절약할 수 있지만 첫 요청에서 Cold
> Start 지연이 발생할 수 있다.**

------------------------------------------------------------------------

# 13. Serverless에 적합한 Workload

  상황                                               적합성
  -------------------------------------------------- -------------------------------------
  간헐적이고 예측하기 어려운 Traffic                 적합
  Event Trigger 처리                                 적합
  사용하지 않을 때 Resource를 없애고 싶은 Workload   적합
  항상 높은 부하가 유지되는 서비스                   상대적으로 이점이 줄어들 수 있음
  극단적인 Low Latency가 필요한 서비스               Cold Start 고려 필요
  매우 장시간 실행되는 작업                          플랫폼의 실행 모델과 제한 확인 필요

------------------------------------------------------------------------

# 14. Observability

**현재 KCNA에서 Observability는 Cloud Native Architecture의 공식
competency이다.**

Cloud Native 환경은 여러 Container와 Microservice가 분산되어 동작하기
때문에 단순히 "서버가 살아 있는가"만 확인해서는 문제를 파악하기
어렵다.

그래서 시스템이 외부로 내보내는 Telemetry를 이용해 내부 상태를 이해할 수
있어야 한다.

------------------------------------------------------------------------

## Monitoring과 Observability

두 개념은 비슷하지만 범위가 다릅니다.

### Monitoring

미리 정의한 Metric이나 Condition을 확인한다.

예를 들면 다음과 같다.

``` text
CPU가 80%를 넘었는가?
Pod가 Down 되었는가?
HTTP 5xx가 증가했는가?
```

즉 **알고 있는 문제를 확인하는 것**에 가깝다.

### Observability

Metric, Log, Trace 같은 Telemetry를 이용해 시스템의 내부 상태를 이해하고
**사전에 정확히 정의하지 못한 문제까지 분석할 수 있는 능력**을
의미한다.

``` text
Monitoring
→ "문제가 발생했는가?"

Observability
→ "왜 문제가 발생했고 어디에서 발생했는가?"
```

> **시험 포인트**
>
> Monitoring은 Observability를 구현하는 중요한 활동이지만 두 단어를
> 완전히 같은 의미로 보지는 않는다.

------------------------------------------------------------------------

# 15. Telemetry: Metrics, Logs, Traces

KCNA에서는 세 가지 Signal을 정확하게 구분해야 한다.

## Metrics

시간에 따라 측정되는 숫자 데이터이다.

예:

-   CPU Usage
-   Memory Usage
-   Request Count
-   Error Rate
-   Request Latency

``` text
10:00 CPU 30%
10:01 CPU 45%
10:02 CPU 82%
```

Metric은 다음에 적합하다.

-   Trend 확인
-   Threshold Alert
-   Aggregation
-   Dashboard

대표 프로젝트는 **Prometheus**이다.

------------------------------------------------------------------------

## Logs

특정 시점에 발생한 Event의 기록이다.

``` text
2026-08-09T10:00:00 ERROR database connection failed
```

Metric에서 오류가 증가했다는 사실을 발견했다면 Log를 통해 **구체적으로
어떤 오류가 발생했는지** 확인할 수 있다.

대표적인 Cloud Native Log 수집 프로젝트로 Fluentd 등이 있다.

------------------------------------------------------------------------

## Traces

하나의 Request가 여러 Service를 통과하는 전체 경로를 추적한다.

``` text
Client
  ↓
API Gateway
  ↓
Service A
  ↓
Service B
  ↓
Database
```

분산 환경에서는 한 요청이 여러 Microservice를 지나기 때문에 어느
구간에서 지연이나 오류가 발생했는지 찾기 어렵다.

Distributed Tracing은 이 Request 흐름을 연결해서 보여줍니다.

### Trace와 Span

``` text
Trace
├── Span: API Gateway
├── Span: Service A
├── Span: Service B
└── Span: Database
```

-   **Trace**: 하나의 Request 전체 흐름
-   **Span**: Trace를 구성하는 개별 작업 단위

대표 프로젝트는 **Jaeger**이며, OpenTelemetry를 이용해 Trace를
수집·전송할 수도 있다.

------------------------------------------------------------------------

## Metrics / Logs / Traces 비교

  -----------------------------------------------------------------------
  Signal                  무엇을 알려주는가       예
  ----------------------- ----------------------- -----------------------
  **Metrics**             시스템 상태와 변화 추세 CPU, Error Rate,
                                                  Latency

  **Logs**                특정 Event의 상세 내용  Error message

  **Traces**              Request가 지나간 경로와 Service A → B → DB
                          구간별 처리             
  -----------------------------------------------------------------------

시험에서는 다음처럼 기억하면 빠르다.

``` text
Metrics → 얼마나? 상태가 어떤가?
Logs    → 무슨 일이 발생했나?
Traces  → 어디를 지나면서 문제가 발생했나?
```

------------------------------------------------------------------------

# 16. Prometheus

Prometheus는 Cloud Native 환경에서 널리 사용하는 **Metric Monitoring 및
Alerting 시스템**이다.

핵심 특징은 다음과 같다.

-   Time-Series Metric
-   Label 기반 데이터 모델
-   Pull 기반 Scraping
-   PromQL
-   Alerting 생태계

일반적인 흐름은 다음과 같다.

``` text
Application / Exporter
        ↑
     Scrape
        ↑
   Prometheus
```

Prometheus가 대상의 Metric Endpoint를 주기적으로 Scrape하여 데이터를
수집하는 Pull Model이 핵심이다.

> **시험 함정**
>
> Prometheus의 대표 역할은 **Log 저장이 아니라 Metric 수집과
> Monitoring**이다.

------------------------------------------------------------------------

# 17. OpenTelemetry

OpenTelemetry는 **Telemetry 데이터를 생성, 수집, 처리하고 Export하기
위한 Vendor-Neutral Observability Framework**이다.

대표 Signal은 다음과 같다.

-   Traces
-   Metrics
-   Logs

일반적인 구조는 다음과 같다.

``` text
Application
    ↓
OpenTelemetry SDK / Instrumentation
    ↓
OpenTelemetry Collector
    ↓
Observability Backend
```

여기서 중요한 점은 OpenTelemetry 자체를 Prometheus나 Jaeger와 같은 최종
Monitoring Backend로 보면 안 된다는 것이다.

``` text
OpenTelemetry
→ Telemetry 생성 / 계측 / 수집 / 처리 / 전송

Prometheus
→ 주로 Metrics Monitoring

Jaeger
→ Distributed Tracing Backend
```

> **시험 포인트**
>
> `Vendor-neutral telemetry instrumentation` 또는
> `Metrics/Logs/Traces를 공통 방식으로 수집·전송`이라는 설명이 나오면
> **OpenTelemetry**를 연결한다.

------------------------------------------------------------------------

# 18. CNCF --- Cloud Native Computing Foundation

CNCF는 Linux Foundation 산하에서 Cloud Native Open Source 생태계를
지원하는 재단이다.

주요 역할은 다음과 같다.

-   Cloud Native Open Source Project의 중립적인 Home 제공
-   Vendor-Neutral 생태계 지원
-   Project Governance와 Maturity 지원
-   Community Collaboration 촉진
-   교육과 Certification
-   KubeCon + CloudNativeCon 운영
-   Cloud Native 기술의 Adoption과 Sustainability 지원

Kubernetes는 Google에서 시작된 프로젝트이며 이후 CNCF에 기증되었다.

CNCF가 중요한 이유는 특정 회사가 Cloud Native 생태계를 독점하는 대신
**여러 회사와 개인 Contributor가 함께 프로젝트를 발전시키는
Vendor-Neutral 생태계**를 지원하기 때문이다.

------------------------------------------------------------------------

# 19. CNCF Project Maturity

CNCF 프로젝트의 대표적인 Maturity Level은 다음 순서로 이해한다.

``` text
Sandbox
   ↓
Incubating
   ↓
Graduated
```

## Sandbox

초기 또는 실험적인 단계의 프로젝트이다.

새로운 아이디어와 기술을 CNCF 생태계 안에서 발전시킬 수 있는 단계이다.

## Incubating

프로젝트의 Adoption과 Community가 성장하고 실제 Production 사용과 지속
가능한 프로젝트 운영 능력이 발전한 단계이다.

## Graduated

높은 Maturity와 Adoption, 안정적인 Governance와 Community를 갖춘 성숙한
프로젝트 단계이다.

> **주의**
>
> `Graduated = 버그가 전혀 없는 완벽한 프로젝트`라는 의미는 아니다.\
> Maturity는 프로젝트의 Adoption, Governance, Contributor Community,
> 지속 가능성 등을 종합적으로 나타내는 신호이다.

### 대표 프로젝트와 역할

  프로젝트        대표 역할
  --------------- --------------------------------------------
  Kubernetes      Container Orchestration
  containerd      Container Runtime
  etcd            Distributed Key-Value Store
  CoreDNS         DNS
  Helm            Kubernetes Package Manager
  Prometheus      Metrics / Monitoring
  OpenTelemetry   Telemetry Instrumentation / Collection
  Envoy           Proxy / Service Networking
  Fluentd         Log/Data Collection
  Argo            Kubernetes-native Workflow / GitOps 생태계
  Flux            GitOps Continuous Delivery
  KEDA            Event-Driven Autoscaling
  Knative         Kubernetes 기반 Serverless
  Cilium          Networking / Security / Observability
  Harbor          Cloud Native Registry
  Jaeger          Distributed Tracing

프로젝트의 Maturity 상태는 시간이 지나면서 변경될 수 있으므로
**프로젝트별 현재 단계까지 무작정 암기하기보다 프로젝트의 대표 역할을
우선 연결**하는 것이 좋다.

------------------------------------------------------------------------

# 20. CNCF Landscape

Cloud Native 생태계는 Kubernetes 하나만으로 구성되지 않는다.

대략 다음과 같은 여러 기술 영역이 함께 존재한다.

``` text
Application Delivery
        ↓
Container Orchestration
        ↓
Runtime / Networking / Storage
        ↓
Observability / Security
        ↓
Infrastructure
```

대표 카테고리에는 다음이 있다.

-   Container Runtime
-   Orchestration
-   Service Networking
-   Storage
-   Database
-   Observability
-   Security
-   CI/CD
-   GitOps
-   Registry
-   Serverless

CNCF Landscape는 이처럼 방대한 Cloud Native 프로젝트와 제품을 영역별로
확인할 수 있도록 정리한 생태계 지도이다.

> **시험 포인트**
>
> KCNA에서는 모든 CNCF 프로젝트를 암기하는 것보다 **프로젝트 이름과 대표
> 역할을 연결**하는 것이 훨씬 중요하다.

------------------------------------------------------------------------

# 21. Open Governance와 Community Collaboration

Cloud Native Open Source Project는 특정 회사 하나가 모든 의사결정을
독점하는 방식이 아니라 여러 조직과 개인 Contributor가 참여하는 Open
Governance를 지향한다.

대표 참여자는 다음과 같다.

-   Contributor
-   Maintainer
-   Project Leadership
-   End User
-   Vendor
-   Community Group

Open Governance가 중요한 이유는 다음과 같다.

-   Vendor Neutrality
-   Transparency
-   다양한 조직의 Contribution
-   지속 가능한 프로젝트 운영
-   특정 회사에 대한 종속 감소
-   Open Collaboration

------------------------------------------------------------------------

# 22. TOC, TAG, SIG, WG

현재 KCNA에는 **Cloud Native Community and Collaboration**이 공식
competency로 포함되어 있으므로 커뮤니티의 기본 구조도 이해해 두는 것이
좋다.

## CNCF TOC --- Technical Oversight Committee

CNCF의 기술적 방향과 프로젝트 생태계에 대한 기술적 Oversight를
담당한다.

프로젝트 Lifecycle과 CNCF의 기술적 Governance에서 중요한 역할을 한다.

## CNCF TAG --- Technical Advisory Group

특정 기술 영역의 전문가와 Contributor가 협력하며 CNCF 생태계에 기술적
Guidance와 Collaboration을 제공하는 그룹이다.

KCNA에서는 세부 조직을 전부 외우기보다 다음 관계를 이해하면 충분하다.

``` text
CNCF
├── TOC → 기술적 Oversight
└── TAG → 기술 영역별 Community Collaboration / Guidance
```

## Kubernetes SIG --- Special Interest Group

Kubernetes Community에서 특정 기술 영역을 지속적으로 담당하는
그룹이다.

예:

``` text
SIG Network
SIG Storage
SIG Node
SIG Scheduling
```

## WG --- Working Group

특정 문제나 목표를 해결하기 위해 여러 영역의 Contributor가 협력하는
그룹이다.

일반적으로 지속적인 기술 영역을 담당하는 SIG와 비교하면 **특정 과제나
목표에 집중하는 협업 그룹**으로 이해하면 좋다.

``` text
CNCF TOC
→ CNCF 기술적 Oversight

CNCF TAG
→ CNCF 기술 영역별 Collaboration

Kubernetes SIG

```

# 25. SLI, SLO, SLA와 Error Budget

Observability와 SRE를 함께 이해할 때 자주 등장하는 용어이다.

## SLI --- Service Level Indicator

서비스 품질을 나타내는 **실제 측정 지표**이다.

예:

-   Availability
-   Latency
-   Error Rate
-   Throughput

``` text
이번 달 실제 Availability = 99.95%
```

이 값은 SLI이다.

## SLO --- Service Level Objective

SLI에 대해 설정한 **목표 수준**이다.

``` text
한 달 Availability를 99.9% 이상 유지한다.
```

이것이 SLO이다.

## SLA --- Service Level Agreement

서비스 제공자와 고객 사이의 **계약적 서비스 수준 약속**이다.

SLA를 위반하면 Service Credit이나 계약상 보상 조건이 발생할 수도
있다.

``` text
SLI = 실제 측정값
SLO = 목표
SLA = 고객과의 계약
```

## Error Budget

SLO가 100%가 아니라면 허용 가능한 실패 범위가 존재한다.

예를 들어 Availability SLO가 99.9%라면 개념적으로 나머지 0.1%가 허용
가능한 비가용성 범위가 된다.

``` text
SLO = 99.9%
Error Budget ≈ 0.1%
```

Error Budget은 Reliability를 유지하면서도 새로운 기능을 얼마나 빠르게
변경하고 배포할지 판단하는 데 사용할 수 있다.

> **시험 포인트**
>
> `실제 측정값 = SLI`, `목표 = SLO`, `계약 = SLA`를 먼저 확실히
> 구분한다.

# 26. Open Standards와 Interoperability

Cloud Native 생태계에는 수많은 Vendor와 프로젝트가 존재한다.

이들이 함께 동작하려면 특정 제품만 이해하는 구조보다 **표준화된
Interface**가 중요하다.

``` text
Upper Layer
     ↓
Standard Interface
     ↓
Implementation A
Implementation B
Implementation C
```

Open Standard와 표준 Interface가 주는 대표적인 장점은 다음과 같다.

-   Interoperability
-   Portability
-   Vendor Neutrality
-   Vendor Lock-In 감소
-   구현체 교체 가능성
-   생태계 확장

다만 Open Source나 Kubernetes를 사용한다고 Vendor Lock-In이 완전히
사라지는 것은 아니다.

Managed Database, IAM, Storage, Networking 같은 Cloud Provider 고유
API에 의존할 수도 있기 때문이다.

따라서 정확한 표현은 다음과 같다.

> **Open Standards와 Portable Architecture는 Vendor Lock-In을 줄이고
> 상호운용성을 높이는 데 도움이 된다.**

------------------------------------------------------------------------

# 27. OCI, CRI, CNI, CSI

KCNA에서 자주 헷갈리는 표준과 Interface이다.

## OCI --- Open Container Initiative

OCI는 Container 생태계의 Open Industry Standard를 정의한다.

특히 다음 두 규격이 중요하다.

``` text
OCI
├── Image Specification
└── Runtime Specification
```

### OCI Image Specification

Container Image의 구성과 배포 형식을 정의한다.

### OCI Runtime Specification

OCI Bundle을 실행하는 Container Runtime의 동작 규격을 정의한다.

------------------------------------------------------------------------

## CRI --- Container Runtime Interface

CRI는 **kubelet과 Container Runtime 사이의 Interface**이다.

``` text
kubelet
   ↓
  CRI
   ↓
containerd / CRI-O
```

Kubernetes가 특정 Container Runtime 구현체에 강하게 결합되지 않도록
해줍니다.

------------------------------------------------------------------------

## CNI --- Container Network Interface

CNI는 Container Networking Plugin을 연결하기 위한 Specification이다.

``` text
Kubernetes
   ↓
  CNI
   ↓
Network Plugin
```

대표적인 Kubernetes CNI 구현체로 Cilium, Calico 등이 있다.

------------------------------------------------------------------------

## CSI --- Container Storage Interface

CSI는 Container Orchestrator와 Storage System을 연결하는 표준화된
Storage Interface이다.

``` text
Kubernetes
   ↓
  CSI
   ↓
Storage Driver
   ↓
Storage Backend
```

다양한 Storage Vendor가 Kubernetes와 통합될 수 있도록 한다.

------------------------------------------------------------------------

## 네 가지 최종 구분

``` text
OCI = Container Image / Runtime 규격
CRI = kubelet ↔ Container Runtime
CNI = Container Networking
CSI = Container Storage
```

> **시험 함정**
>
> OCI와 CRI는 같은 계층이 아니다.\
> **OCI는 Container Image/Runtime 규격**, **CRI는 Kubernetes와 Runtime
> 사이의 Interface**이다.

------------------------------------------------------------------------

# 28. Immutable Infrastructure

Mutable Infrastructure에서는 실행 중인 Server에 접속하여 직접 수정할 수
있다.

``` text
Server v1
   ↓ SSH
Package Update
   ↓
Server v1.1
```

반면 Immutable Infrastructure에서는 실행 중인 인스턴스를 직접
수정하기보다 새로운 Artifact를 만들어 교체한다.

``` text
Image v1
   ↓
Build Image v2
   ↓
Deploy New Instance
   ↓
Replace v1
```

장점은 다음과 같다.

-   환경 일관성
-   Reproducibility
-   Configuration Drift 감소
-   Rollback 단순화
-   자동화된 배포와 잘 맞음

Container Image와 Kubernetes Deployment가 이 방식과 잘 맞는다.

------------------------------------------------------------------------

# 29. Rolling Update와 Rollback

Kubernetes Deployment의 대표적인 Update Strategy는
**RollingUpdate**이다.

기존 Pod를 한 번에 모두 종료하는 대신 새 Version Pod를 점진적으로
생성하고 기존 Version을 줄인다.

``` text
v1  v1  v1
     ↓
v1  v1  v2
     ↓
v1  v2  v2
     ↓
v2  v2  v2
```

대표 설정은 다음과 같다.

-   `maxUnavailable`
-   `maxSurge`

### maxUnavailable

Update 중 사용할 수 없는 Pod의 최대 수 또는 비율이다.

### maxSurge

Desired Replica 수보다 추가로 생성할 수 있는 Pod의 최대 수 또는
비율이다.

Rolling Update는 서비스 가용성을 유지하면서 점진적으로 새 Version으로
교체하기 위한 전략이다.

다만 다음 표현은 정확하지 않다.

``` text
Rolling Update = 무조건 Zero-Downtime  X
```

실제 Zero-Downtime을 달성하려면 다음 요소도 중요하다.

-   충분한 Replica
-   Readiness Probe
-   적절한 `maxUnavailable`
-   Graceful Shutdown
-   Service Routing
-   애플리케이션 호환성

새 Version에 문제가 있으면 이전 Revision으로 되돌리는 **Rollback**을
사용할 수 있다.

------------------------------------------------------------------------

# 30. Rolling, Recreate, Blue-Green, Canary

배포 전략도 시나리오 형태로 구분해 두면 좋다.

## Rolling Update

기존 Version과 새 Version의 Pod를 점진적으로 교체한다.

## Recreate

기존 Version을 먼저 종료하고 새 Version을 생성한다.

Downtime이 발생할 수 있다.

## Blue-Green

기존 환경과 새 환경을 별도로 준비한 뒤 Traffic을 전환한다.

``` text
Blue  = Current
Green = New

Traffic ─▶ Blue

검증 후

Traffic ─▶ Green
```

## Canary

새 Version에 일부 Traffic만 보내 검증한 뒤 점진적으로 비율을 확대한다.

``` text
90% → v1
10% → v2

검증

50% → v1
50% → v2

검증

100% → v2
```

  전략         핵심
  ------------ --------------------------------------
  Rolling      Pod를 점진적으로 교체
  Recreate     기존 Version 종료 후 새 Version 실행
  Blue-Green   두 환경을 준비하고 Traffic 전환
  Canary       일부 Traffic부터 새 Version 검증

# 32. 시나리오로 확인하기

## 상황 1

Web Traffic이 증가하면서 동일한 Application Pod 수를 자동으로 늘리고
싶다.

**→ HPA**

Pod 자체의 Resource 크기가 아니라 **Replica 수**를 조절하기 때문이다.

------------------------------------------------------------------------

## 상황 2

Pod가 Pending 상태이고 Cluster에 해당 Pod를 배치할 Node Resource가
부족하다.

**→ Cluster Autoscaler**

문제는 Pod 개수가 아니라 **Cluster의 Node Capacity**이다.

------------------------------------------------------------------------

## 상황 3

Kafka Consumer를 Consumer Lag에 따라 늘리고 Message가 없으면 Replica를
0으로 줄이고 싶다.

**→ KEDA**

CPU가 아니라 **외부 Event/Kafka Lag**을 Scaling Signal로 사용하며
Scale-to-Zero가 필요하다.

------------------------------------------------------------------------

## 상황 4

Kubernetes에서 HTTP Request가 없을 때 Workload를 0으로 줄이는 Serverless
Platform이 필요하다.

**→ Knative**

------------------------------------------------------------------------

## 상황 5

한 Request가 API → Service A → Service B → Database를 지나가는데 어느
구간에서 Latency가 발생하는지 확인하고 싶다.

**→ Distributed Tracing**

------------------------------------------------------------------------

## 상황 6

CPU Usage와 HTTP Error Rate의 장기간 추세를 확인하고 Threshold Alert를
설정하고 싶다.

**→ Metrics / Prometheus**

------------------------------------------------------------------------

## 상황 7

특정 오류가 발생한 정확한 시간과 Error Message를 확인하고 싶다.

**→ Logs**

------------------------------------------------------------------------

## 상황 8

애플리케이션에서 Metrics, Logs, Traces를 Vendor-Neutral 방식으로
계측하고 여러 Backend로 전달하고 싶다.

**→ OpenTelemetry**

------------------------------------------------------------------------

## 상황 9

kubelet이 containerd 같은 Container Runtime과 통신해야 한다.

**→ CRI**

------------------------------------------------------------------------

## 상황 10

Container Image Format과 Runtime 동작 규격을 표준화하고 싶다.

**→ OCI**

------------------------------------------------------------------------

## 상황 11

특정 Vendor에 강하게 종속되지 않고 여러 구현체가 상호운용되도록 만들고
싶다.

**→ Open Standards / Interoperability / Vendor Neutrality**

------------------------------------------------------------------------

## 상황 12

실제 Availability를 측정했더니 이번 달 99.93%였다.

**→ SLI**

반면,

``` text
Availability를 99.9% 이상 유지한다.
```

는 **SLO**이다.

# 34. 정리

이번 영역에서 가장 중요한 것은 개별 도구의 세부 설정을 외우는 것이
아니라 **Cloud Native 시스템이 왜 이런 구조를 사용하는지** 이해하는
것이다.

Cloud Native는 Container를 사용하는 것만을 의미하지 않는다. 느슨하게
결합된 시스템을 만들고, 선언형 API와 자동화를 통해 반복 가능하게
운영하며, 장애가 발생해도 복구할 수 있고, 필요에 따라 확장·축소할 수
있으며, 시스템 내부 상태를 관측할 수 있어야 한다.

현재 KCNA 기준으로는 특히 다음 세 축을 중심으로 정리하는 것이 좋다.

1.  **Observability**\
    Metrics, Logs, Traces를 구분하고 Prometheus, OpenTelemetry, Jaeger가
    각각 어떤 역할을 하는지 연결한다.

2.  **Cloud Native Ecosystem and Principles**\
    Declarative API, Reconciliation, Resilience, Loose Coupling,
    Microservices, Immutable Infrastructure, Scalability와 Elasticity
    같은 원칙을 이해한다.

3.  **Cloud Native Community and Collaboration**\
    CNCF가 왜 Vendor-Neutral Foundation인지, Project Maturity가
    무엇인지, TOC·TAG·SIG·WG 같은 Community 구조가 어떤 역할을 하는지 큰
    그림을 이해한다.

그리고 기존 KCNA에서 중요하게 다루던 HPA, VPA, Cluster Autoscaler, KEDA,
Serverless, Knative, OCI/CRI/CNI/CSI도 개념 간 차이를 시나리오로 구분할
수 있도록 정리해 두면 다른 도메인의 문제를 풀 때도 도움이 된다.

결국 시험에서 가장 중요한 질문은 다음과 같다.

``` text
이 기술의 이름이 무엇인가?
```

보다,

``` text
이 문제를 해결하려면 어떤 Cloud Native 개념이나 기술이 필요한가?
```

를 판단하는 것이다.
