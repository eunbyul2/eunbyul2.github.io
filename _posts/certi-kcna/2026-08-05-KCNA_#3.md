# KCNA #3 - Kubernetes Fundamentals 2: API, 컨테이너, 스케줄링

이전 글에서는 Kubernetes Cluster를 구성하는 Control Plane과 Worker Node, 그리고 Pod, ReplicaSet, Deployment, Service, Namespace 같은 핵심 Resource를 정리했다.

이번에는 Kubernetes가 이러한 Resource를 **어떻게 API Object로 관리하는지**, Pod 안의 Container가 ​**어떤 Image와 Runtime을 통해 실행되는지**, 그리고 새로 생성된 Pod가 ​**어떤 기준으로 Worker Node에 Scheduling되는지**를 정리한다. 마지막에는 Application Configuration을 Container Image와 분리하기 위한 ConfigMap과 Secret까지 살펴본다.

현재 KCNA에서 **Kubernetes Fundamentals는 전체 시험의 44%**를 차지하며, 공식 Competency는 다음과 같이 구성되어 있다.

```text
Kubernetes Fundamentals - 44%

├── Kubernetes Core Concepts
├── Administration
├── Scheduling
└── Containerization
```

이번에 살펴볼 API, Container, Scheduling, ConfigMap과 Secret은 서로 따로 떨어진 주제가 아니다. 사용자가 Manifest를 작성한 순간부터 실제 Container가 Worker Node에서 실행되기까지 하나의 흐름으로 연결된다.

```text
Manifest 작성
   ↓
kubectl
   ↓
Kubernetes API
   ↓
Desired State 저장
   ↓
Controller의 Reconciliation
   ↓
Pod 생성
   ↓
Scheduler가 Node 선택
   ↓
kubelet
   ↓
CRI
   ↓
Container Runtime
   ↓
Container 실행
   ↓
ConfigMap / Secret으로 설정 전달
```

따라서 각각의 용어를 따로 외우기보다 **이 전체 흐름에서 각 Component와 Resource가 어떤 역할을 담당하는지 이해하는 것**을 목표로 정리했다.

---

# 1. Kubernetes는 API 중심 시스템이다

Kubernetes에서 Resource를 생성하거나 수정하고 삭제하는 대부분의 작업은 **Kubernetes API를 통해 이루어진다.**

예를 들어 다음 명령을 실행한다고 해보자.

```bash
kubectl apply -f deployment.yaml
```

이때 `kubectl`이 Worker Node에 직접 접근해 Container를 실행하는 것은 아니다. `kubectl`은 Manifest를 읽고 Kubernetes API Server인 `kube-apiserver`에 API Request를 전달한다.

```text
User
  │
  │ kubectl apply
  ▼
kubectl
  │
  │ Kubernetes API Request
  ▼
kube-apiserver
  │
  ├── Authentication
  ├── Authorization
  ├── Admission Control
  │
  ▼
Kubernetes API Object
  │
  ▼
etcd
```

Object가 API Server를 통해 등록된 이후에는 Controller, Scheduler, kubelet 등의 Kubernetes Component가 해당 Object를 관찰하면서 각자 필요한 작업을 수행한다.

따라서 Kubernetes를 이해할 때는 단순히 **"kubectl로 Cluster를 조작한다"​**고 보기보다 **"kubectl을 이용해 Kubernetes API에 원하는 상태를 전달한다"​**고 이해하는 것이 더 정확하다.

Kubernetes의 Component 사이 통신 역시 API Server를 중심으로 이루어진다. 이런 구조 때문에 Kubernetes를 **API-driven system**이라고 볼 수 있다.

---

# 2. kubectl의 역할

`kubectl`은 Kubernetes Cluster 안에서 실행되는 Control Plane Component가 아니다. **Kubernetes API와 통신하기 위한 Command-Line Client**이다.

```text
kubectl ───── HTTPS / Kubernetes API ─────▶ kube-apiserver
```

따라서 Kubernetes API를 직접 호출할 수 있다면 반드시 `kubectl`만 사용해야 하는 것은 아니다. Application에서는 Kubernetes Client Library를 사용할 수도 있고 REST API를 직접 호출할 수도 있다.

## API Request가 처리되는 과정

API Request는 단순히 API Server에 도착했다고 바로 적용되는 것은 아니다.

개념적으로 다음 과정을 거친다.

```text
Request
   ↓
Authentication
"누구인가?"
   ↓
Authorization
"이 작업을 할 권한이 있는가?"
   ↓
Admission Control
"Cluster에 적용하기 전에 허용/변경해야 하는가?"
   ↓
Object 처리
```

세 가지를 구분하면 다음과 같다.

| 과정 | 질문 |
|---|---|
| Authentication | 사용자가 누구인가? |
| Authorization | 해당 사용자가 이 작업을 수행할 권한이 있는가? |
| Admission Control | 권한이 있는 요청을 실제로 적용하기 전에 추가 검증 또는 변경이 필요한가? |

KCNA에서 Security Domain을 깊게 다루는 단계는 아니지만 `kube-apiserver`가 단순한 HTTP Endpoint가 아니라 Kubernetes API Request의 중심이라는 정도는 이해할 필요가 있다.

### KCNA 시험 포인트

| 대상 | 역할 |
|---|---|
| `kubectl` | Kubernetes API를 호출하는 CLI Client |
| `kube-apiserver` | Kubernetes API를 제공하는 Control Plane Component |
| `etcd` | Kubernetes Cluster State를 저장하는 Key-Value Store |

즉 `kubectl`을 Container Runtime이나 Cluster 내부 Component라고 설명하는 보기는 틀린 설명이다.

---

# 3. Kubernetes에서는 상태를 Object로 표현한다

Kubernetes에서는 Cluster에서 관리할 상태를 **API Object**로 표현한다.

대표적인 Object에는 Pod, Deployment, ReplicaSet, StatefulSet, DaemonSet, Service, ConfigMap, Secret, Namespace, Node 등이 있다.

Kubernetes Object는 단순한 YAML 설정값이 아니라 **사용자가 Cluster가 어떤 상태이기를 원하는지 표현하는 Record of Intent**로 볼 수 있다.

예를 들어 Deployment에서 다음과 같이 선언했다고 해보자.

```yaml
spec:
  replicas: 3
```

이것은 Kubernetes에 **"이 Application의 Pod Replica가 3개 존재하는 상태를 유지해 달라"​**고 선언하는 것이다.

현재 실제 Pod가 2개라면 Controller는 Desired State와 Current State의 차이를 감지하고 새로운 Pod를 생성하려고 한다.

```text
Desired State = 3
Current State = 2
        ↓
Controller가 차이 확인
        ↓
Reconciliation
        ↓
Current State = 3
```

이처럼 Kubernetes의 Object, Declarative Model, Desired State, Controller, Reconciliation은 서로 연결된 개념이다.

---

# 4. Kubernetes Manifest의 기본 구조

일반적인 Kubernetes Manifest에서는 다음과 같은 Field를 자주 볼 수 있다.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
  namespace: default
  labels:
    app: web
spec:
  replicas: 3
```

주요 Field의 역할은 다음과 같다.

| Field | 역할 |
|---|---|
| `apiVersion` | Resource가 사용하는 Kubernetes API Group과 Version |
| `kind` | 생성하려는 Object의 종류 |
| `metadata` | Name, Namespace, Label, Annotation 등 Object의 식별 정보 |
| `spec` | 사용자가 원하는 Desired State |
| `status` | Kubernetes가 관찰한 Current / Observed State |

여기서 주의할 점이 있다. **모든 Kubernetes Resource가 완전히 동일한 `spec`과 `status` 구조를 갖는 것은 아니다.**

Resource마다 Schema가 다르며, 여러 주요 Kubernetes Object에서 `spec`과 `status`를 통해 원하는 상태와 관찰된 상태를 표현한다. 따라서 `모든 Kubernetes Object는 무조건 동일한 5개 Field를 가진다`고 외우면 정확하지 않다.

## spec과 status

KCNA에서는 특히 `spec`과 `status`를 명확하게 구분해야 한다.

```text
spec
→ 사용자가 선언한 Desired State

status
→ Kubernetes가 관찰한 Current / Observed State
```

예를 들어 Deployment가 `replicas: 3`을 원하지만 현재 Replica가 2개라면 Controller가 둘의 차이를 확인하고 Current State를 Desired State에 맞추려고 한다.

```text
spec = Desired Replica 3
status = Observed Replica 2
          ↓
     Reconciliation
          ↓
Observed State를 Desired State에 맞춤
```

### KCNA 시험 포인트

- `spec` = Desired State
- `status` = Current / Observed State
- Controller = Desired State와 Current State의 차이를 관찰하고 조정
- 지속적인 조정 과정 = Reconciliation

`status represents the desired state`라는 설명은 틀리다.

# 5. API Group과 Version

`apiVersion`은 단순히 Kubernetes Software Version을 적는 Field가 아니다. **해당 Resource가 어느 API Group의 어떤 Version을 사용하는지 나타낸다.**

예를 들어 Pod는 다음과 같이 작성한다.

```yaml
apiVersion: v1
kind: Pod
```

Deployment는 다음과 같다.

```yaml
apiVersion: apps/v1
kind: Deployment
```

왜 Pod는 `v1`이고 Deployment는 `apps/v1`일까?

Kubernetes API가 Resource를 성격에 따라 여러 **API Group**으로 나누어 관리하기 때문이다.

API Group은 크게 **Core API Group**과 **Named API Group**으로 구분할 수 있다.

---

## 5.1 Core API Group

Kubernetes의 기본적인 Resource들은 **Core API Group**에 속한다.

Core API Group은 다른 Group과 달리 Group 이름을 `apiVersion`에 적지 않고 Version만 작성한다.

```yaml
apiVersion: v1
```

대표적인 Resource는 다음과 같다.

| Resource | API Group | apiVersion |
|---|---|---|
| Pod | Core | `v1` |
| Service | Core | `v1` |
| ConfigMap | Core | `v1` |
| Secret | Core | `v1` |
| Namespace | Core | `v1` |
| PersistentVolume | Core | `v1` |
| PersistentVolumeClaim | Core | `v1` |

Core Group이라고 다음처럼 작성하지 않는다.

```text
core/v1   ❌
```

실제로는 Group 이름이 생략된다.

```text
v1        ✅
```

REST API Path에서도 Core Group은 `/api/v1`을 사용한다.

따라서 `apiVersion: v1`을 보면 단순히 Version 1이라고만 생각하지 않고 **Core API Group의 v1 Version**이라고 이해하면 된다.

---

## 5.2 Named API Group

Core API Group 이외의 Resource는 이름을 가진 API Group에 속한다.

기본 형식은 다음과 같다.

```text
<API Group>/<Version>
```

Deployment는 `apps` Group의 `v1` Version이다.

```yaml
apiVersion: apps/v1
kind: Deployment
```

Job은 `batch` Group이다.

```yaml
apiVersion: batch/v1
kind: Job
```

Ingress는 `networking.k8s.io` Group이다.

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
```

Named API Group의 REST Path는 개념적으로 다음과 같다.

```text
/apis/<group>/<version>
```

KCNA에서 알아둘 대표 Resource는 다음과 같다.

| Resource | API Group | apiVersion |
|---|---|---|
| Pod | Core | `v1` |
| Service | Core | `v1` |
| ConfigMap | Core | `v1` |
| Secret | Core | `v1` |
| Namespace | Core | `v1` |
| Deployment | `apps` | `apps/v1` |
| ReplicaSet | `apps` | `apps/v1` |
| StatefulSet | `apps` | `apps/v1` |
| DaemonSet | `apps` | `apps/v1` |
| Job | `batch` | `batch/v1` |
| CronJob | `batch` | `batch/v1` |
| Ingress | `networking.k8s.io` | `networking.k8s.io/v1` |
| NetworkPolicy | `networking.k8s.io` | `networking.k8s.io/v1` |
| Role | `rbac.authorization.k8s.io` | `rbac.authorization.k8s.io/v1` |
| ClusterRole | `rbac.authorization.k8s.io` | `rbac.authorization.k8s.io/v1` |

모든 API Group을 완벽하게 암기할 필요는 없지만 다음 정도는 바로 연결할 수 있어야 한다.

```text
Pod / Service / ConfigMap / Secret
→ Core API Group
→ v1

Deployment / ReplicaSet / StatefulSet / DaemonSet
→ apps/v1

Job / CronJob
→ batch/v1

Ingress / NetworkPolicy
→ networking.k8s.io/v1
```

## 왜 API Group을 나눌까?

Kubernetes에는 Workload, Networking, Batch, RBAC, Storage 등 여러 기능이 존재한다. 모든 API Object를 하나의 거대한 Group에 넣는 대신 기능 영역별로 API Group을 나누면 API를 체계적으로 관리하고 확장하기 쉽다.

```text
Kubernetes API
│
├── Core
│   ├── Pod
│   ├── Service
│   ├── ConfigMap
│   └── Secret
│
├── apps
│   ├── Deployment
│   ├── ReplicaSet
│   ├── StatefulSet
│   └── DaemonSet
│
├── batch
│   ├── Job
│   └── CronJob
│
└── networking.k8s.io
    ├── Ingress
    └── NetworkPolicy
```

### 시험에서 바로 판단하기

| 문장 | 판단 |
|---|---|
| Pod uses `apps/v1`. | ❌ Pod는 Core Group의 `v1` |
| Deployment belongs to the `apps` API group. | ✅ |
| Job belongs to the `batch` API group. | ✅ |
| Ingress belongs to the Core API Group. | ❌ |
| ConfigMap uses `v1`. | ✅ |

# 6. Alpha, Beta, Stable API Version

Kubernetes API Version은 API의 성숙도를 나타내기도 한다.

| Version | 단계 | 의미 |
|---|---|---|
| `v1alpha1` | Alpha | 실험적이며 변경 또는 제거 가능성이 큼 |
| `v1beta1` | Beta | Alpha보다 성숙했지만 변경 가능 |
| `v1` | Stable / GA | 안정적인 API Version |

여기서 `v1beta1`은 Kubernetes 전체 Software가 Beta라는 의미가 아니다. **해당 API Version의 Maturity Level**을 의미한다.

Kubernetes Upgrade 과정에서는 오래된 Alpha 또는 Beta API Version이 Deprecated되거나 제거될 수 있으므로 실제 운영에서도 현재 Cluster가 지원하는 `apiVersion`을 확인하는 것이 중요하다.

### KCNA 시험 포인트

```text
Alpha
→ Experimental

Beta
→ Alpha보다 성숙하지만 변경 가능

Stable
→ vX 형태의 안정적인 API Version
```

# 7. API Resource 확인과 Discovery

Kubernetes API에는 많은 Resource가 있기 때문에 실제 Cluster에서 어떤 API Resource와 Version이 제공되는지 확인하는 방법도 있다.

대표적으로 다음 명령을 사용할 수 있다.

```bash
kubectl api-resources
```

이 명령에서는 Resource 이름, Short Name, API Version, Namespace Scope, Kind 등을 확인할 수 있다.

예를 들어 이전 글에서 살펴본 `NAMESPACED` 여부도 여기에서 확인할 수 있다.

또 Resource의 Field 구조를 확인할 때는 다음과 같은 명령을 사용할 수 있다.

```bash
kubectl explain deployment
kubectl explain deployment.spec
```

KCNA는 실기 시험이 아니므로 명령어 자체를 암기하는 것이 핵심은 아니지만, **Kubernetes API가 Resource Schema와 Discovery 기능을 제공한다**는 관점으로 알아두면 API 구조를 이해하는 데 도움이 된다.

# 8. Kubernetes API는 확장할 수 있다

Kubernetes에는 기본 Resource만 존재하는 것이 아니다.

**CRD(CustomResourceDefinition)​**를 이용하면 Kubernetes API에 새로운 Resource Type을 추가할 수 있다.

```text
Kubernetes API
│
├── Built-in Resources
│   ├── Pod
│   ├── Deployment
│   └── Service
│
└── Custom Resources
    └── CRD를 통해 추가
```

Cloud Native Project를 사용하다 보면 `Certificate`, `ServiceMonitor`, `VirtualService`처럼 Kubernetes 기본 Resource가 아닌 Object를 볼 수 있다. 이런 Resource는 해당 Project가 CRD를 생성하여 Kubernetes API를 확장한 경우가 많다.

KCNA 수준에서는 CRD YAML 작성법이나 Custom Controller 구현 방법까지 외울 필요는 없지만 **Kubernetes API가 CRD를 통해 확장될 수 있는 Extensible API라는 점**은 알아두는 것이 좋다.

# 9. Declarative vs Imperative

Kubernetes Resource를 관리하는 방식은 크게 **Imperative**와 **Declarative**로 나눌 수 있다.

## Imperative

Imperative 방식은 사용자가 수행할 동작을 직접 명령한다.

```bash
kubectl run nginx --image=nginx:1.27
kubectl create deployment web --image=nginx:1.27
kubectl scale deployment web --replicas=3
```

빠르게 Resource를 만들거나 수정할 때 편리하지만, 명령만 사용하면 Desired State를 표현하는 파일이 남지 않기 때문에 Version Control과 반복 가능한 운영에는 상대적으로 불리하다.

## Declarative

Declarative 방식에서는 수행 절차를 하나하나 명령하는 것이 아니라 **원하는 최종 상태를 선언한다.**

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: web
spec:
  replicas: 3
```

그리고 이를 적용한다.

```bash
kubectl apply -f deployment.yaml
```

사용자는 Pod를 하나씩 생성하라고 명령하는 것이 아니라 **Replica가 3개인 상태를 유지해 달라**고 선언한다.

이 방식은 Kubernetes의 Reconciliation과 직접 연결된다.

```text
Manifest
   │
   │ Desired State
   ▼
Kubernetes API
   │
   ▼
Controller
   │
   │ Reconciliation
   ▼
Current State를 Desired State에 맞춤
```

Manifest를 Git에 저장하면 변경 이력을 관리할 수 있기 때문에 Declarative Model은 이후 공부할 **GitOps의 기반**이 된다.

### 시험용 비교

| 구분 | Imperative | Declarative |
|---|---|---|
| 핵심 | 수행할 작업 직접 명령 | 원하는 최종 상태 선언 |
| 대표 예 | `kubectl run`, `create`, `scale` | Manifest + `kubectl apply` |
| 관리 중심 | Command | Desired State |
| 변경 이력 관리 | 상대적으로 불편 | Git과 결합하기 좋음 |
| Cloud Native 운영 | 사용 가능 | 핵심적인 접근 방식 |

여기서 중요한 것은 `kubectl create`라는 명령어 자체를 외우는 것이 아니라 **Imperative는 Action 중심, Declarative는 State 중심​**이라는 차이다.

# 10. Container Image

Pod 안에서 실제로 실행되는 것은 Container이고, Container는 **Container Image를 기반으로 생성된다.**

```text
Application Source
       ↓
Container Image
       ↓
Container Registry
       ↓
Worker Node
       ↓
Container Runtime
       ↓
Container
```

Container Image는 Application Binary, Library, Runtime Dependency, Filesystem 등 Application 실행에 필요한 요소를 패키징한 Template이다.

Image는 일반적으로 **읽기 전용 Layer들의 집합**으로 구성되며, Container는 이 Image를 기반으로 실행되는 Instance라고 이해할 수 있다.

```text
Image
→ Container 실행을 위한 Template

Container
→ Image를 기반으로 실제 실행되는 Instance
```

Container Image와 Runtime 관련 Open Standard는 **OCI(Open Container Initiative)​**가 정의한다.

KCNA에서는 OCI Specification의 세부 구조를 외울 필요는 없지만, Cloud Native 생태계에서 Container Format과 Runtime이 특정 Vendor 하나에만 종속되지 않고 **Open Standard를 기반으로 발전한다**는 점을 알아두면 좋다.

---

# 11. Container Registry

Container Image는 일반적으로 **Container Registry**에 저장하고 배포한다.

대표적인 Registry에는 Docker Hub, GitHub Container Registry, Amazon ECR, Google Artifact Registry, Harbor 등이 있다.

Pod에서는 다음과 같이 Image를 지정한다.

```yaml
containers:
  - name: nginx
    image: nginx:1.27
```

여기서 `nginx`는 Image 이름이고 `1.27`은 Tag이다.

Private Registry에서 Image를 Pull해야 한다면 인증이 필요할 수 있으며 Kubernetes에서는 `imagePullSecrets`를 이용해 Registry Credential을 제공할 수 있다.

전체 흐름은 다음과 같다.

```text
Registry
   │
   │ Image Pull
   ▼
Worker Node
   │
   ▼
Container Runtime
   │
   ▼
Container
```

---

# 12. Image Tag와 Digest

Container Image를 식별할 때 Tag와 Digest를 사용할 수 있다.

## Tag

```text
nginx:1.27
```

Tag는 사람이 읽기 쉬운 Version Label이지만 Registry에서 같은 Tag가 이후 다른 Image를 가리키도록 변경될 수 있다.

## Digest

```text
nginx@sha256:...
```

Digest는 특정 Image Content를 식별한다.

| 구분 | Tag | Digest |
|---|---|---|
| 예 | `nginx:1.27` | `nginx@sha256:...` |
| 가독성 | 높음 | 낮음 |
| 동일 이름이 다른 Content를 가리킬 가능성 | 있음 | Content가 달라지면 Digest도 달라짐 |
| 특정 Image 고정 | 상대적으로 약함 | 강함 |

KCNA에서 Digest 계산 방법까지 알 필요는 없지만 **Tag는 변경될 수 있고 Digest는 특정 Image Content를 식별한다**는 차이는 알아두면 좋다.

---

# 13. latest Tag

다음과 같이 Tag를 생략하면 일반적으로 `latest` Tag가 사용된다.

```yaml
image: nginx
```

하지만 `latest`는 **항상 가장 최신 Software Release를 의미하는 특별한 기능이 아니다.**

```text
latest = 항상 최신 Version   ❌
```

`latest` 역시 Registry에서 사용하는 Tag 이름일 뿐이다.

따라서 Production 환경에서는 명시적인 Version Tag나 Digest를 사용하는 것이 더 예측 가능한 배포에 도움이 된다.

# 14. imagePullPolicy와 ImagePullBackOff

Kubernetes에는 Container Image를 언제 Pull할지 결정하는 `imagePullPolicy`가 있다.

| 값 | 의미 |
|---|---|
| `Always` | Container 시작 시 Registry에서 Image 정보를 확인 |
| `IfNotPresent` | Node에 해당 Image가 없을 때 Pull |
| `Never` | Registry에서 Image를 Pull하지 않음 |

또한 Pod 상태를 확인하다 보면 `ImagePullBackOff`를 볼 수 있다.

```text
ImagePullBackOff
→ Kubernetes가 필요한 Container Image를 Pull하지 못하고
  재시도 사이에 Backoff 중인 상태
```

대표적인 원인은 잘못된 Image Name이나 Tag, 존재하지 않는 Image, Private Registry 인증 실패 등이 있다.

`Pending`과 `ImagePullBackOff`를 같은 문제로 이해하면 안 된다.

```text
Pending
→ Scheduling 단계에서도 발생할 수 있음

ImagePullBackOff
→ Container Image Pull 문제와 연결
```

# 15. Container Runtime과 CRI

Container Image를 실제 Container Process로 실행하는 것은 **Container Runtime**이다.

대표적인 CRI-compatible Runtime으로는 `containerd`와 `CRI-O`가 있다.

kubelet은 특정 Runtime 구현에 직접 종속되는 대신 **CRI(Container Runtime Interface)​**라는 표준 Interface를 통해 Runtime과 통신한다.

```text
kubelet
   │
   │ CRI
   ▼
Container Runtime
   │
   ├── containerd
   └── CRI-O
```

각 역할은 다음과 같다.

| 구성요소 | 역할 |
|---|---|
| kubelet | 해당 Node에서 Pod가 원하는 상태로 실행되도록 관리 |
| CRI | kubelet과 Container Runtime 사이의 표준 Interface |
| Container Runtime | Image를 기반으로 실제 Container 실행 |

KCNA에서는 이후 계속 등장하는 CRI, CNI, CSI를 구분해야 한다.

| Interface | 영역 |
|---|---|
| CRI | Container Runtime |
| CNI | Container Networking |
| CSI | Container Storage |

시험에서는 다음처럼 바로 연결할 수 있어야 한다.

```text
Runtime → CRI
Network → CNI
Storage → CSI
```

# 16. Pod와 Container의 관계

Kubernetes가 Scheduling하는 기본 단위는 개별 Container가 아니라 **Pod**이다.

```text
Node
 │
 ▼
Pod
├── Container A
└── Container B
```

Pod에는 하나 이상의 Container가 포함될 수 있다.

같은 Pod 안의 Container는 **같은 Network Namespace와 Pod IP를 공유**하므로 `localhost`를 이용해 서로 통신할 수 있다.

Storage는 조금 다르게 이해해야 한다. Pod에 Volume을 정의하고 여러 Container가 해당 Volume을 각각 Mount하도록 구성하면 File을 공유할 수 있다. 같은 Pod에 있다고 해서 모든 Volume이 자동으로 모든 Container에 Mount되는 것은 아니다.

### KCNA 시험 포인트

```text
Pod
→ Kubernetes의 Scheduling 단위

Container
→ Pod 안에서 실제 Application Process가 실행되는 환경
```

`Kubernetes schedules individual containers directly`라는 설명은 틀리다.

---

# 17. Init Container

**Init Container**는 Application Container가 시작되기 전에 초기화 작업을 수행한다.

일반 Init Container가 여러 개라면 순서대로 실행되며, 각각 성공적으로 완료되어야 다음 Init Container로 넘어간다. 일반 Init Container가 완료된 후 Application Container가 시작된다.

```text
Pod 시작
   ↓
Init Container 1
   ↓
Init Container 2
   ↓
Application Container
```

대표적인 사용 사례는 Configuration 준비, Dependency 확인, 초기 데이터 생성, 필요한 File 다운로드 등이다.

### KCNA 시험 포인트

Application 실행 전에 준비 작업을 수행하고 완료되는 Container를 묻는다면 **Init Container**를 생각하면 된다.

---

# 18. Sidecar Container

Sidecar Container는 Main Application Container와 함께 실행되면서 Application을 보조한다.

대표적으로 Logging Agent, Proxy, Monitoring Agent, Data Synchronization 등에 사용할 수 있다.

```text
Pod
├── Main Application Container
└── Sidecar Container
    ├── Proxy
    ├── Logging
    └── Monitoring
```

같은 Pod에 있기 때문에 Main Container와 Network Namespace를 공유하고, 동일 Volume을 Mount하도록 구성하면 File도 공유할 수 있다.

최근 Kubernetes에서는 Native Sidecar Container를 특수한 Init Container 형태로 지원하지만, KCNA에서는 세부 YAML보다 **일반 Init Container와 Sidecar의 역할 차이**를 이해하는 것이 중요하다.

| 구분 | Init Container | Sidecar Container |
|---|---|---|
| 실행 시점 | Application 시작 전 | Application과 함께 |
| 목적 | 초기화 | Main Application 보조 |
| 일반적인 동작 | 작업 완료 후 종료 | Pod Lifecycle 동안 지속 실행 가능 |
| 예 | 설정 준비, Dependency 확인 | Logging, Proxy, Monitoring |

---

# 19. Scheduling이란?

Pod Object가 생성되었다고 바로 Worker Node에서 실행되는 것은 아니다. 먼저 **어느 Worker Node에서 Pod를 실행할지 결정**해야 한다.

이를 Scheduling이라고 하며 기본 Scheduler인 `kube-scheduler`가 담당한다.

```text
Pod 생성
Node = 미지정
      ↓
kube-scheduler
      ↓
Node 선택
      ↓
Binding
      ↓
선택된 Node의 kubelet
      ↓
Container Runtime
      ↓
Container 실행
```

여기서 반드시 구분해야 할 것은 **Scheduler는 Node를 선택할 뿐 Container를 직접 실행하지 않는다는 것**이다.

```text
kube-scheduler
→ 어느 Node에서 실행할지 결정

kubelet
→ 해당 Node에서 Pod Lifecycle 관리

Container Runtime
→ 실제 Container 실행
```

---

# 20. Filtering, Scoring, Binding

kube-scheduler의 Node 선택 과정은 크게 **Filtering과 Scoring**으로 이해할 수 있으며 최종적으로 선택한 Node를 Pod에 적용하는 **Binding** 과정이 이어진다.

## Filtering

Pod를 실행할 수 없는 Node를 제외한다.

Resource Request를 만족하지 못하거나 `nodeSelector`, Required Affinity, Taint/Toleration 등의 Scheduling Constraint를 만족하지 못하는 Node가 제외될 수 있다.

Filtering을 통과하여 Pod를 실행할 수 있는 Node를 **Feasible Node**라고 한다.

## Scoring

Filtering을 통과한 Node가 여러 개라면 Scheduler가 각 Node를 평가하여 적합도에 따라 점수를 부여한다.

## Binding

최종적으로 선택된 Node에 Pod를 할당하는 과정이다.

```text
All Nodes
   ↓
Filtering
   ↓
Feasible Nodes
   ↓
Scoring
   ↓
Best Node
   ↓
Binding
```

### KCNA 시험 포인트

- Filtering = 실행할 수 없는 Node 제외
- Scoring = Feasible Node를 평가하고 순위 결정
- Binding = 선택한 Node에 Pod를 할당

---

# 21. Pod가 Pending 상태인 이유

Pod가 `Pending` 상태라고 해서 무조건 Container Image 문제라고 생각하면 안 된다.

적절한 Node를 찾지 못해 Scheduling되지 않은 경우에도 Pending 상태에 머물 수 있다.

대표적인 Scheduling 실패 원인은 다음과 같다.

- CPU 또는 Memory Request를 만족할 Node가 없음
- `nodeSelector`에 맞는 Node가 없음
- Required Node Affinity 조건을 만족하는 Node가 없음
- Node에 Taint가 있지만 Pod에 적절한 Toleration이 없음
- Volume 또는 PVC의 Scheduling Constraint를 만족하지 못함
- 기타 Hardware / Software / Policy Constraint 불일치

따라서 `Pending` 상태라면 **Scheduler가 해당 Pod를 배치할 수 있는 Node가 있는지**도 확인해야 한다.

# 22. Resource Requests와 Limits

Container에는 CPU와 Memory의 Request와 Limit을 설정할 수 있다.

```yaml
resources:
  requests:
    cpu: "250m"
    memory: "256Mi"
  limits:
    cpu: "500m"
    memory: "512Mi"
```

두 값은 비슷해 보이지만 역할이 다르다.

## Requests

`requests`는 Container가 필요로 하는 Resource 양을 의미하며 **Scheduler가 해당 Pod를 Node에 배치할 수 있는지 판단하는 핵심 조건 중 하나**이다.

Scheduler는 단순히 현재 순간의 실제 CPU 사용률만 확인하는 것이 아니라 Node Capacity와 이미 Scheduling된 Workload의 Resource Request를 기준으로 Scheduling 가능성을 판단한다.

예를 들어 Pod가 2 CPU를 Request한다고 해보자.

| Node | Scheduling 가능 여부 |
|---|---|
| Node A: Scheduling에 사용할 수 있는 CPU 1 | 불가능 |
| Node B: Scheduling에 사용할 수 있는 CPU 4 | 가능 |

다만 Resource가 Scheduler의 유일한 조건은 아니다. Scheduler는 Resource Requirement 외에도 Node Selector, Affinity, Taint/Toleration, Hardware/Software/Policy Constraint 등을 함께 고려한다.

## Limits

`limits`는 Container가 실행된 이후 사용할 수 있는 Resource 상한과 연결된다.

CPU Limit을 넘어 CPU를 사용하려 하면 CPU Throttling이 발생할 수 있고, Memory Limit을 초과하면 Kernel의 Memory 관리 과정에서 Container가 OOM Kill될 수 있다.

### KCNA에서 반드시 구분

| 항목 | 핵심 역할 |
|---|---|
| `requests` | Scheduling 판단에 사용하는 Resource 요구량 |
| `limits` | 실행 중 Resource 사용 제한 |

시험용으로는 다음처럼 기억하면 된다.

```text
Requests
→ Scheduling

Limits
→ Runtime Resource Enforcement
```

---

# 23. CPU와 Memory Resource 단위

CPU Request나 Limit에서는 다음과 같은 값을 볼 수 있다.

```yaml
cpu: "250m"
```

`m`은 millicpu 또는 millicore 단위이다.

| 값 | CPU |
|---|---:|
| `1000m` | 1 CPU |
| `500m` | 0.5 CPU |
| `250m` | 0.25 CPU |

Memory에서는 `Mi`, `Gi` 같은 단위를 자주 사용한다.

KCNA에서는 복잡한 Resource 계산보다 **Request와 Limit의 목적 차이**를 먼저 이해하는 것이 중요하다.

---

# 24. nodeSelector

특정 Label을 가진 Node에만 Pod를 Scheduling하고 싶다면 `nodeSelector`를 사용할 수 있다.

Node에 다음 Label이 있다고 해보자.

```text
disktype=ssd
```

Pod에서는 다음과 같이 지정할 수 있다.

```yaml
spec:
  nodeSelector:
    disktype: ssd
```

이 Pod는 `disktype=ssd` Label을 가진 Node만 Scheduling 후보로 사용할 수 있다.

따라서 `nodeSelector`는 **Node Label을 기준으로 하는 단순한 Hard Constraint**라고 이해할 수 있다.

---

# 25. Node Affinity

Node Affinity 역시 Node Label을 기준으로 하지만 `nodeSelector`보다 더 다양한 조건을 표현할 수 있다.

대표적으로 다음 두 가지를 구분해야 한다.

## requiredDuringSchedulingIgnoredDuringExecution

조건을 반드시 만족해야 Scheduling할 수 있다. 즉 **Hard Requirement**이다.

## preferredDuringSchedulingIgnoredDuringExecution

조건을 만족하는 Node를 선호하지만 반드시 만족해야 하는 것은 아니다. 즉 **Soft Preference**이다.

| 규칙 | 의미 |
|---|---|
| `required...` | 반드시 만족 |
| `preferred...` | 가능하면 만족 |

`IgnoredDuringExecution`은 Pod가 Scheduling된 이후 Node Label이 변경되어 더 이상 Affinity 조건을 만족하지 않더라도 **그 이유만으로 기존 Pod가 자동 Eviction되지는 않는다는 의미**로 이해할 수 있다.

### nodeSelector와 Node Affinity

```text
nodeSelector
→ 단순한 Node Label 일치
→ Hard Rule

Node Affinity
→ Node Label 기반
→ Required / Preferred 등 더 다양한 조건 표현
```

---

# 26. Pod Affinity와 Anti-Affinity

Node Affinity가 **Node Label**을 기준으로 한다면 Pod Affinity와 Anti-Affinity는 **다른 Pod가 어디에 배치되어 있는지**를 기준으로 Scheduling Rule을 만든다.

Pod Affinity는 특정 Pod와 가까운 Topology에 배치하고 싶은 경우 사용할 수 있고, Pod Anti-Affinity는 특정 Pod와 떨어진 위치에 배치하고 싶은 경우 사용할 수 있다.

예를 들어 동일 Application Replica를 여러 Node로 분산시킬 수 있다.

```text
Node A → web-1
Node B → web-2
Node C → web-3
```

이렇게 분산하면 Node 하나가 장애 나더라도 Application의 모든 Replica가 동시에 영향을 받는 위험을 줄일 수 있다.

Pod Affinity/Anti-Affinity는 단순히 같은 Node만 의미하는 것이 아니라 **Node나 Zone과 같은 Topology Domain**을 기준으로 사용할 수 있다.

### KCNA 시험 포인트

| 기능 | 기준 |
|---|---|
| Node Affinity | Node Label |
| Pod Affinity | 다른 Pod의 위치와 Topology |
| Pod Anti-Affinity | 다른 Pod와 떨어진 Topology |

---

# 27. Topology Spread Constraints

Workload의 Replica를 여러 Node나 Zone에 균형 있게 분산하기 위해 **Topology Spread Constraints**를 사용할 수 있다.

예를 들어 Pod가 하나의 Zone에만 몰리지 않게 다음과 같이 분산하는 것이 목적이다.

```text
Zone A
├── web-1
└── web-2

Zone B
├── web-3
└── web-4
```

Pod Anti-Affinity와 목적이 비슷하게 보일 수 있지만 Topology Spread Constraints는 **Pod 분포의 균형 정도를 직접 제어하기 위한 Scheduling 기능**이다.

KCNA에서는 상세 YAML까지 외울 필요는 없지만 **Availability를 높이기 위해 Pod Replica를 Node나 Zone과 같은 Topology Domain에 분산할 수 있다**는 개념 정도는 알아두면 좋다.

---

# 28. Taint와 Toleration

`nodeSelector`나 Affinity 계열이 **Pod가 어떤 Node에 배치되고 싶은지를 표현하는 방식**이라면, Taint와 Toleration은 반대 방향에서 이해하면 쉽다.

**Taint는 Node에 설정하여 특정 Pod가 해당 Node에 Scheduling되는 것을 제한하는 기능**이고, **Toleration은 Pod에 설정하여 특정 Taint를 허용할 수 있게 하는 기능**이다.

```text
nodeSelector / Affinity
→ Pod 입장에서 "어떤 Node에 가고 싶은가?"

Taint
→ Node 입장에서 "아무 Pod나 들어오지 마"

Toleration
→ Pod 입장에서 "나는 이 Taint를 허용할 수 있어"
```

즉 개념적으로 Affinity 계열은 **Pod가 Node를 끌어당기는(attract)** 방향이고, Taint는 **Node가 Pod를 밀어내는(repel)** 방향이라고 생각하면 구분하기 쉽다.

다만 `attract`와 `repel`은 이해를 위한 표현이며 실제 Scheduler 동작을 완전히 설명하는 공식 알고리즘 이름은 아니다.

---

# 29. Taint

Taint는 Node에 설정한다.

예를 들어 GPU가 장착된 전용 Worker Node가 있다고 해보자.

```text
gpu-node
Taint: gpu=true:NoSchedule
```

GPU Node에 아무 제약도 없다면 다른 Scheduling 조건만 만족하면 일반 Application Pod가 GPU Node에 배치될 수도 있다.

GPU Node를 GPU Workload 중심으로 사용하고 싶다면 Taint를 설정하여 일반 Pod의 Scheduling을 제한할 수 있다.

```text
GPU Node
Taint: gpu=true:NoSchedule
        │
        ├── 일반 Pod
        │      X
        │   Scheduling 제한
        │
        └── GPU Pod
               │
               │ 적절한 Toleration 보유
               ▼
          Scheduling 후보 가능
```

따라서 Taint는 GPU Node뿐 아니라 특정 Hardware가 있는 Node나 특정 Workload 전용 Node를 구성할 때 활용할 수 있다.

---

# 30. Toleration

Toleration은 Pod에 설정한다.

Pod가 Node의 특정 Taint와 대응되는 Toleration을 가지고 있다면 **해당 Taint 때문에 Scheduling Candidate에서 제외되는 것을 피할 수 있다.**

예를 들어 Node에 다음 Taint가 있다고 하자.

```text
gpu=true:NoSchedule
```

GPU Application Pod가 이에 대한 Toleration을 가지고 있다면 해당 Node가 Scheduling 후보가 될 수 있다.

여기서 KCNA에서 반드시 기억해야 할 내용이 있다.

> **Toleration이 있다고 해서 해당 Node에 반드시 Scheduling되는 것은 아니다.**

Toleration은 해당 Taint를 허용할 뿐이다. Scheduler는 여전히 Resource Request, Node Affinity, Pod Affinity/Anti-Affinity, 다른 Taint와 Scheduling Policy 등을 함께 판단한다.

```text
Toleration 있음
→ 해당 Taint 때문에 거절되지 않음
→ 해당 Node가 Scheduling 후보가 될 수 있음
→ 반드시 해당 Node가 선택되는 것은 아님
```

따라서 `Toleration guarantees scheduling to a tainted node`라는 설명은 틀리다.

---

# 31. Control Plane Node와 Taint

Taint와 Toleration을 이해할 때 볼 수 있는 실제 예가 **Control Plane Node**이다.

kubeadm 등 일반적인 Kubernetes Cluster 구성에서는 Control Plane Node에 Taint를 적용해 일반 Application Workload의 Scheduling을 제한하는 경우가 많다.

```text
Control Plane Node
│
├── kube-apiserver
├── kube-scheduler
├── kube-controller-manager
│
└── Taint
      └── 일반 Workload Scheduling 제한
```

Control Plane Node는 Cluster 관리에 중요한 Component를 실행하므로 Application Workload와 분리해서 운영하는 경우가 많기 때문이다.

그러나 다음과 같이 이해하면 안 된다.

```text
Control Plane Node
→ Kubernetes 규칙상 일반 Pod 실행이 절대 불가능하다   ❌
```

Cluster 구성에 따라 Taint를 제거하거나 적절한 Toleration을 이용해 Workload를 실행할 수도 있다.

따라서 정확한 표현은 **일반적인 kubeadm 구성에서는 Control Plane Node에 Taint를 적용하여 일반 Workload Scheduling을 제한하는 경우가 많다** 정도이다.

---

# 32. GPU 전용 Node로 Affinity와 Taint 차이 이해하기

Taint/Toleration과 Node Affinity의 차이를 이해하기 좋은 예가 GPU Node이다.

다음과 같은 Node가 있다고 해보자.

```text
Node: gpu-node-01

Label:
  accelerator=nvidia

Taint:
  gpu=true:NoSchedule
```

GPU Application Pod에는 다음 조건을 적용할 수 있다.

```text
Node Affinity
→ accelerator=nvidia Node를 선택

Toleration
→ gpu=true:NoSchedule Taint를 허용
```

두 기능은 서로 다른 문제를 해결한다.

### Node Affinity

```text
"GPU가 있는 Node에서 실행하고 싶다."
```

Pod가 **원하는 Node의 특성**을 지정하는 것이다.

### Taint / Toleration

```text
"GPU Node에는 아무 Pod나 들어오면 안 된다."
```

Node가 **허용할 Workload를 제한**하는 것이다.

```text
                    GPU Node
          Label: accelerator=nvidia
          Taint: gpu=true:NoSchedule
                       ▲
                       │
        ┌──────────────┴──────────────┐
        │                             │
 일반 Application Pod             GPU Pod
        │                             │
 Toleration 없음              Toleration 있음
        │                     Node Affinity 있음
        X                             │
 Scheduling 제한                     ▼
                              Scheduling 후보
```

여기서 중요한 것은 **Taint/Toleration만으로 "이 GPU Pod를 반드시 GPU Node에 보내라"는 요구사항을 완전히 표현하지 못한다는 것​**이다.

Toleration은 해당 Node에 들어갈 수 있는 **허용 조건**에 가깝고, Node Selector나 Node Affinity는 특정 특성의 Node를 **선택하는 조건**에 가깝다.

# 33. Taint Effect

Taint에는 Effect가 있으며 대표적으로 `NoSchedule`, `PreferNoSchedule`, `NoExecute`를 구분한다.

| Effect | 의미 |
|---|---|
| `NoSchedule` | 해당 Taint를 Tolerate하지 못하는 새 Pod를 Scheduling하지 않음 |
| `PreferNoSchedule` | 가능하면 해당 Pod의 Scheduling을 피함 |
| `NoExecute` | 새 Scheduling뿐 아니라 이미 실행 중인 Pod에도 영향을 줄 수 있음 |

KCNA에서는 세부 Eviction Timing보다 다음 차이를 우선 기억하면 된다.

```text
NoSchedule
→ 새 Pod Scheduling에 영향

PreferNoSchedule
→ 가능하면 피하는 Soft Rule

NoExecute
→ 기존 실행 중 Pod에도 영향 가능
```

---

# 34. Scheduling 관련 기능 비교

| 기능 | 설정/기준 | 핵심 역할 |
|---|---|---|
| `nodeSelector` | Pod / Node Label | 단순한 필수 Node 선택 조건 |
| Node Affinity | Pod / Node Label | Required 또는 Preferred Node 조건 |
| Pod Affinity | Pod / 다른 Pod 위치 | 다른 Pod와 가까운 Topology에 배치 |
| Pod Anti-Affinity | Pod / 다른 Pod 위치 | 다른 Pod와 떨어진 Topology에 배치 |
| Topology Spread | Pod / Topology | Replica를 균형 있게 분산 |
| Taint | Node | 특정 Pod의 Scheduling 제한 |
| Toleration | Pod | 특정 Taint 허용 |

방향으로 기억하면 더 쉽다.

```text
nodeSelector / Node Affinity
Pod ─────────────────────▶ Node
"이런 Node에 가고 싶다."


Taint
Node ─────────────────────▶ Pod
"아무 Pod나 들어오지 마."


Toleration
Pod ─────────────────────▶ Tainted Node
"나는 이 제한을 허용할 수 있다."
```

즉 **Affinity 계열은 attract, Taint는 repel, Toleration은 repel 조건을 허용하는 것​**으로 기억하면 된다.

# 35. Priority와 Preemption

Scheduling을 이해하면서 추가로 알아두면 좋은 개념이 **Pod Priority와 Preemption**이다.

Pod에 Priority가 설정되어 있고 높은 Priority의 Pod를 Scheduling할 수 있는 Resource가 부족한 경우, Scheduler는 상황에 따라 더 낮은 Priority의 Pod를 제거하여 높은 Priority Pod가 Scheduling될 공간을 만들 수 있다.

이 과정을 **Preemption**이라고 한다.

```text
High Priority Pod
       │
       │ Scheduling할 공간 부족
       ▼
Low Priority Pod 제거 가능
       │
       ▼
High Priority Pod Scheduling
```

다만 모든 Scheduling 실패가 Preemption으로 해결되는 것은 아니다. Affinity나 Node Selector 같은 조건 자체를 만족하는 Node가 없다면 낮은 Priority Pod를 제거해도 해결되지 않을 수 있다.

KCNA에서는 세부 PriorityClass YAML보다 다음 정도로 이해하면 충분하다.

```text
Priority
→ 중요한 Pod에 더 높은 Scheduling 우선순위를 부여

Preemption
→ 높은 Priority Pod를 Scheduling하기 위해
  낮은 Priority Pod를 제거할 수 있는 과정
```

# 36. 설정 주입이 필요한 이유

Application의 Configuration을 Container Image 안에 직접 포함하면 환경이 달라질 때마다 Image를 다시 Build해야 할 수 있다.

예를 들어 Application은 동일하지만 Development와 Production의 설정만 다르다고 해보자.

```text
Development
LOG_LEVEL=debug
DB_HOST=dev-db

Production
LOG_LEVEL=info
DB_HOST=prod-db
```

이 설정을 Image 내부에 직접 포함하면 환경마다 서로 다른 Image를 만들게 될 수 있다.

Kubernetes에서는 Application과 Configuration을 분리하기 위해 **ConfigMap과 Secret**을 제공한다.

```text
Container Image
→ Application 실행에 필요한 내용

ConfigMap
→ 민감하지 않은 Configuration

Secret
→ Sensitive Data
```

이를 통해 동일한 Image를 사용하면서 환경별 Configuration만 외부에서 다르게 주입할 수 있다.

# 37. ConfigMap: 민감하지 않은 설정

**ConfigMap**은 Application이 사용하는 **민감하지 않은 Configuration Data를 저장하는 Kubernetes Resource**이다.

대표적으로 다음과 같은 값을 저장할 수 있다.

- Log Level
- Application Mode
- Feature Flag
- 일반 URL
- 일반 Configuration File
- 환경별 설정

예를 들어 다음과 같이 사용할 수 있다.

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  LOG_LEVEL: "info"
  APP_MODE: "production"
```

ConfigMap은 Core API Group에 속하기 때문에 `apiVersion: v1`을 사용한다.

앞에서 공부한 API Group과 연결하면 다음과 같다.

```text
Pod
Service
ConfigMap
Secret
Namespace

→ Core API Group
→ apiVersion: v1
```

## ConfigMap에 저장하면 안 되는 것

ConfigMap은 Non-confidential Configuration을 위한 Resource이다.

따라서 다음과 같은 Sensitive Data는 ConfigMap보다 Secret을 사용하는 것이 적절하다.

- Database Password
- API Token
- Private Key
- Credential
- Authentication Token

시험에서는 우선 데이터 성격을 구분하면 된다.

```text
LOG_LEVEL
→ ConfigMap

APP_MODE
→ ConfigMap

DB_PASSWORD
→ Secret

API_TOKEN
→ Secret
```

---

# 38. Secret: 민감한 정보

**Secret**은 Password, Token, Key 등 Sensitive Data를 저장하기 위한 Kubernetes Resource이다.

대표적으로 다음과 같은 정보를 저장할 수 있다.

- Password
- API Token
- OAuth Token
- SSH Key
- TLS 관련 데이터
- Registry Credential

Secret도 ConfigMap과 마찬가지로 Core API Group에 속한다.

```yaml
apiVersion: v1
kind: Secret
```

개념적으로 다음처럼 구분한다.

```text
ConfigMap
→ Non-confidential Configuration

Secret
→ Sensitive Data
```

하지만 여기서 KCNA에서 매우 중요한 함정이 있다.

> **Kubernetes Secret의 Base64 Encoding은 Encryption이 아니다.**

---

# 39. Secret의 Base64는 암호화가 아니다

Secret의 `data` Field에는 값이 Base64 형태로 표현된다.

예를 들면 다음과 같다.

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-secret
type: Opaque
data:
  username: YWRtaW4=
  password: cGFzc3dvcmQ=
```

여기서 다음 값은 암호화된 값이 아니다.

```text
cGFzc3dvcmQ=
```

단순히 Base64 Encoding된 값이다.

```text
Plain Text
   │
   │ Base64 Encode
   ▼
Base64 String
```

Base64는 누구나 쉽게 Decode할 수 있으므로 Confidentiality를 제공하지 않는다.

```text
Base64 Encoding ≠ Encryption
```

따라서 다음 설명은 틀리다.

```text
"Secret은 Base64로 암호화되므로 안전하다."   ❌
```

정확하게는 다음과 같다.

```text
Secret
→ Sensitive Data를 위한 Kubernetes Resource

Base64
→ Data 표현에 사용되는 Encoding

Encryption
→ 별도로 적용해야 하는 보안 기능
```

---

# 40. Secret의 `data`와 `stringData`

Secret에서는 `data` 외에 `stringData`를 사용할 수도 있다.

`data`에서는 Base64 형태의 값을 사용하지만 `stringData`를 이용하면 일반 문자열을 입력할 수 있다.

```yaml
apiVersion: v1
kind: Secret
metadata:
  name: db-secret
type: Opaque
stringData:
  username: admin
  password: password
```

API Server가 이를 처리하여 Secret Data로 저장한다.

KCNA에서 이 Field의 세부 구현까지 외울 필요는 없지만 다음 정도는 알아두면 된다.

```text
Secret.data
→ Base64 형태의 값

Secret.stringData
→ 일반 문자열 형태로 입력 가능
```

`stringData`를 사용한다고 해서 Secret이 자동으로 Encryption되는 것은 아니다.

---

# 41. Secret Type

Secret에는 목적에 따라 여러 Type이 존재할 수 있다.

대표적으로 다음 정도를 알아두면 된다.

| Type | 용도 |
|---|---|
| `Opaque` | 일반적인 사용자 정의 Secret |
| `kubernetes.io/tls` | TLS Certificate / Private Key |
| `kubernetes.io/dockerconfigjson` | Container Registry 인증 정보 |

KCNA에서는 Secret Type 전체를 암기하기보다 **Secret이 Password 하나만 저장하는 Resource가 아니라 여러 종류의 Sensitive Credential을 관리하는 데 사용할 수 있다**는 정도로 이해하면 된다.

# 42. Secret을 안전하게 보호하려면?

Secret이라는 Resource를 사용했다고 해서 Sensitive Data가 자동으로 완전히 보호되는 것은 아니다.

Kubernetes Secret은 **기본 설정에서 etcd에 암호화되지 않은 형태로 저장될 수 있다.**

따라서 실제 Cluster에서는 다음과 같은 보호 방법을 고려해야 한다.

```text
Secret
│
├── Encryption at Rest
├── RBAC
├── Least Privilege
└── 필요 시 External Secret Management
```

## Encryption at Rest

API Server에 Encryption Configuration을 설정하면 Secret 같은 API Resource를 etcd에 저장할 때 암호화하도록 구성할 수 있다.

```text
Secret
   │
   ▼
kube-apiserver
   │
   │ Encryption at Rest
   ▼
etcd
```

Base64와 Encryption at Rest의 차이를 구분해야 한다.

```text
Base64
→ Encoding

Encryption at Rest
→ 저장된 Data의 Confidentiality 보호
```

## RBAC

Encryption at Rest를 적용하더라도 사용자가 Kubernetes API를 통해 Secret을 읽을 권한이 있다면 값을 조회할 수 있다.

따라서 RBAC과 Least Privilege를 통해 Secret 접근 권한을 필요한 사용자나 ServiceAccount로 제한해야 한다.

```text
User / ServiceAccount
        │
        │ RBAC
        ▼
      Secret
```

KCNA에서는 Encryption Configuration YAML까지 외울 필요는 없고 **Secret은 Base64만으로 안전해지는 것이 아니며 Encryption at Rest와 Access Control이 중요하다**는 점을 이해하면 된다.

# 43. ConfigMap과 Secret을 Container에 전달하는 방법

ConfigMap이나 Secret을 생성하는 것만으로 Application이 자동으로 값을 사용하는 것은 아니다.

Pod가 해당 ConfigMap이나 Secret을 참조하도록 설정해야 한다.

KCNA에서 알아둘 대표적인 방식은 **Environment Variable과 Volume Mount**이다.

```text
ConfigMap / Secret
        │
        ├── Environment Variable
        │
        └── Volume Mount
```

---

# 44. Environment Variable로 전달

ConfigMap이나 Secret의 값을 Container Environment Variable로 전달할 수 있다.

```text
ConfigMap
LOG_LEVEL=info
       │
       ▼
Container Environment
       │
       ▼
LOG_LEVEL=info
```

Secret도 같은 방식으로 전달할 수 있다.

```text
Secret
DB_PASSWORD=...
       │
       ▼
Container Environment
```

## 실행 중 값이 바뀌면?

Container가 이미 실행된 이후 원본 ConfigMap이나 Secret을 변경해도 **기존 Process의 Environment Variable은 자동으로 갱신되지 않는다.**

```text
ConfigMap
LOG_LEVEL=info
       ↓
Pod 시작
       ↓
Container ENV
LOG_LEVEL=info
```

이후 ConfigMap을 변경해도,

```text
ConfigMap
LOG_LEVEL=debug

Existing Container
LOG_LEVEL=info
```

기존 Process의 Environment Variable이 자동으로 `debug`로 바뀌지는 않는다.

일반적으로 변경된 Environment Variable을 적용하려면 새로운 Pod가 생성되어야 한다.

### KCNA 시험 포인트

```text
ConfigMap / Secret → Environment Variable

Source 변경
→ 기존 Container Process의 ENV 자동 갱신 X
```

---

# 45. Volume Mount로 전달

ConfigMap이나 Secret을 **File 형태로 Container Filesystem에 Mount**할 수도 있다.

```text
ConfigMap / Secret
        │
        ▼
      Volume
        │
        ▼
Container Filesystem
```

Application이 `/etc/app/config.yaml` 같은 Configuration File을 읽는 방식이라면 Volume Mount가 자연스러울 수 있다.

Secret의 Certificate나 Key도 File 형태로 제공할 수 있다.

## Volume의 Update

ConfigMap이나 Secret을 Volume으로 Mount한 경우 kubelet의 동기화 과정을 통해 변경된 데이터가 File에 반영될 수 있다.

다만 **즉시 변경된다고 보장할 수는 없다.**

또 하나 알아둘 점은 `subPath`를 이용해 ConfigMap이나 Secret을 Mount한 Container에서는 Source 변경사항이 자동으로 반영되지 않는다는 것이다.

그리고 Mount된 File이 변경되더라도 Application이 해당 File을 자동으로 Reload하지 않는다면 Application 동작에는 바로 반영되지 않을 수 있다.

```text
ConfigMap 변경
      ↓
Mounted File 변경
      ↓
Application이 File을 다시 읽는가?
```

따라서 다음 두 문장은 다르다.

```text
Mounted File이 업데이트될 수 있다.   ✅

Application 설정이 즉시 Reload된다.  항상 그런 것은 아님
```

---

# 46. Environment Variable vs Volume Mount

| 구분 | Environment Variable | Volume Mount |
|---|---|---|
| 전달 형태 | Key-Value Env | File |
| 일반적인 사용 | 간단한 설정값 | Config File, Certificate 등 |
| ConfigMap 사용 | 가능 | 가능 |
| Secret 사용 | 가능 | 가능 |
| Source 변경 시 기존 Process에 자동 적용 | X | File에는 반영될 수 있음 |
| Application Reload | 새 Pod 필요 가능 | Application 구현에 따라 다름 |

어떤 방식이 무조건 더 좋은 것은 아니다. Application이 Configuration을 어떻게 읽는지에 따라 적절한 방식을 선택한다.

---

# 47. ConfigMap vs Secret 최종 비교

| 구분 | ConfigMap | Secret |
|---|---|---|
| 목적 | Non-confidential Configuration | Sensitive Data |
| 예 | URL, Mode, Log Level, Flag | Password, Token, Key, Credential |
| API Group | Core | Core |
| apiVersion | `v1` | `v1` |
| Environment Variable | 가능 | 가능 |
| Volume Mount | 가능 | 가능 |
| Base64 | 일반적인 ConfigMap `data`는 문자열 | Secret `data`에서 Base64 사용 |
| 기본 Encryption 보장 | 해당 없음 | 보장되지 않음 |
| 추가 보안 | 일반 설정에 맞게 접근 통제 | Encryption at Rest, RBAC 등 중요 |

핵심은 다음과 같다.

```text
ConfigMap
→ Non-confidential Configuration

Secret
→ Sensitive Data

Secret data
→ Base64 Encoding

Base64
→ Encryption이 아님
```

# 정리하면서

이번 파트는 Kubernetes API, Container Image, Scheduling, ConfigMap과 Secret처럼 서로 다른 주제를 한꺼번에 다루는 것처럼 보이지만 실제로는 **사용자가 원하는 Application 상태를 Kubernetes에 선언한 뒤 실제 Container가 Worker Node에서 실행되기까지의 하나의 과정**으로 연결된다.

사용자는 Manifest의 `spec`을 통해 Desired State를 선언하고 `kubectl`은 이를 Kubernetes API에 전달한다. `kube-apiserver`가 요청을 처리하면 Kubernetes Controller가 Current State와 Desired State를 지속적으로 비교하고 Reconciliation을 수행한다.

새 Pod가 생성되면 kube-scheduler가 Resource Request뿐 아니라 Node Selector, Affinity, Taint/Toleration과 같은 Scheduling Constraint를 함께 확인한다. Scheduler는 먼저 Filtering으로 실행할 수 없는 Node를 제외하고, Scoring으로 남은 Feasible Node를 평가한 뒤 Binding을 통해 Pod를 최종 Node에 할당한다.

Scheduling 관련 개념에서는 특히 방향을 구분하는 것이 중요했다. `nodeSelector`와 Node Affinity는 Pod가 **어떤 특성의 Node에 배치되고 싶은지**를 표현하고, Taint는 Node가 **어떤 Pod를 받아들이지 않을지**를 표현한다. Toleration은 해당 Taint를 허용하게 해줄 뿐 특정 Node에 대한 Scheduling을 보장하지 않는다.

GPU Node 예제를 보면 이 차이가 더 명확하다. Node Affinity는 `GPU Node에서 실행하고 싶다`는 조건을 표현하는 반면 Taint는 `GPU Node에는 아무 Pod나 들어오지 못하게 하겠다`는 제한을 만든다. GPU Pod의 Toleration은 그 제한을 통과할 수 있게 한다.

Node가 결정된 뒤에는 해당 Worker Node의 kubelet이 CRI를 통해 Container Runtime과 통신하고, Runtime이 Registry에서 Image를 가져와 실제 Container를 실행한다. 이 과정에서도 Image와 Container, Registry와 Runtime, Tag와 Digest, CRI와 Container Runtime의 역할을 각각 구분할 필요가 있다.

Application Configuration은 Container Image와 분리하여 ConfigMap과 Secret으로 관리할 수 있다. ConfigMap은 일반 Configuration을, Secret은 Password나 Token과 같은 Sensitive Data를 저장한다.

특히 Secret에서 가장 중요한 것은 다음 관계였다.

```text
Secret
→ Sensitive Data를 위한 Resource

Base64
→ Encoding

Encryption at Rest
→ 저장된 Data를 보호하기 위한 Encryption

RBAC
→ Secret에 접근할 수 있는 주체 제한
```

즉 **Secret의 Base64 Encoding 자체는 Encryption이 아니다.** Secret이 기본적으로 etcd에서 암호화되어 있다고 가정해서도 안 되며 필요하면 Encryption at Rest를 별도로 구성해야 한다.

ConfigMap과 Secret을 Container에 전달하는 방법도 Environment Variable과 Volume Mount의 차이를 구분해야 한다. Environment Variable은 Source ConfigMap/Secret을 수정해도 이미 실행 중인 Process에 자동으로 반영되지 않지만, Volume Mount 방식은 kubelet의 동기화 과정을 통해 File에 변경사항이 반영될 수 있다. 다만 File이 변경되었다고 Application이 자동으로 Configuration을 Reload한다는 뜻은 아니다.

CKA에서는 `kubectl apply`, `nodeSelector`, `taint`, `toleration`, `resources.requests` 등을 실제로 사용하는 방법에 집중했다면, KCNA에서는 각각의 기술이 **Kubernetes 전체 동작 과정에서 어느 위치에 있고 어떤 문제를 해결하는지 정확하게 구분하는 것**이 더 중요하다고 느꼈다.

결국 이번 Kubernetes Fundamentals 파트에서 가장 중요하게 기억할 흐름은 다음과 같다.

```text
Kubernetes API
→ Desired State
→ Reconciliation
→ Pod 생성
→ Scheduling
→ kubelet
→ CRI
→ Container Runtime
→ Container
→ ConfigMap / Secret
```

각 용어를 따로 외우기보다 이 흐름 안에서 **누가 무엇을 결정하고, 누가 실제로 실행하며, 각 Resource와 Interface가 어떤 문제를 해결하는지** 연결해서 이해하는 것이 KCNA 문제를 풀 때 더 도움이 될 것 같다.
