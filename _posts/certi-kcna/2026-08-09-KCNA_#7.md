# KCNA #7 — Cloud Native Application Delivery: CI/CD, GitOps, 배포 전략, Helm/Kustomize와 Debugging

앞선 내용에서 Cloud Native 시스템을 어떻게 관측하고 문제를 이해하는지 살펴봤다면, 이번에는 **개발자가 작성한 변경 사항이 어떤 과정을 거쳐 실제 Kubernetes 환경에 안전하고 반복 가능하게 전달되는지**를 정리한다.

이 과정을 **Application Delivery**라고 한다.

기존 KCNA 자료에서는 Cloud Native Application Delivery가 **8%**였고 GitOps와 CI/CD가 주요 학습 항목으로 정리되어 있었다. 하지만 2025년 11월 24일 이후 적용된 현재 KCNA에서는 이 Domain의 비중이 **16%**로 커졌다.

현재 KCNA 전체 Domain 비중은 다음과 같다.

| Domain | 비중 |
| --- | ---: |
| Kubernetes Fundamentals | 44% |
| Container Orchestration | 28% |
| **Cloud Native Application Delivery** | **16%** |
| Cloud Native Architecture | 12% |

현재 Cloud Native Application Delivery의 공식 Competency는 다음 두 가지이다.

```text
Cloud Native Application Delivery 16%
├── Application Delivery
└── Debugging
```

즉 기존 자료처럼 GitOps와 CI/CD만 정리해서는 현재 시험 대비가 충분하지 않다. 기존 내용인 CI/CD, GitOps, Argo CD, Flux, Deployment Strategy, Helm, Kustomize, Supply Chain Security는 그대로 이해하되, 현재 시험에서는 **애플리케이션 배포 과정과 배포 실패를 진단하는 Debugging 흐름까지 함께 연결**해야 한다.

---

# 1. Application Delivery란 무엇인가

Application Delivery는 개발자가 작성한 Software Change를 사용자가 실제로 사용할 수 있는 실행 환경까지 전달하는 전체 과정을 의미한다.

일반적으로 다음과 같은 단계가 포함된다.

```text
Source Code
    ↓
Build
    ↓
Test
    ↓
Package / Artifact 생성
    ↓
Container Image Build
    ↓
Registry
    ↓
Deployment Configuration
    ↓
Kubernetes Deployment
    ↓
Verification
    ↓
Operation
```

Cloud Native 환경에서 Container Image는 매우 중요한 실행 Artifact이다. 다만 다음 표현은 지나치게 단정적이다.

```text
Cloud Native Application Delivery의 배달 단위는 항상 Container Image이다.  X
```

실제 Delivery에는 Container Image뿐 아니라 Kubernetes Manifest, Helm Chart, Kustomize Configuration, GitOps Repository, Policy, Configuration, Secret Reference, SBOM, Signature 같은 요소도 함께 관여한다.

따라서 정확하게는 **Container Image가 핵심 실행 Artifact이고, Application Delivery는 Image와 함께 배포 선언·설정·검증까지 포함하는 더 넓은 과정**이라고 이해한다.

---

# 2. Immutable Artifact

Cloud Native Delivery에서 중요한 원칙 중 하나가 **Immutable Artifact**이다.

한 번 만들어 검증한 Artifact를 Production으로 보낼 때 다시 Build해서 다른 결과물을 만드는 것보다 동일한 Artifact를 여러 환경으로 Promotion하는 방식이 재현성을 높인다.

```text
Source Code
    ↓
Build Once
    ↓
Image: app@sha256:abc123
    ↓
Development
    ↓
Staging
    ↓
Production
```

이를 통해 `개발 환경에서는 됐는데 운영에서는 다르다` 같은 환경 차이를 줄일 수 있다.

---

# 3. CI/CD

CI/CD는 Application Delivery를 자동화하는 대표적인 Practice이다.

```text
CI = Continuous Integration
CD = Continuous Delivery / Continuous Deployment
```

KCNA에서는 세 개념을 정확히 구분해야 한다.

---

# 4. CI — Continuous Integration

Continuous Integration은 여러 개발자가 만든 Code Change를 자주 통합하고 자동으로 검증하는 Practice이다.

```text
Code Commit
    ↓
Build
    ↓
Unit Test
    ↓
Integration Test
    ↓
Lint / Static Analysis
    ↓
Security Scan
    ↓
Artifact / Image Build
```

핵심 목적은 **변경 사항을 빠르게 통합하고 문제를 가능한 이른 시점에 발견하는 것**이다.

기존 자료에서 `CI의 산출물은 테스트를 통과한 Container Image`라고 설명했는데, Cloud Native Application에서는 대표적인 예이지만 절대적인 정의는 아니다. CI는 Binary, Package, Container Image, Helm Chart, SBOM, Test Report 같은 다양한 Artifact를 만들 수 있다.

---

# 5. Continuous Delivery와 Continuous Deployment

## Continuous Delivery

Production에 배포할 수 있는 상태까지 자동화하되 최종 Production 반영에 사람의 승인이나 Trigger가 남아 있을 수 있다.

```text
Commit
  ↓
Build
  ↓
Test
  ↓
Staging
  ↓
Ready for Production
  ↓
Manual Approval
  ↓
Production
```

## Continuous Deployment

검증을 통과한 Change를 사람의 별도 승인 없이 Production까지 자동 배포한다.

```text
Commit
  ↓
Build
  ↓
Test
  ↓
Validation
  ↓
Production
```

시험에서는 다음처럼 구분한다.

```text
Continuous Delivery
→ Production 직전까지 자동화
→ 최종 승인 가능

Continuous Deployment
→ Production 반영까지 자동
```

---

# 6. CI와 CD의 경계

기존 자료의 `이미지를 만드는 일까지 CI, Cluster에 띄우는 일부터 CD`라는 구분은 입문용으로는 유용하지만 너무 절대적으로 외우면 안 된다.

더 정확한 구분은 다음과 같다.

```text
CI
→ Code Change Integration + Automated Validation

CD
→ 검증된 Software Change의 Delivery / Deployment
```

Pipeline 설계에 따라 Image Build 위치나 Test Environment 배포 위치는 달라질 수 있다.

---

# 7. CI/CD Pipeline

CI와 CD의 여러 단계를 자동으로 연결한 흐름을 Pipeline이라고 한다.

```text
Developer
   ↓
Git Push
   ↓
CI Pipeline
├── Build
├── Test
├── Scan
└── Image Push
   ↓
Registry
   ↓
CD / GitOps
   ↓
Kubernetes
   ↓
Verification
```

대표적인 도구로 Jenkins, GitHub Actions, GitLab CI/CD, Tekton 등이 있다. KCNA에서는 각 도구의 설정 문법보다 **Build/Test/Package/Deploy를 자동화하는 Pipeline 개념**을 이해하면 된다.

---

# 8. Tekton

Tekton은 Cloud Native 환경에서 CI/CD Pipeline을 구성하기 위한 Framework이다.

현재 Tekton은 **CNCF Incubating 프로젝트**이다.

```text
Task
→ 하나 이상의 작업 단계

Pipeline
→ 여러 Task의 실행 흐름
```

KCNA에서는 다음 연결이면 충분하다.

```text
Tekton
→ Kubernetes / Cloud Native CI/CD Framework
```

---

# 9. GitOps

GitOps는 단순히 `Git을 사용한다`는 의미가 아니다.

GitOps의 핵심은 **시스템의 Desired State를 선언적으로 관리하고, Versioned/Immutable한 Source에 저장하며, Software Agent가 이를 자동으로 가져와 Actual State와 지속적으로 Reconcile하는 것**이다.

```text
Developer
   ↓
Git Commit / Pull Request
   ↓
Versioned Desired State
   ↓
GitOps Controller
   ↓
Cluster State 확인
   ↓
Reconciliation
   ↓
Kubernetes
```

---

# 10. Git과 Source of Truth

GitOps 설명에서 Git Repository를 **Single Source of Truth**라고 표현하는 경우가 많다. 실무적으로도 이해하기 좋은 표현이다.

다만 OpenGitOps의 공식 원칙은 특정 Git 제품 자체보다 다음 특성을 중요하게 본다.

```text
Versioned
Immutable
Complete History
```

따라서 다음처럼 이해한다.

> 일반적인 GitOps에서는 Git Repository가 Desired State의 Source of Truth 역할을 한다. 하지만 GitOps의 본질은 특정 Git 제품 자체보다 Declarative, Versioned/Immutable, Pull, Reconciliation 원칙에 있다.

---

# 11. OpenGitOps 4대 원칙

OpenGitOps가 정의한 핵심 원칙은 다음 네 가지이다.

```text
Declarative
Versioned and Immutable
Pulled Automatically
Continuously Reconciled
```

## Declarative

Desired State를 명령 절차가 아니라 선언형으로 표현한다.

```yaml
replicas: 3
image: example/app:v2
```

## Versioned and Immutable

Desired State의 Version History와 변경 이력을 보존한다.

```text
Commit A → Commit B → Commit C
```

누가, 언제, 무엇을 변경했는지 추적할 수 있다.

## Pulled Automatically

Software Agent가 Desired State Source를 자동으로 관찰하고 가져온다.

```text
Repository
    ↑ Pull
GitOps Controller
    ↓
Kubernetes
```

## Continuously Reconciled

Desired State와 Actual State를 지속적으로 비교하여 차이가 있으면 원하는 상태로 수렴시킨다.

```text
Desired = 3
Actual  = 2
   ↓
Reconcile
   ↓
Actual  = 3
```

---

# 12. Push 기반 CD와 Pull 기반 GitOps

전통적인 Push 방식에서는 외부 Pipeline이 Kubernetes API에 변경을 밀어 넣을 수 있다.

```text
CI/CD Pipeline
      ↓
kubectl apply
      ↓
Kubernetes API
```

Pull 기반 GitOps에서는 일반적으로 Cluster 쪽 Controller가 Repository를 관찰한다.

```text
Repository
    ↑ Pull
GitOps Controller
    ↓
Kubernetes API
```

기존 자료의 `자격 증명이 Cluster 밖으로 나가지 않는다`는 표현은 너무 단정적이다. GitOps를 사용해도 Repository Credential, Registry Credential, CI Credential 등은 존재할 수 있다.

정확한 장점은 **외부 CI Pipeline이 직접 Kubernetes Deployment Credential을 보유해야 하는 필요를 줄이고, Deployment 권한을 Cluster 내부 Controller 중심으로 제한할 수 있다는 것**이다.

---

# 13. Drift와 Reconciliation

GitOps에서 Drift는 Desired State와 Actual State가 서로 달라진 상태이다.

```text
Git Desired State = replicas 3
Cluster Actual    = replicas 5
```

이 차이를 Drift라고 한다.

Controller가 이를 감지하고 다시 3으로 맞추면 Reconciliation이다.

```text
Desired = 3
Actual  = 5
   ↓ Drift Detection
Reconcile
   ↓
Actual  = 3
```

---

# 14. GitOps의 장점

| 장점 | 설명 |
| --- | --- |
| Auditability | 변경 이력이 Version Control에 남음 |
| Reproducibility | 같은 Desired State로 환경을 다시 구성 가능 |
| Consistency | 선언된 상태를 일관되게 관리 |
| Drift Detection | Desired와 Actual State 차이 감지 |
| Reconciliation | Actual State를 Desired State로 지속 수렴 |
| Rollback 용이성 | 이전 선언 상태로 되돌리기 쉬움 |
| Separation of Concerns | CI와 Deployment 권한을 분리하기 쉬움 |

단, `Git revert = 모든 것이 완전히 원상복구`는 아니다. Database Schema, Persistent Data, External System의 상태는 별도 Rollback이 필요할 수 있다.

---

# 15. Argo CD

Argo CD는 Kubernetes용 대표 GitOps Continuous Delivery 도구이다. Argo 프로젝트는 현재 **CNCF Graduated**이다.

```text
Git Desired State
       ↓
Argo CD
       ↓
Compare / Diff
       ↓
Sync
       ↓
Kubernetes
```

대표적으로 Application Sync Status, Health Status, Resource Tree, Desired/Live Diff, Sync History 등을 확인할 수 있다.

```text
Argo CD
→ Kubernetes GitOps Continuous Delivery
→ Desired State와 Live State 비교 / Sync
```

---

# 16. Flux

Flux 역시 Kubernetes 환경에서 GitOps를 구현하는 대표적인 Continuous Delivery Solution이며 현재 **CNCF Graduated** 프로젝트이다.

Argo CD와 구현 방식은 다르지만 시험에서는 공통 원리를 이해하면 된다.

```text
Versioned Desired State
       ↓
Controller
       ↓
Kubernetes Actual State
       ↓
Continuous Reconciliation
```

# 17. Deployment Strategy

새 Version을 기존 Version과 어떤 방식으로 교체할지를 Deployment Strategy라고 한다.

KCNA에서는 다음 전략을 구분할 수 있어야 한다.

```text
Recreate
Rolling Update
Blue-Green
Canary
```

---

# 18. Recreate

기존 Version을 모두 종료한 뒤 새로운 Version을 실행한다.

```text
v1 v1 v1
   ↓
Stop All
   ↓
-
   ↓
v2 v2 v2
```

가장 단순하지만 기존 Pod 종료와 새 Pod 준비 사이에 Downtime이 발생할 수 있다.

---

# 19. Rolling Update

기존 Pod를 한 번에 모두 종료하지 않고 새 Version Pod로 점진적으로 교체한다.

```text
v1 v1 v1
   ↓
v1 v1 v2
   ↓
v1 v2 v2
   ↓
v2 v2 v2
```

Kubernetes Deployment의 기본 Strategy는 **RollingUpdate**이다.

주요 설정은 다음과 같다.

```text
maxSurge
maxUnavailable
```

- `maxSurge`: Desired Replica 수를 초과해 추가 생성할 수 있는 최대 수 또는 비율
- `maxUnavailable`: Update 중 사용할 수 없는 Pod의 최대 수 또는 비율

기본적으로 둘 다 25%이다.

---

# 20. Rolling Update와 Zero-Downtime

Rolling Update는 Zero-Downtime Deployment를 구현하는 대표 방식이지만, 실제 서비스 가용성은 다음 요소에도 영향을 받는다.

- Readiness Probe
- 충분한 Replica
- `maxUnavailable`
- Graceful Termination
- Startup Time
- Application Compatibility
- Database Migration

따라서 `Rolling Update = 무조건 Zero-Downtime`이라고 단정하지 않는다.

---

# 21. Blue-Green

기존 Environment와 새 Environment를 동시에 준비한 뒤 Traffic을 전환한다.

```text
Blue  = v1
Green = v2

Traffic → Blue
```

검증 후:

```text
Traffic → Green
```

빠른 전환과 복귀가 장점이지만 두 Environment를 동시에 유지하므로 Resource가 더 필요할 수 있다.

---

# 22. Canary

새 Version에 일부 Traffic만 먼저 보내 검증한 뒤 비율을 점진적으로 늘린다.

```text
v1 = 90%
v2 = 10%

↓ 검증

v1 = 50%
v2 = 50%

↓ 검증

v2 = 100%
```

핵심은 **새 Version의 위험을 전체 사용자에게 한 번에 노출하지 않는 것**이다.

---

# 23. Deployment Strategy 비교

| Strategy | 방식 | 장점 | 주의점 |
| --- | --- | --- | --- |
| Recreate | 기존 Version 종료 후 새 Version | 단순함 | Downtime 가능 |
| Rolling Update | Pod 점진 교체 | Deployment 기본 | 두 Version 일시 공존 |
| Blue-Green | 두 Environment + Traffic 전환 | 빠른 전환/복귀 | Resource 증가 |
| Canary | 일부 Traffic부터 새 Version 검증 | 위험 감소 | Traffic Control 필요 |

---

# 24. Helm

Helm은 Kubernetes의 대표적인 **Package Manager**이며 CNCF Graduated 프로젝트이다.

핵심 용어는 다음과 같다.

```text
Chart
Template
Values
Release
```

## Chart

Kubernetes Application 배포에 필요한 Resource와 Metadata를 묶은 Package이다.

```text
mychart/
├── Chart.yaml
├── values.yaml
└── templates/
    ├── deployment.yaml
    └── service.yaml
```

## Template

Values를 이용해 Kubernetes Manifest를 Rendering할 수 있는 Template이다.

```yaml
replicas: {{ .Values.replicaCount }}
```

## Values

Template에 주입되는 설정값이다.

```yaml
replicaCount: 3
image:
  repository: example/app
  tag: v2
```

## Release

Chart를 Cluster에 설치한 하나의 Instance이다.

```text
Chart → Release: app-dev
Chart → Release: app-prod
```

시험용으로는 다음처럼 기억한다.

```text
Chart = Package
Template = Manifest Template
Values = 설정값
Release = 설치된 Chart Instance
```

---

# 25. Kustomize

Kustomize는 기존 Kubernetes Resource를 기반으로 설정을 추가·변경·조합하는 Configuration Management 도구이다.

`kubectl`에 통합되어 다음과 같이 사용할 수 있다.

```bash
kubectl apply -k ./overlays/prod
```

핵심 패턴은 Base와 Overlay이다.

## Base

공통 Kubernetes Resource를 정의한다.

```text
base/
├── deployment.yaml
├── service.yaml
└── kustomization.yaml
```

## Overlay

Base를 재사용하면서 Environment별 차이를 적용한다.

```text
overlays/
├── dev/
└── prod/
```

Replica, Image, Resource, Label, Namespace 같은 차이를 적용할 수 있다.

---

# 26. Kustomize는 단순 YAML 병합만 하는 도구가 아니다

기존 자료의 `순수 YAML 병합`이라는 표현은 지나치게 단순하다.

Kustomize는 다음과 같은 Transformation을 수행할 수 있다.

- Patch 적용
- Image 변경
- Name Prefix / Suffix
- Label / Annotation 추가
- Namespace 설정
- ConfigMap / Secret Generator
- Resource Composition

따라서 다음처럼 이해한다.

> **Kustomize는 Template Variable 치환 없이 Kubernetes Resource를 Base/Overlay, Patch, Transformation으로 Customization하는 도구이다.**

---

# 27. Helm vs Kustomize

| 구분 | Helm | Kustomize |
| --- | --- | --- |
| 핵심 목적 | Package Management | Configuration Customization |
| 핵심 개념 | Chart / Template / Values / Release | Base / Overlay / Patch |
| Template | 사용 | 전통적인 Variable Template 방식 사용 안 함 |
| Release 관리 | 지원 | 자체 Release 개념 없음 |
| 실행 | Helm CLI | kubectl `-k` 통합 |

한 줄로 구분하면 다음과 같다.

```text
Helm
→ Package Manager
→ Chart + Template + Values + Release

Kustomize
→ Manifest Customization
→ Base + Overlay + Patch
```

---

# 28. ConfigMap과 Secret

Application Delivery에서는 Build Artifact와 Runtime Configuration을 분리하는 것이 중요하다.

```text
ConfigMap
→ 일반 Configuration

Secret
→ Password / Token / Key 같은 민감 정보
```

일반적인 구조는 다음과 같다.

```text
Immutable Image
       +
Environment Configuration
       +
Secret
       ↓
Deployment
```

Environment별 설정을 Image에 직접 Bake하는 방식보다 동일한 Image를 재사용하기 쉽다.

# 29. Supply Chain Security

Application Delivery Pipeline이 자동화될수록 **어떤 Artifact를 신뢰할 수 있는가**가 중요하다.

```text
Source
  ↓
Build
  ↓
Dependency
  ↓
Artifact
  ↓
Registry
  ↓
Deployment
```

기본적으로 다음 개념을 알아두면 좋다.

- Trusted Source
- Artifact Integrity
- Image Signature
- Vulnerability Scanning
- SBOM
- Provenance / Attestation

현재 공식 KCNA Application Delivery Competency에는 Supply Chain Security가 별도 세부 항목으로 명시되어 있지 않으므로 Application Delivery와 Debugging보다 우선순위는 낮다.

# 30. Cosign

Cosign은 Sigstore 프로젝트에서 Software Artifact를 **Sign하고 Signature를 Verify**하는 CLI이다.

```text
Artifact
  ↓ Sign
Signature

Consumer
  ↓ Verify
Trusted Artifact 확인
```

Image Signing은 다음을 확인하는 데 도움이 된다.

```text
Authenticity
→ 누가 만든 Artifact인가?

Integrity
→ Artifact가 변경되지 않았는가?
```

---

# 31. SBOM

SBOM은 **Software Bill of Materials**의 약자이다.

Software Artifact에 어떤 Component와 Dependency가 포함되어 있는지 목록화한다.

```text
Application
├── Library A v1.2
├── Library B v3.0
├── OpenSSL ...
└── Other Dependencies
```

새 취약점이 발견되었을 때 어떤 Artifact가 영향을 받는지 확인하는 데 도움이 된다.

```text
Dependency 목록 → SBOM
Artifact Sign / Verify → Cosign
```

# 33. Application Debugging 기본 흐름

애플리케이션이 정상 배포되지 않을 때 다음 순서로 접근하면 좋다.

```text
1. Resource 상태 확인
        ↓
2. Pod 상태 확인
        ↓
3. describe / Event 확인
        ↓
4. Container Log 확인
        ↓
5. Deployment Rollout 확인
        ↓
6. Service / Endpoint / Probe 확인
```

KCNA는 CKA처럼 실제 Troubleshooting 작업을 깊게 수행하는 시험은 아니지만 **어떤 정보로 어떤 문제를 확인하는지**는 알아야 한다.

# 34. kubectl get

가장 먼저 Resource의 현재 상태를 확인한다.

```bash
kubectl get deployment
kubectl get pods
kubectl get service
kubectl get pods -o wide
```

대표적으로 READY, STATUS, RESTARTS, NODE 등을 확인한다.

---

# 35. kubectl describe

Resource의 상세 상태와 Event를 확인할 때 유용하다.

```bash
kubectl describe pod <pod-name>
```

다음과 같은 문제 확인에 도움이 된다.

- Scheduling 실패
- Image Pull 실패
- Probe 실패
- Volume Mount 문제
- Container State
- Kubernetes Event

대표 Event 예시는 다음과 같다.

```text
FailedScheduling
FailedMount
FailedPull
BackOff
Unhealthy
```

# 36. kubectl logs

Application 자체 Error는 Container Log에서 확인한다.

```bash
kubectl logs <pod-name>
```

여러 Container가 있다면:

```bash
kubectl logs <pod-name> -c <container-name>
```

이전 Container Instance의 Log가 필요하면:

```bash
kubectl logs <pod-name> --previous
```

구분은 다음과 같다.

```text
describe
→ Kubernetes 관점의 상태 / Event

logs
→ Application / Container Output
```

# 37. Event

Pod가 Pending인 경우 `Pending` 자체는 원인이 아니라 증상이다.

```bash
kubectl get events
```

또는 `kubectl describe pod`의 Events를 통해 다음 원인을 찾을 수 있다.

- Insufficient CPU / Memory
- NodeSelector mismatch
- Untolerated taint
- PVC binding issue
- Failed Scheduling

# 38. Rollout 상태 확인

새 Version Deployment 진행 상태는 다음과 같이 확인할 수 있다.

```bash
kubectl rollout status deployment/<name>
```

Revision History:

```bash
kubectl rollout history deployment/<name>
```

Rollback:

```bash
kubectl rollout undo deployment/<name>
```

시험에서는 다음 역할 정도를 구분하면 된다.

```text
rollout status
→ 배포 진행 상태

rollout history
→ Revision 이력

rollout undo
→ 이전 Revision으로 Rollback
```

# 39. 자주 보는 Pod 상태

## Pending

Pod가 아직 실행 Node에 Scheduling되지 않았거나 필요한 조건이 준비되지 않은 상태일 수 있다.

대표 원인:

- CPU / Memory 부족
- PVC 문제
- Node Affinity
- Taint / Toleration
- Scheduling Constraint

확인:

```text
kubectl describe pod
Events
```

## ImagePullBackOff / ErrImagePull

Container Image를 가져오지 못하는 상태이다.

대표 원인:

- 잘못된 Image Name
- 존재하지 않는 Tag
- Registry 접근 실패
- ImagePullSecret 문제
- Authentication 실패

## CrashLoopBackOff

Container가 시작된 뒤 반복해서 종료되고 Restart가 반복될 때 나타날 수 있다.

대표 원인:

- Application Startup Error
- 잘못된 Configuration
- Missing Secret
- Dependency 연결 실패
- Liveness Probe 실패

확인:

```text
kubectl logs
kubectl logs --previous
kubectl describe pod
```

---

# 40. Readiness, Liveness, Startup Probe

## Readiness Probe

Container가 **Traffic을 받을 준비가 되었는지** 판단한다.

Readiness가 실패하면 Pod가 Running이어도 Service Endpoint에서 제외될 수 있다.

## Liveness Probe

Container가 **정상적으로 살아 있는지** 확인한다. 반복적으로 실패하면 kubelet이 Container를 Restart할 수 있다.

## Startup Probe

시작 시간이 긴 Application의 Startup 완료 여부를 확인한다. Startup Probe가 성공하기 전까지 Liveness/Readiness 평가를 지연시키는 데 사용할 수 있다.

시험용으로 다음처럼 구분한다.

```text
Readiness
→ Traffic 받을 준비?

Liveness
→ 정상적으로 살아 있는가?

Startup
→ Startup 완료?
```

---

# 41. Running과 Ready는 다르다

배포 문제에서는 Pod가 단순히 Running인지 보는 것만으로 부족하다.

```text
STATUS = Running
READY  = 0/1
```

이라면 Process는 실행 중이지만 Traffic을 받을 준비가 되지 않았을 수 있다.

Rolling Update에서 Readiness가 제대로 동작해야 새 Pod가 준비되기 전 Traffic이 전달되는 문제를 줄일 수 있다.

# 42. Service Selector와 Pod Label

Pod는 정상인데 Service를 통해 접근되지 않는다면 Selector와 Label을 확인한다.

```yaml
Service selector:
  app: web

Pod label:
  app: api
```

이처럼 값이 다르면 Service가 해당 Pod를 선택하지 못한다.

```text
Service
→ Selector로 Pod 선택

Pod Label
→ Selector와 일치해야 함
```

# 43. CI/CD와 GitOps의 관계

GitOps와 CI/CD는 경쟁 관계가 아니다.

```text
Developer
   ↓
Git Push
   ↓
CI
├── Build
├── Test
├── Scan
└── Image Push
   ↓
Registry
   ↓
Deployment Repo Update
   ↓
GitOps Controller
   ↓
Kubernetes
```

역할을 나누면 다음과 같다.

```text
CI
→ Artifact 생성 / 검증

GitOps
→ Desired State 기반 Continuous Delivery
```

GitOps가 CI를 대체한다고 생각하면 안 된다.

# 44. Image Tag와 Digest

```text
example/app:v1
```

`v1`은 Tag이다.

```text
example/app@sha256:abcdef...
```

은 Content Digest이다.

```text
Tag
→ 사람이 읽기 쉬운 Reference
→ 같은 Tag가 다른 Content를 가리키도록 변경될 수 있음

Digest
→ Content-addressable Identifier
→ 정확한 Image Content 식별
```

Immutable Delivery와 재현성 관점에서 Digest를 알아두면 좋다.

## 수정 2 — 배달 단위는 항상 Container Image

정확하게는 Container Image가 핵심 실행 Artifact이고, Application Delivery에는 Manifest, Configuration, Chart, Policy, Signature 등도 포함될 수 있다.

## 수정 3 — CI와 CD 경계

```text

→ Integration + Automated Validation

```

`Image Build까지 무조건 CI`라고 절대적으로 외우지 않는다.

## 수정 4 — GitOps = Git 사용

```text

```

```text

```

## 수정 5 — GitOps에서는 Credential이 Cluster 밖에 없다

지나친 단정이다. 더 정확한 표현은 **Pull 기반 GitOps가 외부 CI의 직접적인 Kubernetes Deployment Credential 보유 필요를 줄일 수 있다**는 것이다.

## 수정 6 — Git revert면 모든 State가 완벽히 Rollback

Manifest는 쉽게 되돌릴 수 있지만 Database Schema, Persistent Data, External State는 별도 Rollback이 필요할 수 있다.

## 수정 7 — Kustomize = 순수 YAML 병합

더 정확하게는 Template Variable 없이 Kubernetes Resource를 Patch/Transform/Compose하는 Customization 도구이다.

## 수정 8 — Tekton 상태

현재 Tekton은 **CNCF Incubating** 프로젝트이다.

## 수정 9 — Argo / Flux 상태

현재 Argo와 Flux는 모두 **CNCF Graduated** 프로젝트이다.

## 수정 10 — Supply Chain Security 우선순위

Cosign/SBOM은 유용하지만 현재 공식 Competency에는 별도 항목으로 명시되어 있지 않다. Application Delivery와 Debugging을 먼저 학습한다.

# 50. 정리

Cloud Native Application Delivery의 핵심은 Code를 단순히 Cluster에 복사하는 것이 아니다.

변경 사항을 Build하고 Test하고, 신뢰할 수 있는 Artifact를 만들고, Versioned Configuration으로 Desired State를 정의하며, 자동화된 Pipeline과 Controller를 통해 반복 가능하게 전달하고, 문제가 발생하면 빠르게 원인을 진단할 수 있어야 한다.

전체 흐름을 연결하면 다음과 같다.

```text
Developer
   ↓
Git Commit
   ↓
CI
├── Build
├── Test
├── Scan
└── Artifact / Image
   ↓
Registry
   ↓
Deployment Configuration
   ↓
GitOps / CD
   ↓
Kubernetes Deployment
   ↓
Rolling / Canary / Blue-Green
   ↓
Verification
   ↓
Debugging / Observability
```

CI/CD에서는 다음을 구분한다.

```text
CI
→ Integration + Validation

Continuous Delivery
→ 운영 배포 가능 상태까지 자동화

Continuous Deployment
→ 운영 반영까지 자동화
```

GitOps에서는 다음 네 원칙을 기억한다.

```text
Declarative
Versioned and Immutable
Pulled Automatically
Continuously Reconciled
```

배포 전략에서는 다음을 구분한다.

```text
Recreate
RollingUpdate
Blue-Green
Canary
```

Manifest 관리에서는 다음을 구분한다.

```text
Helm
→ Package Manager
→ Chart / Template / Values / Release

Kustomize
→ Manifest Customization
→ Base / Overlay / Patch
```

현재 KCNA에서 특히 보강해야 하는 부분은 **Debugging**이다.

```text
Resource 상태
   ↓
Pod 상태
   ↓
describe / Event
   ↓
logs
   ↓
rollout
   ↓
Service / Probe
```

시험에서 Application Delivery 문제를 만났을 때는 단순히 도구 이름을 외우기보다 다음 질문을 순서대로 생각하면 된다.

```text
Build / Integration 문제인가?

Artifact 문제인가?

Deployment Strategy 문제인가?

Desired와 Actual State가 다른가?

Pod가 생성되지 않는가?

Container가 시작 후 죽는가?

Image를 가져오지 못하는가?

Pod는 Running이지만 Ready하지 않은가?

Service가 올바른 Pod를 선택하는가?
```

이 흐름을 이해하면 CI/CD, GitOps, Deployment Strategy, Helm/Kustomize, Debugging 문제를 각각 분리해서 판단할 수 있다.
