# KCNA #2 - Kubernetes Fundamentals 1: 아키텍처와 핵심 리소스

KCNA의 첫 번째이자 가장 비중이 높은 영역인 **Kubernetes Fundamentals**를 공부하면서 Kubernetes Cluster Architecture와 핵심 Resource를 다시 정리했다.

CKA를 공부하면서 대부분 직접 다뤄봤던 내용이지만, KCNA는 실제 명령어를 실행하는 시험이 아니라 객관식 시험이기 때문에 조금 다른 관점으로 볼 필요가 있었다.

단순히 `kube-scheduler는 스케줄링`, `kubelet은 Node Agent`처럼 외우는 것보다,

> **사용자가 Kubernetes에 Deployment를 생성하면 어떤 Component들이 어떤 순서로 동작하는가?**

라는 전체 흐름 안에서 각각의 역할을 연결해서 이해하는 것이 중요하다.

---

# 1. Kubernetes Cluster의 전체 구조

Kubernetes Cluster는 크게 **Control Plane**과 **Worker Node**로 구성된다.

```text
Kubernetes Cluster
│
├── Control Plane
│   ├── kube-apiserver
│   ├── etcd
│   ├── kube-scheduler
│   └── kube-controller-manager
│
└── Worker Node
    ├── kubelet
    ├── Container Runtime
    └── kube-proxy
```

Control Plane은 Cluster 전체를 관리하고 의사결정을 담당하고, Worker Node에서는 실제 Application Workload가 실행된다.

쉽게 정리하면 다음과 같다.

```text
Control Plane
→ 무엇을, 어디에서, 어떤 상태로 유지할지 관리

Worker Node
→ 결정된 내용을 바탕으로 실제 Pod와 Container 실행
```

다만 이 표현만 외우기보다는 실제 Pod가 만들어지는 과정을 같이 이해하는 것이 좋다.

---

# 2. Pod 하나가 실행되기까지

예를 들어 다음과 같이 Deployment를 생성한다고 생각해보자.

```bash
kubectl apply -f deployment.yaml
```

아주 단순화하면 다음과 같은 과정이 발생한다.

```text
사용자
  │
  │ kubectl apply
  ▼
kube-apiserver
  │
  ├── 요청 인증 / 인가
  ├── Admission 과정
  │
  ▼
etcd
  │
  │ Desired State 저장
  ▼
Controller
  │
  │ 필요한 Pod 생성
  ▼
kube-scheduler
  │
  │ Pod가 실행될 Node 선택
  ▼
kube-apiserver
  │
  ▼
선택된 Node의 kubelet
  │
  │ CRI
  ▼
Container Runtime
  │
  ▼
Container 실행
```

여기서 중요한 점은 하나의 Component가 모든 작업을 처리하지 않는다는 것이다.

각 Component는 자신의 역할을 담당하고 Kubernetes API를 중심으로 협력한다.

이 흐름을 이해하면 KCNA에서 Component의 역할을 묻는 문제가 훨씬 쉬워진다.

---

# 3. Control Plane

Control Plane은 Kubernetes Cluster의 상태와 동작을 관리한다.

대표적인 Component는 다음과 같다.

| Component | 핵심 역할 |
|---|---|
| `kube-apiserver` | Kubernetes API 제공 |
| `etcd` | Cluster State 저장 |
| `kube-scheduler` | Pod를 실행할 Node 선택 |
| `kube-controller-manager` | Desired State와 Current State 조정 |
| `cloud-controller-manager` | Cloud Provider 연동 |

각각의 역할을 조금 더 자세히 살펴본다.

---

# 4. kube-apiserver

`kube-apiserver`는 Kubernetes Control Plane의 **Frontend**이다.

사용자나 Kubernetes Component가 Cluster와 상호작용할 때 사용하는 Kubernetes API를 제공한다.

예를 들어,

```bash
kubectl get pods
```

를 실행했다고 해서 `kubectl`이 Worker Node에 직접 접속하여 Pod 목록을 가져오는 것이 아니다.

```text
kubectl
   │
   │ Kubernetes API
   ▼
kube-apiserver
   │
   ▼
Cluster State
```

Deployment를 생성하는 경우에도 마찬가지다.

```text
kubectl apply
      │
      ▼
kube-apiserver
      │
      ├── Authentication
      ├── Authorization
      ├── Admission Control
      │
      ▼
     etcd
```

즉 `kube-apiserver`는 Kubernetes의 거의 모든 제어 작업이 통과하는 중심점이다.

### Authentication / Authorization / Admission

세 개념도 구분할 필요가 있다.

```text
Authentication
→ "누구인가?"

Authorization
→ "이 사용자가 이 작업을 해도 되는가?"

Admission Control
→ "허용된 요청이라도 Cluster에 적용하기 전에
   추가 검증이나 변경이 필요한가?"
```

예를 들어 사용자가 Pod 생성을 요청했다면,

```text
사용자 확인
   ↓
Authentication

Pod 생성 권한 확인
   ↓
Authorization

정책에 맞는 요청인지 확인
   ↓
Admission

API Object 저장
```

과 같은 관점으로 이해할 수 있다.

### KCNA 시험 포인트

```text
Kubernetes API의 Frontend
→ kube-apiserver

API 요청 처리
→ kube-apiserver

Authentication / Authorization / Admission
→ API Request 처리 과정
```

---

# 5. etcd

`etcd`는 Kubernetes가 사용하는 **Distributed Key-Value Store**이다.

Kubernetes API Object의 상태 정보가 저장된다.

예를 들면,

```text
Deployment
Pod
Service
ConfigMap
Secret
Namespace
RBAC Object
...
```

등의 Cluster State가 저장된다.

따라서 etcd를 단순한 Application Database로 생각하면 안 된다.

```text
Kubernetes API Objects
        │
        ▼
       etcd
```

Kubernetes가 관리해야 할 Cluster State를 영속적으로 저장하는 **Control Plane의 핵심 데이터 저장소**이다.

etcd는 여러 Member로 구성할 수 있으며 **Raft Consensus Algorithm**을 사용하여 일관성을 유지한다.

### 왜 etcd Backup이 중요한가?

Application Data를 etcd에 저장하는 것은 아니지만 Kubernetes가 Cluster를 어떻게 구성하고 있었는지에 대한 상태가 저장되어 있다.

따라서 etcd 데이터를 잃으면 Cluster의 Control Plane State를 잃게 된다.

CKA에서 `etcdctl snapshot`을 이용해 etcd를 백업했던 이유도 이것 때문이다.

### KCNA 시험 포인트

```text
Distributed Key-Value Store
Cluster State
Raft

→ etcd
```

---

# 6. kube-scheduler

`kube-scheduler`는 아직 Node가 배정되지 않은 Pod를 확인하여 **어느 Node에서 실행할 것인지 결정**한다.

예를 들어 새로운 Pod가 생성되었다고 하자.

```text
Pod
Node = ?

   ↓

kube-scheduler

   ↓

Pod
Node = worker-02
```

Scheduler는 Node를 선택할 때 여러 조건을 고려한다.

대표적으로,

- CPU / Memory 등 Resource
- Node Selector
- Node Affinity
- Pod Affinity / Anti-Affinity
- Taint / Toleration
- 기타 Scheduling Constraint

등이 있다.

하지만 Scheduler가 직접 Container를 실행하는 것은 아니다.

```text
kube-scheduler
→ Node 선택

kubelet
→ 선택된 Node에서 Pod 실행 관리

Container Runtime
→ 실제 Container 실행
```

이 차이는 시험에서 특히 중요하다.

### 시험에서 틀리기 쉬운 표현

> kube-scheduler runs containers on worker nodes.

❌ 틀린 설명이다.

Scheduler는 **Node를 선택**한다.

실제 Container 실행은 해당 Node의 kubelet과 Container Runtime이 담당한다.

---

# 7. kube-controller-manager와 Reconciliation

`kube-controller-manager`는 여러 Kubernetes Controller를 실행하는 Control Plane Component이다.

Controller를 이해하려면 먼저 Kubernetes의 **Desired State**와 **Current State**를 이해해야 한다.

예를 들어 Deployment에 다음과 같이 선언했다고 하자.

```yaml
spec:
  replicas: 3
```

사용자가 원하는 상태는 다음과 같다.

```text
Desired State
Pod = 3
```

그런데 실제 상태가 다음과 같다면,

```text
Current State
Pod = 2
```

둘 사이에는 차이가 있다.

Controller는 이를 감지하여 현재 상태를 원하는 상태에 맞춘다.

```text
Desired State = 3
Current State = 2
       │
       ▼
Controller
       │
       │ Reconciliation
       ▼
새로운 Pod 생성
       │
       ▼
Current State = 3
```

이러한 지속적인 조정 과정을 **Reconciliation Loop**라고 한다.

---

# 8. Declarative Model

Reconciliation을 이해하면 Kubernetes의 **Declarative Model**도 자연스럽게 연결된다.

Imperative 방식에서는 사용자가 수행할 절차를 직접 명령한다.

```text
Pod 하나 만들어
→ 또 하나 만들어
→ 또 하나 만들어
```

반면 Declarative 방식에서는 최종적으로 원하는 상태를 선언한다.

```text
"Pod가 항상 3개 존재해야 한다."
```

그리고 Kubernetes가 알아서 현재 상태를 원하는 상태에 맞춘다.

```text
Desired State
      │
      │ Reconciliation
      ▼
Current State
```

따라서 Kubernetes의 **Self-Healing**도 이 구조와 연결된다.

Pod 하나가 사라지면,

```text
Desired = 3
Current = 2
```

가 되고 Controller가 차이를 감지해 다시 Pod를 생성한다.

즉 Kubernetes에서는 사용자가 장애가 발생할 때마다 복구 명령을 내리는 것이 아니라 **원하는 상태를 선언하고 Controller가 그 상태를 지속적으로 유지하도록 하는 것**이 핵심이다.

---

# 9. cloud-controller-manager

`cloud-controller-manager`는 Kubernetes의 Cloud Provider 관련 Control Logic을 담당한다.

Kubernetes의 핵심 로직과 AWS, Azure, GCP 등의 Cloud-specific Logic을 분리하기 위해 존재한다.

대표적으로 다음과 관련된다.

```text
Kubernetes
     │
     ▼
cloud-controller-manager
     │
     ├── Node 관련 Cloud 정보
     ├── Route
     └── Cloud Load Balancer
```

예를 들어 Cloud 환경에서 `LoadBalancer` Type Service를 생성했을 때 Cloud Provider의 Load Balancer와 연동되는 과정이 대표적인 예이다.

### 주의

오래된 자료에서는 Cloud Storage Provisioning도 `cloud-controller-manager` 역할처럼 설명되는 경우가 있다.

현재 Kubernetes Storage Integration은 주로 **CSI(Container Storage Interface)** 기반으로 분리되어 있으므로,

```text
cloud-controller-manager
= Kubernetes와 Cloud Provider의 Control Logic 연결
```

이라는 핵심 개념으로 기억하는 것이 좋다.

---

# 10. Worker Node

Worker Node는 실제 Application Workload가 실행되는 Node이다.

```text
Worker Node
│
├── kubelet
├── Container Runtime
├── kube-proxy
│
└── Pods
    └── Containers
```

Control Plane이 의사결정을 담당한다면 Worker Node는 그 결과에 따라 실제 Workload를 실행한다.

---

# 11. kubelet

`kubelet`은 각 Node에서 동작하는 **Node Agent**이다.

해당 Node에 할당된 PodSpec을 확인하고 Container Runtime을 통해 필요한 Container가 실행되도록 관리한다.

```text
kube-apiserver
      │
      ▼
   kubelet
      │
      │ CRI
      ▼
Container Runtime
      │
      ▼
  Container
```

또한 Node와 Pod의 상태를 Control Plane에 보고한다.

kubelet은 다음과 연결해서 기억하면 된다.

```text
Node Agent
Pod 실행 관리
Container Runtime 연동
Probe 수행
Node / Pod 상태 보고
```

---

# 12. Container Runtime과 CRI

Container Runtime은 실제 Container를 실행하는 소프트웨어이다.

대표적으로,

- `containerd`
- `CRI-O`

등이 있다.

kubelet은 특정 Container Runtime 구현에 직접 종속되지 않고 **CRI(Container Runtime Interface)​**를 통해 Runtime과 통신한다.

```text
kubelet
   │
   │ CRI
   ▼
Container Runtime
   │
   ├── containerd
   └── CRI-O
```

KCNA에서는 앞으로 다음 세 가지 Interface가 계속 등장하기 때문에 구분해야 한다.

| Interface | 역할 |
|---|---|
| CRI | Container Runtime |
| CNI | Container Networking |
| CSI | Container Storage |

즉,

```text
CRI → Runtime
CNI → Network
CSI → Storage
```

로 먼저 기억해두면 된다.

---

# 13. kube-proxy

`kube-proxy`는 각 Node에서 Kubernetes **Service Networking**을 구현하는 Component이다.

Service와 Backend Endpoint 정보를 확인하고 Node의 Network Rule을 구성하여 Service Traffic이 Backend Pod로 전달될 수 있도록 한다.

전통적으로 Linux의 다음 기능을 사용해 왔다.

```text
iptables
IPVS
```

여기서 이름 때문에 `kube-proxy`가 모든 Packet을 Application Proxy처럼 직접 받아서 전달한다고 생각하기 쉽다.

하지만 일반적으로 kube-proxy는 **Packet Forwarding을 위한 Network Rule을 구성하고 유지하는 역할**을 한다.

### kube-proxy는 반드시 있어야 할까?

현대 Kubernetes 환경에서는 반드시 그런 것은 아니다.

일부 Networking 구현은 eBPF 등을 이용하여 kube-proxy의 기능을 대체할 수 있다.

예를 들어 Cilium을 kube-proxy replacement 방식으로 구성할 수 있다.

따라서 정확한 이해는 다음과 같다.

```text
kube-proxy
→ Kubernetes Service Networking의 전통적인 구현 Component
```

---

# 14. Component가 장애 나면 어떻게 될까?

각 Component의 역할을 외우는 가장 좋은 방법 중 하나는 **해당 Component가 중단되면 무엇이 안 되는지** 생각해보는 것이다.

| Component | 주요 영향 |
|---|---|
| kube-apiserver | API Request 처리 불가 |
| etcd | Cluster State Read/Write에 심각한 문제 |
| kube-scheduler | Scheduling이 필요한 Pod가 Node를 배정받지 못함 |
| kube-controller-manager | Reconciliation 중단 |
| kubelet | 해당 Node의 Pod 관리 및 상태 보고 문제 |

여기서 중요한 것은 Control Plane이 중단되었다고 해서 **현재 실행 중인 모든 Pod가 즉시 종료되는 것은 아니라는 것**이다.

예를 들어 Scheduler가 중단되더라도 기존 Pod는 Worker Node에서 계속 실행될 수 있다.

```text
Control Plane
     X

Worker Node
│
├── Pod A → Running
├── Pod B → Running
└── Pod C → Running
```

대신 새로운 Pod의 Scheduling 같은 Control Plane 작업에 문제가 발생한다.

---

# 15. Pod

Pod는 Kubernetes의 **가장 작은 Deployable Computing Unit**이다.

Kubernetes에서는 Container를 독립적으로 Scheduling하지 않고 **Pod 단위로 Scheduling**한다.

```text
Node
 │
 ▼
Pod
├── Container A
└── Container B
```

하나의 Pod에는 하나 이상의 Container가 들어갈 수 있다.

같은 Pod 안에 있는 Container들은 Network Namespace를 공유하므로 같은 Pod IP와 Port Space를 사용하고 `localhost`로 서로 통신할 수 있다.

필요한 경우 Volume을 통해 Storage도 공유할 수 있다.

### Pod와 Container는 같은 것이 아니다

```text
Pod
→ Kubernetes가 Scheduling하고 관리하는 단위

Container
→ 실제 Application Process가 실행되는 환경
```

따라서 시험에서 `smallest deployable unit in Kubernetes`라는 표현이 나오면 **Pod**를 생각한다.

---

# 16. ReplicaSet

ReplicaSet은 **지정한 수의 Pod Replica가 항상 존재하도록 보장**한다.

예를 들어,

```text
ReplicaSet
replicas = 3

    │
    ├── Pod
    ├── Pod
    └── Pod
```

Pod 하나가 사라지면,

```text
Desired = 3
Current = 2

      ↓

ReplicaSet Controller

      ↓

새로운 Pod 생성
```

과 같이 다시 Desired State를 맞춘다.

ReplicaSet은 **Label Selector**를 통해 자신이 관리해야 하는 Pod를 찾는다.

하지만 일반적인 Application Deployment에서는 ReplicaSet을 직접 생성하기보다 상위 Resource인 **Deployment**를 사용한다.

---

# 17. Deployment

Deployment는 ReplicaSet을 관리하는 상위 Workload Resource이다.

대표적으로 다음 기능을 제공한다.

- ReplicaSet 관리
- Scaling
- Rolling Update
- Rollback
- Revision 관리

구조를 보면 이해하기 쉽다.

```text
Deployment
     │
     ▼
ReplicaSet
     │
     ▼
    Pods
```

Application Image를 새로운 Version으로 변경하면 Deployment는 새로운 ReplicaSet을 만들고 Pod를 점진적으로 교체할 수 있다.

### Deployment vs ReplicaSet

| Deployment | ReplicaSet |
|---|---|
| Application Deployment 관리 | Pod Replica 수 관리 |
| ReplicaSet 관리 | Pod 관리 |
| Rolling Update | Replica 유지 |
| Rollback | Replica 유지 |
| 일반적으로 직접 사용 | Deployment가 내부적으로 사용하는 경우가 많음 |

시험에서는 한 문장으로 기억하면 된다.

```text
Deployment
→ ReplicaSet 관리

ReplicaSet
→ Pod 관리
```

---

# 18. Service가 필요한 이유

Pod에는 중요한 특성이 있다.

**Pod는 Ephemeral하다.**

Pod가 장애로 사라지고 새로운 Pod가 생성되면 새로운 IP를 받을 수 있다.

예를 들어,

```text
Pod A
10.0.1.10

   ↓ 장애

새로운 Pod
10.0.2.15
```

Client가 기존 `10.0.1.10`에 직접 연결하고 있었다면 문제가 발생한다.

그래서 Pod 앞에 **Service**를 둔다.

```text
              ┌── Pod A
Client → Service ── Pod B
              └── Pod C
```

Service는 여러 Pod에 대해 **안정적인 Network Endpoint**를 제공한다.

Pod가 교체되더라도 Client는 Service를 통해 접근할 수 있다.

---

# 19. Service와 Pod는 어떻게 연결될까?

일반적으로 **Label과 Selector**를 사용한다.

Pod에 다음 Label이 있다고 하자.

```yaml
labels:
  app: web
```

Service에는 다음 Selector가 있다.

```yaml
selector:
  app: web
```

그러면 Kubernetes는 해당 Label을 가진 Pod들을 Service의 Backend로 연결한다.

```text
Service
selector: app=web
      │
      ├── Pod A [app=web]
      ├── Pod B [app=web]
      └── Pod C [app=web]
```

즉 Service는 특정 Pod 이름 하나를 직접 기억하는 방식이 아니다.

**Label을 기준으로 Pod 집합을 선택한다.**

이 덕분에 Pod가 삭제되고 새로운 Pod가 만들어져도 동일한 Label을 가지고 있다면 Service Backend에 포함될 수 있다.

# 20. Service Type

KCNA에서는 주요 Service Type의 차이를 구분할 수 있어야 한다.

## ClusterIP

기본 Service Type이다.

Cluster 내부에서 접근할 수 있는 Service를 제공한다.

```text
Cluster 내부 Client
       │
       ▼
   ClusterIP
       │
       ▼
      Pods
```

---

## NodePort

각 Node의 Port를 통해 Service를 외부에 노출한다.

```text
External Client
       │
       ▼
<Node IP>:<NodePort>
       │
       ▼
    Service
       │
       ▼
      Pods
```

---

## LoadBalancer

외부 Load Balancer를 이용하여 Service를 외부에 노출한다.

```text
Internet / External Client
           │
           ▼
     Load Balancer
           │
           ▼
        Service
           │
           ▼
          Pods
```

지원되는 Cloud 환경에서는 Cloud Provider Integration을 통해 외부 Load Balancer가 Provisioning될 수 있다.

### 시험용 구분

```text
Cluster 내부 접근
→ ClusterIP

Node IP + Port를 통한 접근
→ NodePort

External Load Balancer
→ LoadBalancer
```

# 21. Label과 Selector

Label은 Kubernetes Object에 붙이는 **Key-Value Metadata**이다.

예를 들어,

```yaml
labels:
  app: nginx
  environment: production
```

처럼 사용할 수 있다.

Selector는 Label을 기준으로 Resource를 선택한다.

```text
Label
→ Resource가 가지고 있는 정보

Selector
→ 원하는 Label을 가진 Resource를 선택
```

예를 들어 Service와 Pod의 관계는 다음과 같다.

```text
Service
selector: app=web
       │
       ▼
Pod
label: app=web
```

ReplicaSet도 Label Selector를 이용하여 자신이 관리해야 할 Pod를 식별한다.

따라서 Kubernetes Resource 간의 관계를 이해할 때 **Label / Selector**는 매우 중요한 개념이다.

# 22. Namespace

Namespace는 처음에는 단순한 개념처럼 보이지만 정확하게 이해해두는 것이 좋다.

Namespace는 하나의 Kubernetes Cluster 안에서 **Namespaced Resource를 논리적으로 구분하기 위한 Scope**이다.

예를 들어 하나의 Cluster를 개발 환경과 운영 환경에서 같이 사용한다고 생각해보자.

```text
Kubernetes Cluster
│
├── Namespace: dev
│   ├── Deployment: web
│   ├── Service: web
│   └── ConfigMap: web-config
│
└── Namespace: production
    ├── Deployment: web
    ├── Service: web
    └── ConfigMap: web-config
```

`dev`와 `production`은 서로 다른 Namespace이므로 같은 이름의 Resource가 존재할 수 있다.

```text
dev/web

production/web
```

즉 Namespace는 **Resource Name의 Scope를 나누는 역할**도 한다.

---

# 23. Namespace를 폴더라고 생각하면 될까?

처음 이해할 때는 폴더와 비슷하게 생각할 수 있지만 완전히 같은 개념은 아니다.

Kubernetes의 모든 Resource가 Namespace 안에 들어가는 것이 아니기 때문이다.

Kubernetes Resource는 크게 두 가지 Scope로 나뉜다.

```text
Kubernetes Resources
│
├── Namespaced Resources
│
└── Cluster-Scoped Resources
```

---

# 24. Namespaced Resource

특정 Namespace에 속하는 Resource이다.

대표적으로,

```text
Pod
Deployment
ReplicaSet
Service
ConfigMap
Secret
Role
```

등이 있다.

예를 들어,

```bash
kubectl get pods -n dev
```

라고 하면 `dev` Namespace에 존재하는 Pod를 조회한다.

```text
Cluster
│
├── Namespace: dev
│   ├── Pod
│   ├── Service
│   └── Deployment
│
└── Namespace: prod
    ├── Pod
    ├── Service
    └── Deployment
```

---

# 25. Cluster-Scoped Resource

반대로 특정 Namespace에 속하지 않고 **Cluster 전체 Scope에 존재하는 Resource**도 있다.

대표적으로,

```text
Node
Namespace
PersistentVolume
ClusterRole
ClusterRoleBinding
```

등이 있다.

특히 Node를 생각하면 이해하기 쉽다.

잘못 이해하면 다음과 같이 생각할 수 있다.

```text
Cluster
│
├── Namespace: dev
│   └── Node A
│
└── Namespace: production
    └── Node B
```

하지만 실제 구조는 그렇지 않다.

```text
                 Kubernetes Cluster
                    /          \
                   /            \
              Nodes           Namespaces
             /    \            /      \
        Node A   Node B      dev     production
                             │          │
                            Pods       Pods
```

Node는 특정 Namespace의 소유가 아니다.

`dev` Namespace의 Pod와 `production` Namespace의 Pod가 **동일한 Worker Node에서 실행될 수도 있다.**

예를 들면,

```text
Worker Node A
│
├── Pod A
│   Namespace = dev
│
└── Pod B
    Namespace = production
```

이것이 가능한 이유는 Namespace가 Worker Node를 물리적으로 분리하는 기능이 아니기 때문이다.

---

# 26. 그러면 kube-system은 무엇일까?

Kubernetes Cluster를 조회하다 보면 다음 Namespace를 자주 볼 수 있다.

```text
default
kube-system
kube-public
kube-node-lease
```

이 중 `kube-system`은 **Kubernetes System Component와 Add-on 관련 Resource들이 주로 위치하는 Namespace**이다.

예를 들어 kubeadm 기반 환경에서는 다음과 같은 Pod를 볼 수 있다.

```text
kube-system
│
├── kube-apiserver-...
├── kube-scheduler-...
├── kube-controller-manager-...
├── kube-proxy-...
└── coredns-...
```

여기서 처음에는 한 가지 의문이 생길 수 있다.

> kube-apiserver는 Control Plane Component인데 왜 Namespace 안에 Pod로 존재하지?

kubeadm 기반 Kubernetes에서는 Control Plane Component인 `kube-apiserver`, `kube-scheduler`, `kube-controller-manager` 등을 **Static Pod**로 실행할 수 있기 때문이다.

즉,

```text
kube-apiserver
→ Kubernetes Control Plane Component

kube-apiserver Pod
→ 해당 Component가 실행되는 형태
```

이다.

`kube-system` Namespace 안에 Pod로 보인다고 해서 Control Plane이라는 개념 자체가 Namespace에 종속된다는 뜻은 아니다.

---

# 27. Kubernetes의 기본 Namespace

대표적인 기본 Namespace도 구분해두면 좋다.

| Namespace | 역할 |
|---|---|
| `default` | Namespace를 별도로 지정하지 않은 Object가 기본적으로 생성되는 Namespace |
| `kube-system` | Kubernetes System Component와 Add-on 관련 Object |
| `kube-public` | Cluster 내에서 공개적으로 읽을 수 있도록 의도된 데이터에 사용 |
| `kube-node-lease` | Node Heartbeat에 사용되는 Lease Object 저장 |

특히 `kube-node-lease`에는 각 Node와 연결된 Lease Object가 존재하며 kubelet이 이를 갱신하여 Node Heartbeat를 효율적으로 전달한다.

---

# 28. Namespace가 다르면 서로 격리될까?

여기서 한 가지 중요한 함정이 있다.

**Namespace가 다르다고 Network Traffic이 자동으로 차단되는 것은 아니다.**

예를 들어,

```text
Namespace: dev
     │
     │ Network Traffic
     ▼
Namespace: production
```

Namespace가 다르다는 이유만으로 이 통신이 자동 차단되는 것은 아니다.

Network Isolation이 필요하다면 **NetworkPolicy** 같은 별도의 정책을 사용해야 한다.

마찬가지로 Namespace만 생성했다고 완전한 Multi-Tenant Security가 만들어지는 것도 아니다.

실제 환경에서는 필요에 따라 다음과 같은 기능을 함께 사용한다.

```text
Namespace
    +
RBAC
    +
NetworkPolicy
    +
ResourceQuota
    +
LimitRange
```

따라서,

> Namespace provides complete network isolation.

이라는 보기가 나오면 틀린 설명이다.

Namespace의 핵심은 **Resource의 논리적인 Scope를 제공하는 것**이다.

---

# 29. 실제 Resource Scope 확인하기

어떤 Resource가 Namespace에 속하는지 헷갈린다면 다음 명령으로 직접 확인할 수 있다.

```bash
kubectl api-resources
```

출력에는 `NAMESPACED` Column이 존재한다.

예를 들어,

```text
NAME                  NAMESPACED

pods                  true
services              true
deployments           true

nodes                 false
namespaces            false
persistentvolumes     false
```

따라서,

```text
NAMESPACED = true
→ Namespace에 속하는 Resource

NAMESPACED = false
→ Cluster-Scoped Resource
```

라고 보면 된다.

이렇게 보니 예전에 CKA를 공부하면서 `kubectl get pods -A`는 사용했지만 `kubectl get nodes -A`가 사실상 Namespace 구분과 관계없는 이유도 연결해서 이해할 수 있었다.

# 30. Namespace에서 시험에 나올 수 있는 포인트

### Q. Which Kubernetes resource is cluster-scoped?

```text
A. Pod
B. ConfigMap
C. Node
D. Service
```

정답은 **C. Node**

Pod, ConfigMap, Service는 Namespaced Resource이고 Node는 Cluster-Scoped Resource이다.

---

### Q. Does a Namespace automatically provide network isolation?

```text
No.
```

Namespace 자체는 Network Traffic을 자동 차단하지 않는다.

Network Isolation에는 `NetworkPolicy` 등을 사용할 수 있다.

---

### Q. Where are Kubernetes system objects commonly located?

```text
kube-system
```

다만 **모든 Kubernetes Resource가 kube-system에 존재한다는 뜻은 아니다.**

# 31. KCNA에서 꼭 구분해야 하는 개념

이번 파트에서 다음 관계는 확실하게 구분할 수 있어야 한다.

| 비교 | A | B |
|---|---|---|
| Control Plane vs Worker | Cluster 관리/의사결정 | Workload 실행 |
| Scheduler vs kubelet | 실행할 Node 선택 | 해당 Node에서 Pod 실행 관리 |
| kubelet vs Runtime | Pod Lifecycle 관리 | 실제 Container 실행 |
| Deployment vs ReplicaSet | Deployment Lifecycle 관리 | Replica 수 유지 |
| Pod vs Container | Kubernetes Scheduling 단위 | 실제 Process 실행 환경 |
| Pod vs Service | Workload 실행 | 안정적인 Network Endpoint |
| Label vs Selector | Object에 붙이는 Metadata | Label 기반 Object 선택 |
| Namespace vs Node | Resource Scope | Cluster-Scoped Compute Resource |
| CRI vs CNI vs CSI | Runtime | Network / Storage |

# 32. 시험에서 자주 헷갈릴 수 있는 문장

아래 문장을 보고 바로 O/X를 판단할 수 있을 정도로 정리해두는 것이 좋다.

### `kube-scheduler runs containers on worker nodes.`

**X**

Scheduler는 Pod가 실행될 Node를 선택한다.

실제 Container 실행은 kubelet과 Container Runtime이 담당한다.

### `etcd stores Kubernetes cluster state.`

**O**

etcd는 Kubernetes Cluster State를 저장하는 Distributed Key-Value Store이다.

### `A Deployment directly manages containers.`

**X**

관계는 다음과 같다.

```text
Deployment
→ ReplicaSet
→ Pod
→ Container
```

### `A Service provides a stable endpoint for a set of Pods.`

**O**

Pod는 교체될 수 있기 때문에 Service가 안정적인 접근 지점을 제공한다.

### `A Namespace provides complete network isolation.`

**X**

Namespace와 Network Isolation은 다른 개념이다.

### `Nodes belong to Kubernetes Namespaces.`

**X**

Node는 Cluster-Scoped Resource이다.

### `Pods in different Namespaces may run on the same Node.`

**O**

Namespace는 Node를 물리적으로 분리하지 않는다.

### `kube-proxy is responsible for scheduling Pods.`

**X**

Scheduling은 `kube-scheduler`의 역할이다.

### `The kubelet runs on Kubernetes Nodes.`

**O**

kubelet은 각 Node에서 동작하는 Node Agent이다.

이번 내용을 각각 따로 외우기보다는 다음 흐름으로 연결해서 기억한다.

```text
                    Kubernetes Cluster
                             │
          ┌──────────────────┴──────────────────┐
          │                                     │
     Control Plane                         Worker Node
          │                                     │
   kube-apiserver                             kubelet

          │                                     │

                 │
```

Workload Resource 관계는 별도로 다음처럼 기억한다.

```text
Deployment
    │
    ▼
ReplicaSet
    │
    ▼
   Pod
    │
    ▼
Container
```

Network 관점에서는,

```text
Client
   │
   ▼
Service
   │
   │ Label Selector
   ▼
Pod A   Pod B   Pod C
```

Resource Scope 관점에서는,

```text

│

│   ├── Node
```

# 정리하면서

이번 내용은 CKA를 공부하면서 이미 많이 다뤘던 내용이라 각각의 Component 이름 자체는 익숙했다.

하지만 KCNA 관점에서 다시 정리해보니 단순히 `kube-scheduler = Scheduling`, `kubelet = Node Agent`처럼 외우는 것보다 **Pod 하나가 생성될 때 각 Component가 어느 시점에 어떤 역할을 하는지 연결해서 이해하는 것이 훨씬 명확했다.**

특히 Namespace는 이전에는 단순히 `dev`, `prod`처럼 Cluster 내부 환경을 나누는 단위 정도로 생각했는데, 이번에 다시 보면서 **Kubernetes Resource의 Scope라는 관점**으로 이해할 필요가 있다는 점을 알게 되었다.

```text
Pod / Deployment / Service
→ Namespaced Resource

Node / Namespace / PersistentVolume
→ Cluster-Scoped Resource
```

그리고 Namespace를 나눈다고 Node까지 나뉘는 것도 아니고, Network가 자동으로 격리되는 것도 아니다.

결국 이번 파트의 핵심은 각각의 Component와 Resource를 따로 외우는 것이 아니라,

```text
API 요청
   ↓
Control Plane
   ↓
Desired State 저장 / Reconciliation / Scheduling
   ↓
Worker Node
   ↓
Pod
   ↓
Container
```

이라는 Kubernetes 전체 동작 과정 안에서 **누가 무엇을 담당하는지 구분하는 것**이라고 정리할 수 있다.
