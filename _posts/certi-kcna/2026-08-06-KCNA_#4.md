# KCNA #4 - Container Orchestration: 네트워킹, 보안, 트러블슈팅, 스토리지

앞선 글까지 Kubernetes Cluster Architecture, API, Container, Scheduling을 정리했다면 이번에는 Kubernetes에서 Containerized Workload를 실제로 운영하는 데 필요한 **Networking, Security, Troubleshooting, Storage​**를 중심으로 정리한다.

기존 KCNA 자료에서는 Container Orchestration이 다음과 같이 **22%**로 설명되는 경우가 많다.

```text
Old Curriculum

Container Orchestration - 22%

├── Container Runtime
├── Security
├── Networking
├── Storage
└── Service Mesh
```

하지만 KCNA Curriculum은 2025년 11월 이후 변경되었고, 현재 공식 범위는 다음과 같다.

```text
Current Curriculum

Container Orchestration - 28%

├── Networking
├── Security
├── Troubleshooting
└── Storage
```

즉 **22% → 28%로 비중이 증가했고, Troubleshooting이 공식 Competency로 명시되었다.**

반대로 Container Runtime은 현재 `Kubernetes Fundamentals → Containerization`과도 연결되고, Service Mesh는 현재 Container Orchestration의 공식 Competency 이름에는 별도로 적혀 있지 않다.

그렇다고 기존 자료의 Runtime이나 Service Mesh 내용을 버릴 필요는 없다. CRI/CNI/CSI 같은 Interface를 이해하려면 Runtime 구조를 알아야 하고 Service Mesh 역시 Cloud Native Networking을 이해하는 데 의미가 있기 때문이다.

따라서 이번 글에서는 다음처럼 구분해 정리한다.

```text
현재 KCNA Container Orchestration 핵심

├── Networking        ★ 핵심
├── Security          ★ 핵심
├── Troubleshooting   ★ 핵심
└── Storage           ★ 핵심

함께 알아둘 배경지식

├── Container Runtime / OCI / CRI
└── Service Mesh
```

이 영역에서 가장 중요한 관점은 **Kubernetes가 모든 기능을 직접 구현하는 시스템이 아니라 여러 표준 Interface와 Plugin을 조합하는 Platform**이라는 점이다.

대표적인 예가 다음 세 가지다.

| Interface | 영역 |
|---|---|
| CRI | Container Runtime |
| CNI | Container Networking |
| CSI | Container Storage |

시험에서 셋을 섞어서 보기를 만드는 경우를 대비해서 최소한 다음 연결은 바로 떠올라야 한다.

```text
R → Runtime → CRI
N → Network → CNI
S → Storage → CSI
```

---

# 1. Container Runtime

Container Runtime은 **Container Image를 기반으로 실제 Container Process를 생성하고 실행하는 소프트웨어**이다.

Kubernetes Worker Node에서 kubelet이 직접 Linux Namespace와 cgroup을 구성하여 Container를 만드는 것은 아니다.

개념적인 흐름은 다음과 같다.

```text
kubelet
   │
   │ CRI
   ▼
Container Runtime
   │
   ▼
Container Process
```

대표적인 Kubernetes Container Runtime에는 `containerd`와 `CRI-O`가 있다.

---

# 2. 고수준 Runtime과 저수준 Runtime

Container Runtime을 이해할 때 고수준 Runtime과 저수준 Runtime을 구분하면 구조가 이해하기 쉽다.

## 고수준 Runtime

고수준 Runtime은 Image 관리, Container Lifecycle 관리 등 Container 실행에 필요한 상위 기능을 담당한다.

대표적으로 다음과 같다.

- containerd
- CRI-O

## 저수준 Runtime

저수준 Runtime은 실제 Linux Kernel 기능을 이용하여 Process 격리와 Container 실행을 담당한다.

대표적인 구현체가 **runc**이다.

전체 구조를 단순화하면 다음과 같다.

```text
kubelet
   │
   │ CRI
   ▼
containerd / CRI-O
   │
   ▼
runc
   │
   ├── Linux Namespace
   ├── cgroup
   └── Container Process
```

즉 containerd를 Container 관리 계층, runc를 실제 Container Process 실행 계층이라고 생각하면 이해하기 쉽다.

KCNA에서 저수준 Runtime 내부 구조까지 깊게 알 필요는 없지만 `containerd/CRI-O`와 `runc`가 같은 역할을 하는 것은 아니라는 정도는 구분하면 좋다.

---

# 3. OCI 표준

Container Image와 Runtime이 각 Vendor마다 완전히 다른 형식을 사용하면 서로 호환하기 어렵다.

이를 위한 Open Standard가 **OCI(Open Container Initiative)​**이다.

OCI에서는 대표적으로 다음 Specification을 정의한다.

| Specification | 역할 |
|---|---|
| Image Specification | Container Image Format과 구조 |
| Runtime Specification | Container 실행 방식 |
| Distribution Specification | Container Image Distribution 관련 규격 |

기존 자료에서는 주로 `image-spec`, `runtime-spec` 두 가지가 강조되지만 현재 OCI에는 Distribution Specification도 존재한다.

- image-spec: 컨테이너 이미지의 포맷(레이어 구조, 매니페스트 등)을 정의합
- runtime-spec: 풀어 둔 이미지를 어떻게 실행할지(파일시스템 번들, 수명 주기)를 정의합
OCI 덕분에 어느 도구로 빌드한 이미지든 OCI를 따르는 어느 런타임에서나 동일하게 동작한다.
- runc는 OCI runtime-spec의 참조 구현입

KCNA에서는 Specification 내부 구조를 외울 필요는 없다.

중요한 것은 다음이다.

```text
OCI
→ Container Image / Runtime 생태계의 Open Standard

runc
→ OCI Runtime Specification과 밀접하게 연결된 Runtime 구현체
```

Docker로 Build한 Image라고 해서 Kubernetes에서 반드시 Docker Engine이 필요한 것도 아니다.

Image가 OCI-compatible Format을 사용한다면 containerd 같은 Runtime에서도 실행할 수 있다.

---

# 4. CRI: kubelet과 Container Runtime의 Interface

**CRI(Container Runtime Interface)​**는 kubelet과 Container Runtime 사이의 표준 Interface이다.

```text
kubelet
   │
   │ CRI
   ▼
Container Runtime
├── containerd
└── CRI-O
```

CRI는 kubelet이 Runtime 구현에 직접 종속되지 않도록 한다.

즉 Kubernetes 관점에서는,

```text
"containerd를 어떻게 제어하는가?"
```

보다,

```text
"CRI를 구현하는 Runtime인가?"
```

가 중요하다.

CRI는 kubelet과 Runtime 사이의 **gRPC 기반 Protocol**이다.

따라서 다음 표현을 구분해야 한다.

```text
CRI
→ Container Runtime 자체가 아님
→ kubelet과 Runtime 사이 Interface

containerd / CRI-O
→ CRI를 통해 Kubernetes와 연동되는 Runtime
```

---

# 5. dockershim은 왜 제거되었을까?

초기 Kubernetes에서는 Docker Engine이 Kubernetes CRI를 직접 구현하지 않았기 때문에 kubelet과 Docker 사이에 **dockershim**이라는 Adapter가 존재했다.

```text
Before

kubelet
   │
   ▼
dockershim
   │
   ▼
Docker Engine
```

하지만 containerd와 CRI-O처럼 CRI를 직접 지원하는 Runtime이 널리 사용되면서 Kubernetes 내부에서 Docker 전용 Adapter를 유지할 필요성이 줄었다.

결국 dockershim은 Kubernetes v1.24에서 제거되었다.

현재 구조는 다음처럼 이해할 수 있다.

```text
kubelet
   │
   │ CRI
   ▼
containerd / CRI-O
```

여기서 시험에서 헷갈리면 안 되는 부분이 있다.

> dockershim이 제거되었으므로 Docker로 Build한 Image는 Kubernetes에서 사용할 수 없다.

이 설명은 틀리다.

**Image Build Tool과 Container Runtime은 별개**이다.

Docker로 Build한 OCI-compatible Image는 containerd 같은 Runtime에서도 실행할 수 있다.

# 6. CRI / CNI / CSI

이 세 Interface는 KCNA를 공부하면서 반드시 구분해두는 것이 좋다.

| Interface | Full Name | 담당 영역 | 대표 구현 |
|---|---|---|---|
| CRI | Container Runtime Interface | Container 실행 | containerd, CRI-O |
| CNI | Container Network Interface | Pod Networking | Cilium, Calico, Flannel |
| CSI | Container Storage Interface | Persistent Storage | AWS EBS CSI, Ceph CSI 등 |

공통점은 Kubernetes가 특정 구현체에 종속되지 않도록 **표준 경계**를 제공한다는 것이다.

```text
Kubernetes
│
├── CRI → Runtime
├── CNI → Network
└── CSI → Storage
```

### 시험에서 바로 구분하기

`Which interface connects kubelet to container runtimes?`

→ CRI

`Which interface is responsible for Pod networking?`

→ CNI

`Which interface allows external storage systems to integrate with Kubernetes?`

→ CSI

이 세 문장은 실제 공개 시험 문항을 인용한 것이 아니라 **공식 Curriculum을 공부하기 위한 개념 확인 문장**이다.

# 8. Authentication과 Authorization

Kubernetes Security에서 먼저 구분해야 하는 두 개념이다.

```text
Authentication
→ "당신은 누구인가?"

Authorization
→ "당신이 이 작업을 할 수 있는가?"
```

예를 들어 사용자가 다음 요청을 한다고 생각해보자.

```text
"production Namespace의 Secret을 읽겠다."
```

Kubernetes는 먼저 사용자의 Identity를 확인한다.

```text
Authentication
→ 이 요청을 보낸 사용자가 누구인지 확인
```

그 다음 해당 사용자가 실제로 Secret을 읽을 권한이 있는지 확인한다.

```text
Authorization
→ 이 사용자가 Secret GET 권한을 가지고 있는가?
```

RBAC는 Authorization을 구현하는 대표적인 방식이다.

---

# 9. RBAC

**RBAC(Role-Based Access Control)​**는 Kubernetes에서 `누가 무엇을 할 수 있는가`를 정의하는 Authorization Model이다.

RBAC의 핵심 Resource는 다음 네 가지다.

```text
Role
ClusterRole
RoleBinding
ClusterRoleBinding
```

그리고 권한을 부여받는 Subject에는 대표적으로 다음이 있다.

```text
User
Group
ServiceAccount
```

---

# 10. Role

**Role**은 특정 Namespace 안에서 사용할 수 있는 Permission을 정의한다.

예를 들어 다음 권한을 가진 Role을 만들 수 있다.

```text
Namespace: dev

pods
→ get
→ list
→ watch
```

즉 Role은 **Namespaced Resource**이다.

---

# 11. ClusterRole

**ClusterRole**은 Cluster Scope의 RBAC Permission Object이다.

ClusterRole은 다음 두 상황 모두에 사용할 수 있다.

1. Node처럼 Cluster-Scoped Resource에 대한 권한
2. 여러 Namespace에 공통적으로 사용할 수 있는 Permission Template

여기서 중요한 점이 있다.

> ClusterRole을 사용하면 반드시 Cluster 전체 권한만 부여된다.

이건 정확하지 않다.

ClusterRole을 **RoleBinding으로 연결하면 특정 Namespace 안에서만** 해당 ClusterRole의 Permission을 부여할 수도 있다.

이 차이는 시험에서 헷갈리기 쉽다.

---

# 12. RoleBinding

RoleBinding은 Permission을 실제 Subject에 연결한다.

RoleBinding은 특정 Namespace에 존재한다.

```text
Role
   │
   ▼
RoleBinding
   │
   ▼
User / Group / ServiceAccount
```

하지만 RoleBinding이 반드시 Role만 참조하는 것은 아니다.

```text
RoleBinding
├── Role 참조 가능
└── ClusterRole 참조 가능
```

ClusterRole을 RoleBinding으로 연결하더라도 **권한의 Scope는 해당 RoleBinding이 존재하는 Namespace로 제한**된다.

이 부분은 꼭 기억해야 한다.

---

# 13. ClusterRoleBinding

ClusterRoleBinding은 ClusterRole을 Subject에 연결하고 **Cluster 전체 Scope로 권한을 부여**한다.

```text
ClusterRole
      │
      ▼
ClusterRoleBinding
      │
      ▼
User / Group / ServiceAccount

→ Cluster-wide Permission
```

전체를 비교하면 다음과 같다.

| Resource | Scope | 역할 |
|---|---|---|
| Role | Namespace | Namespace Permission 정의 |
| ClusterRole | Cluster | Cluster-level Permission 정의/재사용 가능 |
| RoleBinding | Namespace | Role 또는 ClusterRole을 Namespace 범위로 연결 |
| ClusterRoleBinding | Cluster | ClusterRole을 Cluster 전체 범위로 연결 |

### KCNA에서 헷갈리는 포인트

**RoleBinding은 ClusterRole을 참조할 수 있다.**

다만 그 경우에도 권한은 RoleBinding이 존재하는 Namespace에 한정된다.

---

# 14. ServiceAccount

ServiceAccount는 **Kubernetes Workload의 Identity**라고 이해하면 된다.

사람 사용자가 Kubernetes API를 호출하는 것과 Pod 안의 Application이 Kubernetes API를 호출하는 것은 구분해야 한다.

```text
Human
→ User Identity

Pod / Application
→ ServiceAccount Identity
```

예를 들어 Controller나 Operator가 Kubernetes API를 호출해야 한다면 ServiceAccount Identity를 사용할 수 있다.

ServiceAccount는 Namespace-scoped Resource이다.

---

# 15. Least Privilege

RBAC를 이해할 때 함께 기억해야 하는 원칙이 **Least Privilege**이다.

필요한 권한만 최소한으로 부여하는 것이다.

예를 들어 Pod 목록만 조회해야 하는 Application에 다음 권한까지 줄 이유는 없다.

```text
Secret delete
Node update
ClusterRole create
```

따라서,

```text
필요한 Resource만
+
필요한 Verb만
+
필요한 Scope에서만
```

권한을 주는 것이 기본 보안 원칙이다.

---

# 16. NetworkPolicy

**NetworkPolicy**는 Pod에 대한 Network Traffic을 제어한다.

주로 L3/L4 수준에서 다음 Traffic을 제어한다.

```text
Ingress
→ Pod로 들어오는 Traffic

Egress
→ Pod에서 나가는 Traffic
```

NetworkPolicy는 Pod Selector를 이용하여 Policy 대상 Pod를 선택한다.

---

# 17. NetworkPolicy 기본 동작을 정확하게 이해하기

기존 글에서는 다음과 같이 설명되어 있었다.

```text
정책 없음
→ 모두 허용

정책 하나 적용
→ 명시하지 않은 Traffic 모두 차단
```

큰 방향은 이해하기 쉽지만 **정확하게는 Ingress와 Egress를 따로 봐야 한다.**

Pod는 특정 방향에 대해 자신을 선택하는 NetworkPolicy가 없다면 그 방향에서 기본적으로 Non-isolated 상태이다.

예를 들어 **Ingress Policy가 해당 Pod를 선택하면 그 Pod의 Ingress가 Isolation 대상**이 된다.

```text
NetworkPolicy 없음
→ Ingress 기본 허용
→ Egress 기본 허용
```

Ingress만 제한하는 Policy가 있다면,

```text
Ingress
→ Policy에서 허용한 Traffic 기준으로 제한

Egress
→ 별도 Egress Isolation이 없다면 기존 Default Allow
```

가 될 수 있다.

따라서 다음 표현이 더 정확하다.

> 어떤 Pod가 특정 방향(Ingress 또는 Egress)에 대해 NetworkPolicy에 의해 Isolation되면, 그 방향에서는 적용되는 Policy들이 허용한 Traffic만 허용된다.

---

# 18. NetworkPolicy는 Additive하다

여러 NetworkPolicy가 같은 Pod를 선택할 수도 있다.

이 경우 Policy가 서로 덮어쓰는 방식이 아니라 **허용 Rule이 합쳐지는 Additive Model**로 동작한다.

예를 들어,

```text
Policy A
→ frontend Namespace 허용

Policy B
→ monitoring Namespace 허용
```

두 Policy가 동일 Pod를 선택한다면 개념적으로 두 Source 모두 허용될 수 있다.

즉 NetworkPolicy는 일반 Firewall Rule처럼 `위에서 먼저 일치한 Rule이 승리`하는 순서 기반 모델로 이해하면 안 된다.

---

# 19. NetworkPolicy는 CNI 지원이 필요하다

NetworkPolicy Object를 만들었다고 무조건 Traffic이 차단되는 것은 아니다.

NetworkPolicy Enforcement를 지원하는 Network Plugin이 필요하다.

대표적으로 다음과 같은 CNI가 NetworkPolicy 기능을 제공할 수 있다.

- Calico
- Cilium

일부 단순 CNI 구성에서는 NetworkPolicy API Object를 생성할 수 있어도 실제 Traffic Enforcement가 되지 않을 수 있다.

따라서 시험에서는 다음 문장을 구분해야 한다.

```text
NetworkPolicy API Object 존재
≠ NetworkPolicy Enforcement가 무조건 동작
```

CNI가 해당 기능을 지원해야 한다.

---

# 20. SecurityContext

**SecurityContext**는 Pod 또는 Container가 어떤 권한과 Security Setting으로 실행될지 정의한다.

대표적으로 다음 설정이 있다.

```yaml
securityContext:
  runAsNonRoot: true
  allowPrivilegeEscalation: false
  readOnlyRootFilesystem: true
```

개념은 다음과 같다.

| 설정 | 목적 |
|---|---|
| `runAsNonRoot` | Root User 실행 방지 |
| `allowPrivilegeEscalation: false` | Process의 Privilege Escalation 제한 |
| `readOnlyRootFilesystem` | Container Root Filesystem을 Read-only로 사용 |
| Capabilities | Linux Capability 추가/제거 |
| seccomp | System Call 제한 Profile 적용 |

KCNA에서는 SecurityContext의 모든 Field를 암기하기보다 **Container Runtime Permission을 최소화하기 위한 설정**이라는 관점을 이해하면 된다.

# 21. Pod Security Standards

Kubernetes에는 Pod의 Security Level을 정의하는 **Pod Security Standards(PSS)​**가 있다.

세 가지 Level을 구분해야 한다.

| Level | 의미 |
|---|---|
| Privileged | 거의 제한 없음 |
| Baseline | 알려진 Privilege Escalation을 막는 기본 수준 |
| Restricted | Pod Hardening Best Practice에 가까운 강한 제한 |

Security 강도는 다음 순서로 이해하면 된다.

```text
Privileged
   ↓
Baseline
   ↓
Restricted

제한 약함 → 제한 강함
```

### Privileged

System 또는 Infrastructure Workload처럼 높은 권한이 필요한 경우 사용할 수 있는 매우 허용적인 Level이다.

### Baseline

일반 Application에 적용하기 쉬우면서 알려진 Privilege Escalation을 제한하는 중간 수준이다.

### Restricted

더 강한 Pod Security Best Practice를 강제한다.

시험에서는 `가장 엄격한 Level`을 물으면 **Restricted**, `가장 허용적인 Level`을 물으면 **Privileged**이다.

---

# 22. Pod Security Admission

Pod Security Standards는 **정책의 기준**이고, 이를 Kubernetes에서 실제로 적용하는 Built-in Mechanism이 **Pod Security Admission(PSA)​**이다.

```text
Pod Security Standards
→ 어떤 Security Level을 사용할 것인가?

Pod Security Admission
→ 그 Standard를 실제 Pod Admission 단계에서 적용
```

PSA는 Namespace 수준에서 적용할 수 있다.

대표적인 Mode도 알아두면 좋다.

| Mode | 동작 |
|---|---|
| `enforce` | 위반 Pod 생성 거부 |
| `warn` | 요청은 허용하지만 사용자에게 Warning |
| `audit` | 요청은 허용하지만 Audit Annotation 기록 |

즉 `Restricted`와 `enforce`는 같은 종류의 값이 아니다.

```text
Restricted
→ Security Standard Level

enforce
→ Admission Mode
```

---

# 23. PodSecurityPolicy와 PSA

과거 Kubernetes에는 **PodSecurityPolicy(PSP)​**라는 Resource가 있었다.

하지만 PSP는 Deprecated된 뒤 Kubernetes에서 제거되었고, 현재는 Pod Security Standards와 Pod Security Admission을 사용하는 방향으로 바뀌었다.

시험에서 오래된 자료를 볼 때 다음을 구분해야 한다.

```text
PodSecurityPolicy
→ Legacy / Removed

Pod Security Standards
→ Privileged / Baseline / Restricted

Pod Security Admission
→ Built-in Enforcement Mechanism
```

---

# 24. Kubernetes Networking Model

Kubernetes Network Model의 기본 원칙 중 하나는 **각 Pod가 자신의 Cluster-wide IP를 가진다**는 것이다.

의도적인 Network Segmentation이 없다면 Pod는 Node가 달라도 서로 통신할 수 있어야 한다.

```text
Node A                     Node B

Pod A                      Pod B
10.0.1.10  ──────────────▶ 10.0.2.20
```

일반적인 Kubernetes Network Model에서는 Pod 간 통신에 Application이 NAT나 Proxy를 직접 의식하지 않아도 된다.

또 같은 Pod 안의 Container는 동일 Network Namespace를 공유하기 때문에 `localhost`로 서로 통신할 수 있다.

---

# 25. CNI

**CNI(Container Network Interface)​**는 Container/Pod Networking을 구성하기 위한 표준 Interface이다.

Pod가 생성될 때 CNI Plugin은 일반적으로 다음과 같은 Networking 작업에 관여한다.

- Network Interface 구성
- Pod IP Address 할당
- Pod Network 연결
- Routing / Overlay 구성
- 구현체에 따라 NetworkPolicy 적용

대표적인 CNI 구현체는 다음과 같다.

### Flannel

상대적으로 단순한 Pod Network 구현으로 알려져 있다.

### Calico

NetworkPolicy와 Routing 기능으로 많이 사용된다.

### Cilium

eBPF를 활용하여 Networking, NetworkPolicy, Observability 등의 기능을 제공한다.

시험에서는 구현체 내부 구조보다 다음 관계가 더 중요하다.

```text
CNI
→ Pod Networking

CRI
→ Container Runtime

CSI
→ Storage
```

# 26. Service

Pod는 생성되고 삭제되면서 IP가 변경될 수 있다.

Service는 변하는 Pod 집합 앞에 **안정적인 Network Endpoint**를 제공한다.

```text
Client
   │
   ▼
Service
   │
   ├── Pod A
   ├── Pod B
   └── Pod C
```

Service는 일반적으로 Label Selector를 이용해 Backend Pod를 선택하고 Kubernetes는 Backend 정보를 **EndpointSlice** Object로 관리한다.

따라서 Service Troubleshooting에서 다음 관계도 중요하다.

```text
Service
→ Selector
→ Matching Pods
→ EndpointSlice
```

Service가 존재해도 Selector와 Pod Label이 맞지 않으면 Backend Endpoint가 없을 수 있다.

---

# 27. Service Type

대표적인 Service Type은 다음 세 가지다.

| Type | 노출 범위 | 주요 용도 |
|---|---|---|
| ClusterIP | Cluster 내부 | 내부 Service 간 통신 |
| NodePort | Node IP + Port | 외부에서 간단히 접근 |
| LoadBalancer | 외부 Load Balancer | 외부 Service Exposure |

## ClusterIP

기본 Service Type이다.

Cluster 내부에서 사용할 수 있는 Virtual IP를 제공한다.

## NodePort

각 Node의 Port를 통해 Service에 접근할 수 있도록 한다.

```text
<Client>
   ↓
NodeIP:NodePort
   ↓
Service
   ↓
Pods
```

## LoadBalancer

지원되는 환경에서 External Load Balancer를 통해 Service를 외부에 노출할 수 있다.

```text
External Client
      ↓
Load Balancer
      ↓
Service
      ↓
Pods
```

---

# 28. "ClusterIP ⊂ NodePort ⊂ LoadBalancer"는 항상 절대적인 규칙일까?

기존 자료에서는 Service Type을 다음처럼 외우기도 한다.

```text
ClusterIP
   ⊂
NodePort
   ⊂
LoadBalancer
```

이 표현은 **기본적인 구현 관계를 이해하는 데는 도움이 되지만 절대 규칙으로 외우면 안 된다.**

NodePort Service는 ClusterIP 기능 위에 NodePort Exposure를 추가하는 방식으로 동작하는 것이 일반적이다.

LoadBalancer Service도 기본적으로 NodePort를 사용할 수 있지만, 최신 Kubernetes에서는 구현에 따라 `allocateLoadBalancerNodePorts: false`를 사용하여 LoadBalancer Service에 NodePort를 할당하지 않는 구성도 가능하다.

따라서 시험에서는 다음 수준으로 이해하는 편이 안전하다.

```text
ClusterIP
→ Cluster 내부 Endpoint

NodePort
→ Node Port를 통한 Exposure

LoadBalancer
→ External Load Balancer Integration
```

---

# 29. kube-proxy

전통적인 Kubernetes에서는 각 Node의 **kube-proxy**가 Service와 EndpointSlice 정보를 관찰하고 Service Traffic을 Backend로 전달하기 위한 Data Plane Rule을 구성한다.

```text
Service
   │
   ▼
kube-proxy가 Data Plane Rule 구성
   │
   ▼
Backend Pods
```

kube-proxy가 모든 Packet을 User-space Proxy처럼 직접 받아서 전달한다고만 생각하면 정확하지 않다.

환경에 따라 Linux Network Data Plane을 구성해 Packet이 전달되도록 한다.

또 kube-proxy는 Kubernetes에서 유일한 Service Proxy 구현은 아니다.

예를 들어 일부 CNI 구현체는 자체 Service Proxy 기능으로 kube-proxy 기능을 대체할 수 있다.

따라서,

```text
"Kubernetes Service는 반드시 kube-proxy가 있어야만 동작한다."
```

라고 절대적으로 외우는 것은 적절하지 않다.

---

# 30. CoreDNS와 Service Discovery

Kubernetes에서 Application이 매번 Service ClusterIP를 직접 기억할 필요는 없다.

**CoreDNS**를 이용해 Service Name을 IP로 Resolution할 수 있다.

예를 들어 다음 FQDN을 사용할 수 있다.

```text
my-service.my-namespace.svc.cluster.local
```

구조는 다음과 같다.

```text
<Service Name>.<Namespace>.svc.<Cluster Domain>
```

같은 Namespace의 Pod에서는 상황에 따라 짧은 Service Name만으로도 접근할 수 있다.

```text
my-service
```

이를 **Service Discovery**라고 한다.

### 시험에서 구분

```text
CoreDNS
→ Name Resolution / Service Discovery

CNI
→ Pod Network

kube-proxy 또는 대체 Data Plane
→ Service Traffic Forwarding
```

---

# 31. Ingress

Ingress는 Cluster 외부에서 들어오는 **HTTP/HTTPS Traffic을 Host 또는 Path Rule에 따라 Service로 Routing**하는 API이다.

예를 들어 다음 구조를 만들 수 있다.

```text
example.com/api
        ↓
   API Service

example.com/web
        ↓
   Web Service
```

Ingress Resource만 생성한다고 실제 Traffic 처리가 자동으로 이루어지는 것은 아니다.

**Ingress Controller**가 필요하다.

```text
Ingress Resource
→ Routing Rule

Ingress Controller
→ Rule을 실제 Traffic 처리 설정으로 구현
```

대표적으로 nginx 계열 Controller나 Traefik 등이 있다.

---

# 32. 현재 Kubernetes에서는 Gateway API도 알아두기

현재 Kubernetes 공식 문서에서는 **새로운 기능이 필요한 경우 Ingress보다 Gateway API 사용을 권장**하고 있으며 Ingress API 자체는 Frozen 상태이다.

Ingress가 제거되는 것은 아니지만 새로운 기능 개발은 Gateway API를 중심으로 진행된다.

```text
Ingress
→ 기존 HTTP/HTTPS Routing API
→ Stable이지만 API 자체는 Frozen

Gateway API
→ 보다 확장된 Traffic Routing API
→ 현재 Kubernetes가 권장하는 방향
```

현재 KCNA 공식 Competency에서 Gateway API라는 이름이 직접 명시되어 있지는 않으므로 상세 Resource 구조까지 외울 필요는 없다.

다만 **Ingress가 External HTTP/HTTPS Routing이고 현재 Kubernetes에서는 Gateway API가 후속 방향이라는 정도**는 알아두면 좋다.

지금까지의 Networking을 하나로 연결하면 다음과 같다.

```text
External Client
      │
      ▼
Ingress / Gateway / LoadBalancer
      │
      ▼
Service
      │
      │ EndpointSlice
      ▼
Pod
      │
      └── Pod IP / Network
             ↑
             CNI
```

# 34. Storage: Ephemeral vs Persistent

Container나 Pod의 Local Data만 사용하면 Workload가 교체될 때 데이터를 유지하기 어렵다.

Storage는 크게 **Ephemeral Storage**와 **Persistent Storage**로 구분해서 이해할 수 있다.

## Ephemeral Volume

Pod Lifecycle과 함께 사용하는 Temporary Storage이다.

대표적인 예가 `emptyDir`이다.

```text
Pod 생성
   ↓
emptyDir 생성
   ↓
Containers가 사용
   ↓
Pod 삭제
   ↓
emptyDir Data 삭제
```

주의할 점은 **Container Restart와 Pod 삭제를 구분해야 한다는 것**이다.

`emptyDir`은 Container 하나가 Restart한다고 바로 사라지는 것이 아니라 **Pod가 존재하는 동안 유지**된다.

Pod 자체가 Node에서 제거되면 `emptyDir` 데이터도 사라진다.

이건 시험에서 헷갈릴 수 있는 부분이다.

---

# 35. Persistent Storage

Database처럼 Pod가 교체되어도 데이터를 유지해야 하는 Workload에는 Persistent Storage가 필요하다.

Kubernetes에서는 대표적으로 다음 Resource를 사용한다.

```text
PersistentVolume
PersistentVolumeClaim
StorageClass
CSI
```

---

# 36. PersistentVolume(PV)

**PersistentVolume(PV)​**은 Cluster에 제공된 Storage Resource이다.

Pod Lifecycle과 독립적으로 존재한다.

PV는 관리자가 미리 만들 수도 있고 Dynamic Provisioning으로 자동 생성될 수도 있다.

여기서 이전 Namespace 글과 연결할 부분이 있다.

**PV는 Cluster-Scoped Resource**이다.

---

# 37. PersistentVolumeClaim(PVC)

PVC는 사용자가 필요한 Storage를 요청하는 Resource이다.

```text
"10Gi Storage가 필요하다."
"ReadWriteOnce가 필요하다."
"특정 StorageClass를 사용하고 싶다."
```

와 같은 요구사항을 표현한다.

PVC는 **Namespaced Resource**이다.

즉,

```text
PV
→ Cluster Scoped

PVC
→ Namespace Scoped
```

라는 차이도 알아두면 좋다.

---

# 38. PV와 PVC 관계

기본 흐름은 다음과 같다.

```text
Pod
 │
 ▼
PVC
 │
 │ Binding
 ▼
PV
 │
 ▼
Actual Storage
```

사용자는 실제 Storage Backend를 직접 Pod에 연결하기보다 PVC를 통해 Storage를 요청한다.

---

# 39. StorageClass

**StorageClass**는 Cluster에서 제공하는 Storage Class와 Dynamic Provisioning 방식을 정의한다.

예를 들어 다음과 같은 Storage Class를 제공할 수 있다.

```text
fast-ssd
standard
archive
```

StorageClass에는 Provisioner와 Parameter, Reclaim Policy 등의 정보가 들어갈 수 있다.

StorageClass 역시 **Cluster-Scoped Resource**이다.

```text
PV
→ Cluster Scoped

StorageClass
→ Cluster Scoped

PVC
→ Namespace Scoped
```

---

# 40. Static Provisioning vs Dynamic Provisioning

## Static Provisioning

관리자가 PV를 미리 생성한다.

```text
Administrator
      ↓
PV 생성
      ↓
PVC 요청
      ↓
Matching PV와 Binding
```

## Dynamic Provisioning

PVC가 생성되면 StorageClass와 Provisioner에 따라 필요한 PV가 자동으로 생성된다.

```text
PVC
 ↓
StorageClass
 ↓
CSI Provisioner
 ↓
Storage 생성
 ↓
PV 자동 생성
 ↓
PVC와 Binding
```

Cloud Native 환경에서는 Dynamic Provisioning이 많이 사용된다.

---

# 41. CSI

**CSI(Container Storage Interface)​**는 Kubernetes와 외부 Storage System 사이의 표준 Interface이다.

```text
Kubernetes
    │
    │ CSI
    ▼
Storage Driver
    │
    ├── AWS EBS
    ├── Ceph
    ├── Storage Vendor
    └── 기타 Backend
```

CSI를 이용하면 Kubernetes Core가 모든 Storage Vendor의 코드를 직접 포함할 필요가 없다.

각 Storage Vendor가 CSI Driver를 제공하면 Kubernetes가 표준 Interface를 통해 Storage를 사용할 수 있다.

---

# 42. Storage Access Modes

PV/PVC를 공부하면서 Access Mode도 알아두면 좋다.

대표적인 Access Mode는 다음과 같다.

| 약어 | Full Name | 의미 |
|---|---|---|
| RWO | ReadWriteOnce | 하나의 Node에서 Read/Write Mount |
| ROX | ReadOnlyMany | 여러 Node에서 Read-only Mount |
| RWX | ReadWriteMany | 여러 Node에서 Read/Write Mount |
| RWOP | ReadWriteOncePod | Cluster 전체에서 하나의 Pod만 Read/Write |

특히 **RWO를 하나의 Pod만 사용할 수 있다는 뜻으로 외우면 안 된다.**

`ReadWriteOnce`는 기본적으로 **하나의 Node에서 Read/Write**라는 의미이므로 같은 Node의 여러 Pod가 해당 Volume을 사용할 수 있는 상황도 있다.

정말 Single Pod Writer가 필요하다면 `ReadWriteOncePod`가 별도로 존재한다.

이 부분은 객관식에서 상당히 헷갈릴 수 있다.

---

# 43. Reclaim Policy

PVC와의 사용이 끝난 뒤 PV 및 실제 Storage를 어떻게 처리할지를 **Reclaim Policy**가 결정한다.

현재 중요한 값은 `Delete`와 `Retain`이다.

## Delete

PV와 연결된 Storage Asset을 삭제한다.

Dynamic Provisioning된 Volume에서 자주 사용된다.

## Retain

PVC가 삭제되어도 PV와 Data를 남기고 관리자가 수동으로 처리하도록 한다.

```text
Delete
→ Storage 제거

Retain
→ Data 보존 / Manual Reclamation 필요
```

중요한 Data를 보존해야 한다면 Retain이 적절할 수 있다.

---

# 44. StorageClass의 기본 Reclaim Policy

Dynamic Provisioning에서 StorageClass가 `reclaimPolicy`를 정의할 수 있다.

StorageClass에서 별도 Reclaim Policy를 지정하지 않으면 **Dynamic Provisioning된 PV의 기본은 Delete**이다.

이 부분은 `PV의 기본값`과 `StorageClass Dynamic Provisioning 기본값`을 섞어서 외우지 않는 것이 좋다.

시험에서는 상황을 정확히 읽어야 한다.

---

# 45. volumeBindingMode

StorageClass에는 Volume을 언제 Provisioning/Binding할지 결정하는 `volumeBindingMode`가 있다.

대표적인 값은 다음과 같다.

| Mode | 의미 |
|---|---|
| Immediate | PVC가 생성되면 바로 Provisioning / Binding |
| WaitForFirstConsumer | 해당 PVC를 사용하는 Pod의 Scheduling 정보를 고려한 뒤 처리 |

`WaitForFirstConsumer`는 Storage가 Zone 등 Topology Constraint를 가지는 환경에서 특히 중요하다.

```text
PVC
   │
   ▼
Pod 생성
   │
   ▼
Scheduler가 Node / Zone 조건 확인
   │
   ▼
적절한 Storage Provisioning
```

이렇게 하면 Storage가 특정 Zone에 만들어졌는데 Pod가 다른 Zone으로 Scheduling되어 사용하지 못하는 상황을 줄일 수 있다.

KCNA에서는 YAML을 외울 필요는 없지만 **Storage Scheduling과 Topology가 연결될 수 있다는 점**은 알아두면 좋다.

---

# 47. Troubleshooting: 현재 KCNA에서 반드시 보강해야 하는 영역

기존 22% Curriculum 자료에서 가장 부족한 부분이다.

현재 공식 KCNA Container Orchestration Competency에는 **Troubleshooting**이 명시되어 있으므로 시험 대비를 위해 반드시 알아둬야 한다.

KCNA는 CKA처럼 Terminal에서 직접 문제를 고치는 실기 시험은 아니다.

따라서 다음과 같은 Scenario를 보고 **어느 Layer에서 문제가 발생했는지 판단하는 능력**이 중요하다.

```text
Pod 문제인가?
Scheduling 문제인가?
Image 문제인가?
Network 문제인가?
DNS 문제인가?
Service Selector 문제인가?
Storage 문제인가?
Permission 문제인가?
```

---

# 48. Troubleshooting의 기본 사고 순서

문제가 발생하면 Kubernetes 전체 Layer를 순서대로 나누면 이해하기 쉽다.

```text
Application
   ↓
Container
   ↓
Pod
   ↓
Scheduling / Node
   ↓
Service / DNS / Network
   ↓
Storage
   ↓
Control Plane
```

예를 들어 `Service에 접속이 안 된다`고 해서 바로 CNI 장애라고 결론 내리면 안 된다.

먼저 다음을 확인할 수 있다.

```text
Pod가 Running인가?
   ↓
Application이 올바른 Port를 Listen하는가?
   ↓
Service가 존재하는가?
   ↓
Service Selector가 Pod Label과 맞는가?
   ↓
EndpointSlice에 Backend가 있는가?
   ↓
Service Port / targetPort가 맞는가?
   ↓
DNS Resolution은 되는가?
   ↓
NetworkPolicy가 막고 있지 않은가?
```

---

# 49. Pod가 Pending인 경우

`Pending` 상태는 Container가 Crash했다는 뜻이 아니다.

Pod가 아직 Scheduling되지 못한 경우일 수 있다.

대표적인 원인은 다음과 같다.

- CPU / Memory 부족
- Node Selector 불일치
- Required Affinity 불일치
- Taint / Toleration 문제
- PVC / Volume Scheduling 문제
- Node가 Scheduling 불가능한 상태

따라서,

```text
Pending
→ 먼저 Scheduling 문제 가능성을 생각
```

하면 된다.

---

# 50. ImagePullBackOff / ErrImagePull

다음 상태는 Container Image를 가져오는 과정과 관련된다.

```text
ErrImagePull
ImagePullBackOff
```

대표적인 원인은 다음과 같다.

- 잘못된 Image Name
- 존재하지 않는 Tag
- Registry 접근 불가
- Private Registry 인증 실패
- `imagePullSecrets` 문제

즉,

```text
Pending
→ Scheduling 가능성

ImagePullBackOff
→ Image Pull 가능성
```

으로 우선 구분한다.

---

# 51. CrashLoopBackOff

`CrashLoopBackOff`는 Container가 실행된 뒤 반복적으로 종료되고 Kubernetes가 Restart를 반복하면서 Backoff하고 있는 상태이다.

대표적으로 다음 원인을 생각할 수 있다.

- Application Startup Failure
- 잘못된 Command / Arguments
- 필요한 Configuration 누락
- Dependency 연결 실패
- Probe 실패
- Application 자체 Error

따라서 `ImagePullBackOff`와 다르다.

```text
ImagePullBackOff
→ Container 시작 전 Image를 가져오는 데 실패

CrashLoopBackOff
→ Container가 실행되지만 반복적으로 종료
```

---

# 52. kubectl describe와 Events

Troubleshooting에서 가장 먼저 상태를 확인할 때 자주 사용하는 명령이 있다.

```bash
kubectl describe pod <pod>
```

`describe`에서는 Resource 상태뿐 아니라 **Events**를 확인할 수 있다.

예를 들어 다음 문제의 단서를 찾을 수 있다.

- FailedScheduling
- FailedMount
- Image Pull Error
- Probe Failure
- Container Restart

KCNA는 실기 시험이 아니므로 명령어 Option을 세세하게 암기할 필요는 없지만 **Events가 문제 원인을 파악하는 중요한 정보**라는 정도는 알아두면 좋다.

---

# 53. kubectl logs

Container가 실행되었지만 Application Error로 종료한다면 Log가 중요한 단서가 된다.

```bash
kubectl logs <pod>
```

Multi-container Pod라면 어떤 Container의 Log인지 구분해야 할 수 있다.

CrashLoopBackOff처럼 이전 Container Instance의 Log가 필요한 상황도 있다.

KCNA에서는 `logs = Application/Container Log 확인` 정도의 목적을 이해하면 충분하다.

---

# 54. Service가 동작하지 않을 때

Service Troubleshooting은 여러 Layer를 순서대로 확인해야 한다.

대표적인 흐름은 다음과 같다.

```text
1. Backend Pod Running?
2. Application Port 정상?
3. Service 존재?
4. Selector와 Pod Label 일치?
5. EndpointSlice 존재?
6. Service port / targetPort 정상?
7. DNS 정상?
8. NetworkPolicy 차단 여부?
```

특히 **Service Selector와 Pod Label 불일치**는 매우 중요한 기본 문제이다.

```text
Service

selector:
  app=web
        │
        ▼
Pod

label:
  app=api
```

이 경우 Service가 Backend Pod를 선택하지 못한다.

따라서 EndpointSlice가 비어 있을 수 있다.

---

# 55. EndpointSlice

Service의 Backend Endpoint 정보는 현대 Kubernetes에서 **EndpointSlice** Resource를 통해 관리된다.

Service Selector와 일치하는 Ready Pod들이 Backend Endpoint로 연결될 수 있다.

따라서,

```text
Service는 존재하지만 접속이 안 됨
+
EndpointSlice에 Endpoint 없음
```

이라면 다음을 의심할 수 있다.

```text
Service Selector와 Pod Label 불일치
Pod가 Ready하지 않음
Backend Pod 자체가 없음
```

---

# 56. DNS Troubleshooting

Service Name으로 접근이 안 된다면 DNS 문제인지 Service 자체 문제인지 구분해야 한다.

예를 들어 다음 이름을 Resolution할 수 있다.

```text
service-name.namespace.svc.cluster.local
```

같은 Namespace에서는 Short Name으로도 접근할 수 있다.

DNS가 문제인지 확인하려면 개념적으로 다음을 본다.

```text
CoreDNS Pod가 Running인가?
        ↓
DNS Service가 존재하는가?
        ↓
DNS EndpointSlice가 있는가?
        ↓
Pod의 /etc/resolv.conf가 정상인가?
```

KCNA에서는 Command를 깊게 외우기보다 **CoreDNS = Cluster DNS / Service Discovery**라는 역할을 확실히 구분하면 된다.

---

# 57. PVC가 Pending인 경우

PVC가 `Pending`이라면 Storage Binding 또는 Provisioning 문제를 생각할 수 있다.

대표적인 원인은 다음과 같다.

- Matching PV가 없음
- StorageClass가 없음
- Default StorageClass가 없음
- CSI Provisioner 문제
- Capacity / AccessMode 불일치
- Topology Constraint
- `WaitForFirstConsumer`로 Pod Scheduling을 기다리는 정상 상태

특히 마지막은 중요하다.

`WaitForFirstConsumer`를 사용하는 PVC가 바로 Bound되지 않는다고 해서 반드시 장애인 것은 아니다.

Pod Scheduling 시점까지 Binding을 기다리는 설계일 수 있다.

---

# 58. Troubleshooting 상태별 빠른 연결

| 증상 | 먼저 생각할 영역 |
|---|---|
| Pod `Pending` | Scheduling / Resource / PVC |
| `ImagePullBackOff` | Image / Registry |
| `CrashLoopBackOff` | Application / Configuration / Probe |
| Service 연결 안 됨 | Selector / EndpointSlice / Port |
| Service Name Resolution 실패 | CoreDNS |
| 특정 Pod 간 통신만 실패 | NetworkPolicy / CNI |
| PVC `Pending` | PV / StorageClass / CSI / Topology |
| `Forbidden` API Error | RBAC / Authorization |
| Pod Security Violation | PSA / PSS / SecurityContext |

이런 식으로 **Error → Layer**를 연결하는 연습이 현재 KCNA Troubleshooting 대비에 특히 중요하다.

# 59. Service Mesh

Service Mesh는 현재 KCNA Container Orchestration 공식 Competency에 별도로 명시되어 있지는 않지만 기존 KCNA 자료와 Cloud Native Networking을 이해하는 데 도움이 되기 때문에 함께 정리한다.

Microservice가 많아지면 Service 간 통신에서 반복되는 요구사항이 생긴다.

- Retry
- Timeout
- mTLS
- Authentication
- Traffic Routing
- Metrics
- Distributed Tracing

이 기능을 각 Application Code에 각각 구현하면 관리가 복잡해진다.

Service Mesh는 이러한 **Service-to-Service Communication 기능을 Application Code 밖의 Infrastructure Layer에서 처리**하는 접근 방식이다.

---

# 60. Service Mesh의 Data Plane과 Control Plane

전통적인 Service Mesh에서는 Proxy를 각 Workload 옆에 배치하는 Sidecar Pattern을 많이 사용했다.

```text
Pod A
├── App
└── Proxy

        │
        │ Service-to-Service Traffic
        ▼

Pod B
├── Proxy
└── App
```

Proxy들이 실제 Traffic을 처리하는 영역을 **Data Plane**이라고 한다.

이 Proxy의 Policy와 Configuration을 관리하는 영역을 **Control Plane**이라고 한다.

```text
Service Mesh

├── Control Plane
│   └── Policy / Configuration 관리
│
└── Data Plane
    └── 실제 Service Traffic 처리
```

대표적인 Service Mesh에는 Istio와 Linkerd가 있다.

---

# 61. Service Mesh에서 얻는 것

대표적인 기능을 세 가지로 묶을 수 있다.

## mTLS

Service 간 Traffic을 암호화하고 상호 인증할 수 있다.

## Traffic Management

Retry, Timeout, Traffic Splitting, Canary Routing 등을 Infrastructure Layer에서 관리할 수 있다.

## Observability

Service 간 Request Metric이나 Trace를 수집하는 데 도움을 줄 수 있다.

따라서 Service Mesh를 한 문장으로 정리하면 다음과 같다.

> **Microservice 간 통신에 필요한 Security, Traffic Management, Observability 기능을 Application Code 밖의 Infrastructure Layer에서 제공하는 방식**

다만 현대 Service Mesh가 항상 Sidecar만 사용하는 것은 아니다.

예를 들어 Istio에는 Sidecar 외 다른 Data Plane Architecture도 존재하므로,

```text
Service Mesh = 무조건 Sidecar
```

로 절대적으로 외우지는 않는 것이 좋다.

KCNA에서는 **전통적인 Sidecar Proxy 개념을 이해하는 수준**이면 충분하다.

# 64. KCNA 시험에서 특히 주의할 문장

### `CRI is responsible for Pod networking.`

**X**

CRI는 Container Runtime Interface이다. Networking은 CNI이다.

### `CSI provides a standard interface for storage integration.`

**O**

### `runc and containerd perform exactly the same role.`

**X**

추상화 Level과 역할이 다르다.

### `Removing dockershim means Docker-built images cannot run on Kubernetes.`

**X**

OCI-compatible Image는 containerd 등의 Runtime에서 실행할 수 있다.

### `A Role is cluster-scoped.`

**X**

Role은 Namespaced Resource이다.

### `A RoleBinding can reference a ClusterRole.`

**O**

다만 Permission Scope는 해당 RoleBinding의 Namespace에 제한된다.

### `A ClusterRoleBinding grants permissions cluster-wide.`

**O**

### `A ServiceAccount represents workload identity.`

**O**

### `NetworkPolicy works even when the CNI does not support enforcement.`

**X**

지원되는 Network Plugin이 필요하다.

### `Once an ingress NetworkPolicy selects a Pod, egress is automatically denied as well.`

**X**

Ingress와 Egress Isolation은 방향별로 구분해야 한다.

### `NetworkPolicies are additive.`

**O**

### `Restricted is the most permissive Pod Security Standard.`

**X**

Restricted는 가장 엄격하다.

### `Pod Security Admission can enforce Pod Security Standards.`

**O**

### `Ingress works without an Ingress Controller.`

**X**

실제 구현 Controller가 필요하다.

### `Ingress is a Service type.`

**X**

Ingress는 별도의 API Resource이다.

### `CoreDNS provides Kubernetes service discovery.`

**O**

### `RWO means only one Pod in the entire cluster can use the volume.`

**X**

RWO는 기본적으로 하나의 Node에서 Read/Write Mount이다. 하나의 Pod만 허용하려면 RWOP를 구분한다.

### `PVC is the user's request for persistent storage.`

**O**

### `StorageClass can be used for dynamic provisioning.`

**O**

### `WaitForFirstConsumer can delay volume provisioning or binding until Pod scheduling information is available.`

**O**

### `A Pending PVC always means storage provisioning has failed.`

**X**

`WaitForFirstConsumer`를 사용한다면 Pod Consumer를 기다리고 있을 수도 있다.

### `ImagePullBackOff usually points to a scheduling resource shortage.`

**X**

Image Pull 문제와 연결된다.

### `CrashLoopBackOff means Kubernetes cannot download the image.`

**X**

Container가 시작된 뒤 반복적으로 Crash하는 상황과 연결된다.

# 65. 실제 KCNA 문제에 대해서

KCNA 시험은 Linux Foundation의 Certification Confidentiality Agreement가 적용되는 시험이다.

공식 KCNA 페이지에서는 Curriculum과 시험 구조는 공개하지만 **실제 Live Exam Question Bank는 공개하지 않는다.**

인터넷에는 `Actual KCNA Questions`, `Exam Dumps`라고 주장하는 사이트가 존재하지만, 해당 문제가 실제 Linux Foundation 문항인지 공식적으로 검증할 수 없고 시험 기밀 자료를 재배포한다고 주장하는 경우도 있다.

따라서 이 글에서는 그런 문제를 **실제 시험 문제라고 인용하지 않는다.**

또 내가 임의로 만든 문제를 `실제 출제 문제`라고 표시하지도 않는다.

대신 실제 응시자가 공개적으로 작성한 후기에서 확인되는 **출제 주제** 정도만 참고한다.

2026년 5월 실제 KCNA 응시 후기를 보면 CKA 이후 KCNA를 응시한 사용자가 Kubernetes 기본 내용 외에 **Prometheus, Open Source Storage, Helm** 관련 문제가 있었다고 공개적으로 언급했다.

다만 실제 문제 문장이나 선택지는 공개하지 않았기 때문에 이를 그대로 `실제 시험 문제`라고 재현할 수는 없다.

즉 시험 문제에 대해서는 다음 기준으로 본다.

```text
Linux Foundation 공식 Curriculum
→ 시험 범위 판단의 기준

Kubernetes 공식 문서
→ 기술 내용 검증

실제 응시자 공개 후기
→ 어떤 Topic이 등장했는지 참고

Exam Dump
→ 공식 검증이 불가능하므로 실제 문제라고 사용하지 않음
```

# 68. 전체 구조로 다시 연결하기

이번 Container Orchestration 영역은 다음처럼 하나의 구조로 연결하면 이해하기 쉽다.

```text
                         Kubernetes
                              │
        ┌─────────────────────┼─────────────────────┐
        │                     │                     │
     Security              Networking             Storage
        │                     │                     │
        ├── RBAC              ├── CNI              ├── PV
        ├── ServiceAccount    ├── Service          ├── PVC
        ├── NetworkPolicy     ├── EndpointSlice    ├── StorageClass
        ├── SecurityContext   ├── CoreDNS          └── CSI
        ├── PSS               └── Ingress/Gateway
        └── PSA
                              │
                              │
                       Troubleshooting
                              │
             ┌────────────────┼────────────────┐
             │                │                │
          Pending      ImagePullBackOff  CrashLoopBackOff
             │                │                │
        Scheduling          Image         Application
```

그 아래 Container 실행 Layer에서는 다음과 같이 연결된다.

# 정리하면서

기존 KCNA 자료에서는 Container Orchestration이 22%이고 Runtime, Security, Networking, Storage, Service Mesh를 중심으로 설명되어 있었지만 현재 Curriculum을 확인해보니 이 영역은 **28%로 비중이 증가했고 Networking, Security, Troubleshooting, Storage가 공식 Competency​**로 지정되어 있었다.

따라서 기존 내용을 그대로 공부하면 특히 Troubleshooting 부분이 부족할 수 있었다.

Container Runtime 부분에서는 kubelet이 직접 Container를 만드는 것이 아니라 CRI를 통해 containerd나 CRI-O 같은 Runtime과 통신하고, Runtime이 runc 같은 저수준 Runtime을 이용해 실제 Container Process를 실행한다는 구조를 다시 연결했다.

```text
kubelet
→ CRI
→ containerd / CRI-O
→ runc
→ Container
```

그리고 CRI, CNI, CSI는 모두 Kubernetes가 특정 구현에 강하게 종속되지 않도록 만드는 표준 Interface라는 공통점이 있지만 각각 Runtime, Networking, Storage라는 서로 다른 영역을 담당한다.

Security에서는 RBAC의 네 Resource를 단순히 이름만 외우는 것보다 Scope를 구분하는 것이 중요했다. 특히 **RoleBinding이 ClusterRole을 참조할 수도 있지만 그 경우에도 권한은 RoleBinding이 존재하는 Namespace에 한정된다**는 부분이 헷갈리기 쉬웠다.

NetworkPolicy 역시 단순히 `Policy가 생기면 모든 Traffic이 Default Deny`라고 외우기보다 **Ingress와 Egress Isolation을 각각 따로 판단해야 하고 여러 Policy의 Allow Rule이 Additive하게 적용된다**는 점을 알아야 했다.

Pod Security에서는 SecurityContext, Pod Security Standards, Pod Security Admission을 서로 구분해야 한다.

```text
SecurityContext
→ Pod / Container의 Runtime Security Setting

Pod Security Standards
→ Privileged / Baseline / Restricted

Pod Security Admission
→ PSS를 실제 Admission 단계에서 적용
```

Networking에서는 CNI가 Pod Network를 구현하고, Service가 변하는 Pod 앞에 Stable Endpoint를 제공하며, EndpointSlice가 Backend 정보를 관리하고, CoreDNS가 Service Discovery를 담당한다는 전체 흐름으로 이해하는 것이 중요했다.

```text
CNI
→ Pod Network

Service
→ Stable Endpoint

EndpointSlice
→ Backend Endpoint

CoreDNS
→ Service Discovery

Ingress / Gateway
→ External HTTP Routing
```

Service Type도 `ClusterIP ⊂ NodePort ⊂ LoadBalancer`라고 무조건 외우기보다 각각 **Cluster 내부 접근, Node Port Exposure, External Load Balancer Integration​**이라는 목적을 먼저 이해하는 것이 더 정확했다.

Storage에서는 PV, PVC, StorageClass, CSI의 관계가 핵심이었다.

```text
PV
→ 실제 Storage Resource

PVC
→ 사용자의 Storage Request

StorageClass
→ Dynamic Provisioning 기준

CSI
→ Kubernetes와 Storage Backend 사이 Interface
```

여기에 RWO가 `하나의 Pod`가 아니라 기본적으로 **하나의 Node에서 Read/Write Mount**를 뜻하고, 정말 하나의 Pod만 허용하려면 RWOP가 있다는 차이도 헷갈리지 않아야 한다.

현재 Curriculum에서 새롭게 특히 신경 써야 할 부분은 Troubleshooting이었다.

```text
Pending
→ Scheduling / Resource / PVC 확인

ImagePullBackOff
→ Image / Registry 확인

CrashLoopBackOff
→ Application / Configuration / Probe 확인

Service 연결 실패
→ Selector / EndpointSlice / Port / DNS 확인

PVC Pending
→ PV / StorageClass / CSI / Topology 확인

Forbidden
→ RBAC 확인
```

KCNA는 CKA처럼 직접 Cluster를 고치는 실기 시험은 아니기 때문에 명령어 자체보다 **문제 상황을 보고 어느 Layer의 문제인지 분류하는 능력**이 중요하다고 생각한다.

마지막으로 Service Mesh는 현재 Container Orchestration의 공식 Competency 이름에는 포함되어 있지 않지만, Microservice Networking을 이해하기 위한 보충 개념으로 남겨두었다. Service Mesh는 Service 간 Communication의 mTLS, Traffic Management, Observability 등을 Application Code 밖의 Infrastructure Layer에서 처리하는 접근 방식이며 Istio와 Linkerd 같은 Project가 대표적이다.

결국 이번 영역에서 가장 중요하게 기억할 것은 다음 구조다.

```text
Runtime
→ CRI

Network
→ CNI

Storage
→ CSI

Permission
→ RBAC

Workload Identity
→ ServiceAccount

Network Isolation
→ NetworkPolicy

Pod Security
→ SecurityContext + PSS + PSA

Service Discovery
→ CoreDNS

Persistent Storage
→ PVC + PV + StorageClass + CSI

Troubleshooting
→ Error/State를 보고 문제 Layer를 구분
```

이렇게 각 기술을 **무엇을 해결하는 기술인지** 기준으로 연결해두면 KCNA의 비슷한 선택지 사이에서도 훨씬 구분하기 쉬울 것 같다.
