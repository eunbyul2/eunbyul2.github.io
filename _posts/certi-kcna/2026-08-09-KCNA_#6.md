# KCNA #6 — Observability: Metrics, Logs, Traces, Prometheus, OpenTelemetry와 FinOps

수십 개의 Pod가 여러 Node에 흩어져 서로를 호출하는 Cloud Native 환경에서는 장애가 발생했을 때 단일 로그 파일 하나만 확인해서는 원인을 찾기 어렵다.

한 Request가 API Gateway, 인증 서비스, 주문 서비스, 결제 서비스, Database를 차례로 거칠 수 있고, Pod는 언제든 재시작되거나 다른 Node에 다시 생성될 수 있다. HPA에 의해 Replica 수가 계속 변할 수도 있다.

이런 환경에서는 시스템이 자신의 상태를 **Metrics, Logs, Traces 같은 Telemetry로 외부에 드러낼 수 있어야 한다.** 이 능력이 바로 **Observability**이다.

다만 기존 KCNA 자료를 볼 때 한 가지 중요한 변경 사항이 있다. 기존 시험에서는 `Cloud Native Observability`가 별도의 **8% Domain**이었지만, 현재 KCNA에서는 독립 Domain이 아니다. 2025년 11월 24일 이후 적용된 시험에서는 Observability가 **Cloud Native Architecture 12%** 안으로 통합되었다.

현재 시험 구조는 다음과 같다.

| Domain | 비중 |
| --- | ---: |
| Kubernetes Fundamentals | 44% |
| Container Orchestration | 28% |
| Cloud Native Application Delivery | 16% |
| **Cloud Native Architecture** | **12%** |

Cloud Native Architecture의 현재 공식 Competency는 다음 세 가지이다.

```text
Cloud Native Architecture 12%
├── Observability
├── Cloud Native Ecosystem and Principles
└── Cloud Native Community and Collaboration
```

따라서 이 글에서 다루는 Observability는 여전히 KCNA의 핵심 시험 범위이지만, **예전처럼 독립 8% Domain이라고 외우면 안 된다.**

또한 기존 자료의 FinOps, OpenCost 같은 내용은 Cloud Native 운영을 이해하는 데 유용하지만, 현재 공식 Competency에 `Cost Management` 또는 `FinOps`가 별도 항목으로 명시되어 있지는 않다. 따라서 시험 우선순위는 **Metrics / Logs / Traces, Prometheus, OpenTelemetry, Monitoring과 Observability의 차이**를 먼저 잡고, FinOps는 보충 개념으로 보는 것이 안전하다.

---

## 1. Monitoring과 Observability

시험에서 가장 먼저 구분해야 하는 개념이 Monitoring과 Observability이다.

### Monitoring

Monitoring은 **미리 정의해 둔 Metric, Condition, Threshold를 지속적으로 확인하는 활동**이다.

예를 들어 다음과 같은 질문을 다룬다.

```text
CPU 사용률이 80%를 넘었는가?
Pod가 Down 되었는가?
HTTP 5xx Error가 증가했는가?
Memory 사용량이 임계값을 넘었는가?
```

즉 어떤 지표를 확인할지 이미 알고 있고, 그 상태가 정상 범위를 벗어났는지 감시한다.

### Observability

Observability는 시스템이 외부로 내보내는 Telemetry를 이용해 **시스템 내부 상태를 이해할 수 있는 능력**이다.

예를 들어 다음과 같은 질문이다.

```text
왜 특정 사용자의 결제 요청만 느린가?
어느 Microservice에서 Latency가 발생했는가?
왜 특정 Node에 있는 Pod에서만 Error가 증가했는가?
새 Version 배포 이후 어떤 요청 경로에서 문제가 생겼는가?
```

미리 Dashboard에 만들어 놓지 않은 질문도 Telemetry를 조합하여 분석할 수 있어야 한다.

```text
Monitoring
→ 이미 알고 있는 상태와 문제를 지속적으로 확인

Observability
→ Telemetry를 이용해 시스템 내부 상태와 예상하지 못한 문제까지 분석
```

Monitoring은 Observability를 구현하는 중요한 활동 중 하나라고 이해하면 된다.

> **KCNA 시험 포인트**
>
> `CPU > 80%인지 감시한다` → Monitoring  
> `왜 특정 Request가 느린지 여러 Signal을 이용해 원인을 찾는다` → Observability

## 2. Telemetry란 무엇인가

Telemetry는 **시스템이 자신의 상태와 동작에 관한 정보를 외부로 내보내는 데이터**를 의미한다.

Cloud Native Observability에서는 전통적으로 다음 세 가지 Signal을 가장 중요하게 다룬다.

```text
Metrics
Logs
Traces
```

최근 OpenTelemetry에서는 Profiles도 새로운 Signal로 발전하고 있지만, 현재 KCNA 수준에서는 **Metrics / Logs / Traces 세 가지를 우선 확실히 구분하는 것**이 중요하다.

## 3. Metrics, Logs, Traces

### Metrics

Metrics는 시스템의 상태를 **숫자로 측정한 데이터**이다. 시간에 따라 지속적으로 기록되므로 일반적으로 Time-Series 형태로 다룬다.

예를 들면 다음과 같다.

- CPU Usage
- Memory Usage
- Request Count
- Request Rate
- Error Rate
- Request Latency
- Queue Length

```text
10:00 → CPU 30%
10:01 → CPU 42%
10:02 → CPU 65%
10:03 → CPU 87%
```

Metrics는 `얼마나 많은가`, `얼마나 빠른가`, `시간에 따라 어떻게 변하는가` 같은 질문에 적합하다. 대량의 상태를 집계하고 Dashboard나 Alert에 사용하기 좋지만, 개별 사건의 상세 Context를 모두 담지는 않는다.

대표적인 도구는 **Prometheus**이다.

### Logs

Logs는 **특정 시점에 발생한 Event의 기록**이다.

```text
2026-08-09T10:00:00Z ERROR database connection timeout
```

로그에는 Timestamp, Log Level, Error Message, Request ID, Pod/Container 정보, Stack Trace 같은 상세 Context가 들어갈 수 있다.

Metrics에서 Error Rate가 증가했다는 사실을 발견했다면 Logs를 이용해 **실제로 어떤 Error가 발생했는지** 확인할 수 있다.

대표적인 수집 도구로 Fluentd, Fluent Bit 등이 있고, 저장·조회 Backend의 예로 Grafana Loki가 있다.

### Traces

Traces는 하나의 Request가 분산 시스템을 지나가는 **전체 처리 경로**를 나타낸다.

```text
Client
  ↓
API Gateway
  ↓
Authentication
  ↓
Order Service
  ↓
Payment Service
  ↓
Database
```

Request 전체 흐름을 **Trace**라고 하고, Trace를 구성하는 각 개별 작업 단위를 **Span**이라고 한다.

```text
Trace
├── Span: API Gateway
├── Span: Authentication
├── Span: Order Service
├── Span: Payment Service
└── Span: Database
```

각 Span에는 시작 시각과 종료 시각, Duration, Attributes, Status 등의 정보가 포함될 수 있다. 이를 통해 어느 Service에서 Latency나 Error가 발생했는지 추적할 수 있다.

대표적인 Distributed Tracing Backend로 **Jaeger**가 있다.

### 세 Signal 비교

| Signal | 핵심 질문 | 대표 예 |
| --- | --- | --- |
| **Metrics** | 얼마나 많은가? 상태가 어떻게 변하는가? | CPU, Error Rate, Latency |
| **Logs** | 정확히 무슨 일이 발생했는가? | Error Message, Stack Trace |
| **Traces** | Request가 어디를 지나갔고 어디서 느려졌는가? | Service A → B → DB |

세 Signal은 경쟁 관계가 아니라 보완 관계이다.

```text
Metrics
   ↓
문제가 발생했다는 사실 확인
   ↓
Traces
   ↓
문제가 발생한 Request 경로와 Service 확인
   ↓
Logs
   ↓
구체적인 Error와 Context 확인
```

## 4. Prometheus

Prometheus는 Cloud Native 환경에서 널리 사용하는 **Metrics Monitoring 및 Alerting 시스템**이며 CNCF Graduated 프로젝트이다.

Prometheus는 다음 역할을 수행한다.

```text
Target 발견
   ↓
Metrics Scrape
   ↓
Time-Series 저장
   ↓
PromQL Query
   ↓
Recording / Alerting Rules
```

Prometheus를 단순히 Dashboard 프로그램으로 이해하면 안 된다. 핵심 역할은 **Metrics를 수집하고 저장하며 Query하고 Alerting Rule을 평가하는 것**이다.

---

## 5. Prometheus의 Pull Model

Prometheus의 대표적인 특징은 **Pull 기반 Metric 수집**이다.

```text
Application / Exporter
        ↑
      Scrape
        ↑
    Prometheus
```

애플리케이션이 Prometheus Server로 Metric을 계속 Push하는 것이 아니라 **Prometheus가 Target의 HTTP Metric Endpoint를 주기적으로 Scrape한다.** 일반적으로 `/metrics` Endpoint가 사용된다.

Kubernetes 환경에서는 Service Discovery를 이용해 Pod, Service 등의 Target을 동적으로 발견할 수 있다.

> **KCNA 시험 포인트**
>
> Prometheus의 기본 수집 모델은 **Pull / Scrape**이다.

### Pushgateway

Prometheus 생태계에는 Pushgateway도 존재한다. 따라서 `Prometheus에서는 Push가 절대 존재하지 않는다`고 외우면 안 된다.

Pushgateway는 특히 **짧게 실행되고 종료되어 Prometheus가 직접 Scrape하기 어려운 Batch Job** 같은 제한적인 경우에 사용할 수 있다.

```text
Short-lived Job
      ↓ push
Pushgateway
      ↑ scrape
Prometheus
```

Job은 Pushgateway로 Metric을 Push하지만, **Prometheus는 Pushgateway를 다시 Pull 방식으로 Scrape한다.**

```text
Prometheus 기본 모델
→ Pull / Scrape

특수한 Short-lived Job
→ Pushgateway 사용 가능

Prometheus
→ Pushgateway 역시 Scrape
```

## 6. Exporter

모든 Application과 System이 Prometheus Format으로 Metric을 직접 제공하는 것은 아니다. 이때 사용하는 것이 **Exporter**이다.

Exporter는 외부 시스템의 상태를 읽어 Prometheus가 Scrape할 수 있는 Metric Format으로 변환한다.

```text
External System
      ↓
   Exporter
      ↓
 /metrics
      ↑
 Prometheus
```

대표적인 예가 **Node Exporter**이다. Linux Node의 CPU, Memory, Disk, Filesystem, Network 같은 System Metric을 노출한다.

> **KCNA 시험 포인트**
>
> Exporter = Prometheus가 직접 Metric을 제공하지 않는 System의 상태를 Prometheus가 Scrape할 수 있게 노출하는 Adapter

## 7. Time-Series와 Label

Prometheus는 Metric을 **Time-Series** 형태로 저장하며 각 Time-Series는 Metric Name과 Label 조합으로 식별된다.

```text
http_requests_total{
  method="GET",
  status="200",
  service="payment"
}
```

Label을 사용하면 같은 Metric을 HTTP Method, Status Code, Service, Pod, Namespace, Region 같은 여러 차원으로 나누어 분석할 수 있다. 이를 **Multi-Dimensional Data Model**이라고 한다.

### Label Cardinality

Label의 값 종류가 지나치게 많으면 Time-Series 수가 급격히 증가할 수 있다. 이를 **High Cardinality** 문제라고 한다.

```text
user_id="1"
user_id="2"
user_id="3"
...
user_id="10000000"
```

각 Label 조합마다 별도의 Time-Series가 만들어질 수 있기 때문이다.

```text
Label
→ Metric을 다양한 차원으로 Query

High Cardinality
→ Time-Series 증가
→ Storage / Memory / Query 비용 증가
```

KCNA에서는 세부 계산보다 Label이 Metric의 차원을 만들고, 과도한 Cardinality가 문제를 일으킬 수 있다는 정도를 이해하면 충분하다.

## 8. PromQL

Prometheus에 저장된 Time-Series는 **PromQL(Prometheus Query Language)**로 Query한다.

예를 들어 누적 Request Counter가 다음과 같다고 하자.

```text
http_requests_total
```

최근 5분 동안 초당 증가율을 구하면 다음처럼 사용할 수 있다.

```promql
rate(http_requests_total[5m])
```

KCNA에서 PromQL 문법을 깊게 외울 필요는 없지만 다음 관계는 알아둔다.

```text
Prometheus
→ Metric 저장

PromQL
→ Prometheus Metric Query
```

## 9. Prometheus Metric Type — 4가지

기존 자료에서는 Prometheus Metric Type을 Counter, Gauge, Histogram **3개**로 정리했지만 이 부분은 수정해야 한다.

Prometheus Client Library에서 주요 Metric Type은 **4개**이다.

```text
Counter
Gauge
Histogram
Summary
```

| Type | 의미 | 대표 예 |
| --- | --- | --- |
| **Counter** | 증가하는 누적값 | 총 Request 수, 총 Error 수 |
| **Gauge** | 증가하거나 감소할 수 있는 현재값 | Memory 사용량, Queue Length |
| **Histogram** | 관측값을 Bucket으로 집계 | Request Latency 분포 |
| **Summary** | Count/Sum과 Client 측 Quantile | Request Latency Quantile |

### Counter

Counter는 일반적으로 누적 증가하는 값이며 Process가 재시작되면 Reset될 수 있다.

```text
http_requests_total
errors_total
processed_jobs_total
```

Counter는 현재 누적값보다 **얼마나 빠르게 증가하는가**가 중요할 때가 많으므로 `rate()` 같은 함수를 사용한다.

### Gauge

Gauge는 값이 자유롭게 증가하거나 감소할 수 있다.

```text
현재 Memory 사용량
현재 Temperature
현재 Queue Length
현재 동시 Connection 수
```

```text
Counter
→ 일반적으로 누적 증가

Gauge
→ 증가 / 감소 가능
```

### Histogram

Histogram은 관측값을 **Bucket** 단위로 집계한다.

```text
<= 0.1 sec
<= 0.3 sec
<= 0.5 sec
<= 1.0 sec
<= +Inf
```

Request Latency 같은 분포를 Bucket에 누적하고 PromQL의 `histogram_quantile()` 등을 이용해 p95, p99 같은 Quantile을 추정할 수 있다.

> **정확한 표현**
>
> Histogram 자체가 p95 값을 직접 저장한다기보다 **Bucket 분포를 저장하고 이를 이용해 Quantile을 계산할 수 있다.**

### Summary

Summary도 Latency나 Size 같은 관측값의 분포를 다루며 일반적으로 Count, Sum, Quantile 정보를 제공할 수 있다.

```text
Histogram
→ Bucket 기반 분포
→ Server 측 집계에 유리

Summary
→ Client 측 Quantile 계산 가능
→ Instance 간 Quantile 단순 집계가 어려움
```

시험용으로는 다음 한 줄이면 충분하다.

```text
Counter   = 누적 증가
Gauge     = 오르내리는 현재값
Histogram = Bucket 기반 분포
Summary   = Client 측 Quantile / Count / Sum
```

## 10. Alerting Rule과 Alertmanager

Prometheus 생태계에서 Alerting은 두 부분으로 나누어 이해한다.

```text
Prometheus
→ Alert Rule 평가
→ Alert 발생

Alertmanager
→ Alert 수신
→ Grouping
→ Deduplication
→ Routing
→ Silence / Inhibition
→ Notification 전송
```

Prometheus가 Metric과 Alerting Rule을 평가하여 **Alert Condition이 충족되었는지 판단**하고, Alertmanager는 전달된 Alert를 Grouping, Deduplication, Routing하여 Email, Slack, PagerDuty, Opsgenie, Webhook 같은 Receiver로 보낸다.

> **KCNA 시험 포인트**
>
> `Alert 조건 평가` → Prometheus  
> `Alert 그룹화·중복 제거·라우팅·Notification` → Alertmanager

## 11. Grafana

Grafana는 **Dashboard와 Visualization**을 담당하는 도구이다.

Prometheus를 Data Source로 사용하는 경우가 많지만 Grafana는 Prometheus 전용 도구가 아니며 Loki, Elasticsearch, Database 등 여러 Data Source와 연결할 수 있다.

```text
Prometheus
→ Metric 수집
→ 저장
→ Query
→ Alert Rule 평가

Grafana
→ Dashboard
→ Visualization
```

> **시험 함정**
>
> Grafana가 Prometheus 대신 Metric을 Scrape하는 것이 아니다.

## 12. Distributed Tracing, Trace와 Span

Microservices 환경에서는 하나의 Request가 여러 Service를 호출한다.

```text
Client
  ↓
API Gateway
  ↓
Auth Service
  ↓
Order Service
  ↓
Payment Service
  ↓
Database
```

Request가 3초 걸렸다고 해서 어느 구간이 문제인지 바로 알 수 없다. Distributed Tracing을 사용하면 각 Span의 시간을 확인할 수 있다.

```text
Trace: checkout-request

API Gateway       20 ms
Auth Service      30 ms
Order Service     50 ms
Payment Service 2800 ms
Database          40 ms
```

이 경우 Payment Service가 Latency의 대부분을 차지한다는 것을 빠르게 찾을 수 있다.

```text
Trace = 하나의 Request 전체 여정
Span  = Trace를 구성하는 개별 작업 구간
```

### Context Propagation

여러 Service에 걸친 하나의 Request를 같은 Trace로 연결하려면 Trace Context를 Service 사이에서 전달해야 한다.

```text
Service A
Trace ID = abc123
        ↓
Service B
Trace ID = abc123
        ↓
Service C
Trace ID = abc123
```

이 과정을 **Context Propagation**이라고 한다. KCNA에서 세부 Header Format까지 외울 필요는 없지만 Distributed Tracing이 Service 간 Context 전달을 통해 하나의 Trace를 연결한다는 개념은 알아두면 좋다.

## 13. OpenTelemetry

OpenTelemetry, 줄여서 OTel은 **Vendor-Neutral Observability Framework**이다.

Telemetry를 다음과 같이 다룰 수 있도록 표준화된 방법과 도구를 제공한다.

- Instrumentation
- Generation
- Collection
- Processing
- Export

대표적으로 다음 Signal을 다룬다.

```text
Traces
Metrics
Logs
```

최근 OpenTelemetry에는 **Profiles** Signal도 추가되고 있지만 기존 세 Signal보다 성숙도가 낮은 영역이며, 현재 KCNA에서는 Metrics / Logs / Traces를 우선 학습하면 된다.

### 왜 OpenTelemetry가 필요한가

Observability Backend마다 별도의 SDK를 사용하면 Application이 특정 Vendor에 강하게 종속될 수 있다.

```text
Application
   ↓
Vendor A SDK
   ↓
Vendor A Backend
```

OpenTelemetry를 사용하면 다음처럼 Backend와 Application Instrumentation 사이의 결합을 줄일 수 있다.

```text
Application
   ↓
OpenTelemetry Instrumentation
   ↓
OpenTelemetry Collector
   ↓
Backend A / Backend B / Backend C
```

> **KCNA 시험 포인트**
>
> `Vendor-Neutral Telemetry Instrumentation`이라는 표현이 나오면 **OpenTelemetry**를 연결한다.

## 14. OpenTelemetry Collector와 OTLP

OpenTelemetry Collector는 Telemetry Pipeline의 중간 계층으로 사용할 수 있다.

```text
Application
    ↓
Receiver
    ↓
Processor
    ↓
Exporter
    ↓
Observability Backend
```

Collector는 여러 Source에서 Telemetry를 받고 처리한 다음 하나 이상의 Backend로 전달할 수 있다.

```text
OTel SDK / Instrumentation
→ Telemetry 생성

OTel Collector
→ Telemetry 수집 / 처리 / 전달

Backend
→ 저장 / Query / Visualization
```

**OTLP(OpenTelemetry Protocol)**는 OpenTelemetry가 Telemetry 데이터를 전달하기 위해 사용하는 Protocol이다. 현재 OTLP는 Traces, Metrics, Logs에서 Stable이고 Profiles는 Development 단계이다.

```text
OpenTelemetry
→ Vendor-Neutral Telemetry Framework

OTLP
→ OpenTelemetry Telemetry 전달 Protocol
```

## 15. Jaeger

Jaeger는 **Distributed Tracing System**이다. Trace를 저장하고 검색하며 Request 경로와 Span을 분석하는 데 사용한다.

```text
OpenTelemetry
→ Telemetry Instrumentation / Collection / Export

Jaeger
→ Distributed Trace 저장 / Query / Visualization
```

## 16. Kubernetes Logging

Kubernetes 환경에서는 Container Log를 다룰 때 `stdout`과 `stderr`가 중요하다.

Container Runtime은 Containerized Application의 표준 출력과 표준 에러 Stream을 Capture하고, kubelet과의 통합을 통해 `kubectl logs`로 확인할 수 있게 한다.

```text
Application
   ↓
stdout / stderr
   ↓
Container Runtime
   ↓
Node Log
   ↓
kubelet / kubectl logs
```

다만 Kubernetes 자체가 **완전한 Cluster-Level Log Storage Backend를 제공하는 것은 아니다.** Node가 사라지거나 Log가 Rotation되면 Local Log만으로는 장기 분석이 어렵기 때문에 실제 환경에서는 Cluster-Level Logging Pipeline을 추가한다.

## 17. Log Collector, Fluentd와 Fluent Bit

Cluster의 각 Node에서 Container Log를 수집하려면 Node-Level Logging Agent를 사용할 수 있다.

```text
Node
├── Pod A
├── Pod B
├── Pod C
└── Log Collector
        ↓
   Central Log Backend
```

모든 Node에서 Agent가 실행되어야 하므로 Kubernetes에서는 **DaemonSet** 형태로 배치하는 경우가 많다.

대표적인 Collector로 Fluentd와 Fluent Bit이 있다.

### Fluentd

Fluentd는 다양한 Source에서 Log와 Event Data를 수집·가공하여 Backend로 전달하는 Data Collector이다.

### Fluent Bit

Fluent Bit은 보다 가볍고 Resource 사용량이 작은 Telemetry Agent / Processor이다. 초기에는 Logging 중심으로 많이 사용되었지만 현재는 Logs뿐 아니라 Metrics와 Traces 처리 기능도 제공한다.

```text
Fluent Bit = 오직 Log만 처리한다.  X
```

KCNA에서는 다음 정도로 기억하면 충분하다.

```text
Fluentd / Fluent Bit
→ Cloud Native Telemetry / Log 수집과 전달

Fluent Bit
→ 상대적으로 Lightweight Agent
```

```text
Application Logs
      ↓
Log Collector
      ↓
     Loki
      ↓
   Grafana
```

시험에서는 다음 역할 정도를 구분하면 된다.

```text
Loki       = Logs
Jaeger     = Traces
Grafana    = Visualization
```

## 19. SLI, SLO, SLA

서비스 Reliability를 숫자로 표현할 때 자주 사용하는 세 가지 개념이다.

| 용어 | 정식 명칭 | 의미 | 예 |
| --- | --- | --- | --- |
| **SLI** | Service Level Indicator | 실제 측정 지표 | 실제 Availability 99.95% |
| **SLO** | Service Level Objective | 목표 수준 | Availability 99.9% 이상 |
| **SLA** | Service Level Agreement | 고객과 합의한 서비스 수준 | 기준 미달 시 Service Credit |

### SLI

SLI는 서비스 품질을 나타내는 **실제 측정값 또는 측정 지표**이다.

- Availability
- Latency
- Error Rate
- Throughput

```text
최근 30일 실제 Availability = 99.95%
```

### SLO

SLO는 SLI에 대해 조직이 설정한 **목표값**이다.

```text
최근 30일 Availability를 99.9% 이상 유지한다.
```

### SLA

SLA는 서비스 제공자와 고객 사이에서 합의한 **서비스 수준 Agreement**이다. SLA에는 Service Credit 같은 보상이나 계약상 조건이 포함될 수 있다.

```text
SLI = Indicator = 실제 측정
SLO = Objective = 목표
SLA = Agreement = 합의 / 계약
```

### 관계

```text
SLI
실제 Availability = 99.95%

        ↓ 비교

SLO
목표 Availability >= 99.9%

        ↓ 외부 약속

SLA
Availability < 99.5%이면 Service Credit 제공
```

조직에 따라 다르지만 일반적으로 SLA를 위반하기 전에 내부적으로 대응할 수 있도록 SLO를 더 엄격하게 설정하는 경우가 많다.

---

## 20. Error Budget

SLO가 100%가 아니라면 일정한 실패를 허용할 수 있는 범위가 생긴다. 이를 **Error Budget**이라고 한다.

예를 들어 Availability SLO가 99.9%라면 개념적으로 다음과 같다.

```text
SLO = 99.9%

허용 가능한 비가용 비율
≈ 0.1%
```

Error Budget이 충분히 남아 있다면 새로운 기능 배포와 변경을 조금 더 적극적으로 진행할 수 있고, 빠르게 소진되고 있다면 Reliability 개선에 집중할 수 있다.

```text
Reliability
     ↕
Development Velocity
```

---

## 21. Golden Signals

Google SRE에서 널리 알려진 대표적인 Service Monitoring Signal은 네 가지이다.

```text
Latency
Traffic
Errors
Saturation
```

- **Latency**: Request 처리 시간
- **Traffic**: 시스템이 받는 Workload의 양
- **Errors**: 실패한 Request의 비율이나 수
- **Saturation**: Resource가 최대 Capacity에 얼마나 가까운가

예시는 다음과 같다.

```text
Latency    → p95 / p99 Request Latency
Traffic    → Requests Per Second
Errors     → HTTP 5xx / Exception Rate
Saturation → CPU / Memory / Disk I/O / Queue
```

Golden Signals는 별도의 Telemetry Type이 아니다.

```text
Telemetry
└── Metrics
    ├── Latency
    ├── Traffic
    ├── Errors
    └── Saturation
```

따라서 `Metrics / Logs / Traces / Golden Signals`를 네 종류의 Telemetry Signal로 보면 안 된다.

FinOps는 Cloud 비용을 단순히 재무팀만 관리하는 것이 아니라 Engineering, Finance, Business가 함께 **Cloud 사용량과 비용을 측정하고 가시화하며 최적화하는 운영 Practice**이다.

```text
비용 가시화
   ↓
Allocation
   ↓
낭비 Resource 발견
   ↓
Rightsizing / Optimization
   ↓
```

다만 현재 KCNA 공식 Competency에 FinOps가 독립 항목으로 명시되어 있지는 않으므로 **시험 우선순위는 Observability 핵심 개념보다 낮게 잡는다.**

## 23. Resource Requests와 Limits

Kubernetes 비용과 Capacity를 이해하려면 Requests와 Limits를 정확히 구분해야 한다.

### Requests

Requests는 Scheduler가 Pod를 배치할 때 **필요한 Resource 양으로 고려하는 값**이다.

```yaml
resources:
  requests:
    cpu: 500m
    memory: 512Mi
```

Requests를 실제 사용량보다 지나치게 크게 설정하면 Resource가 충분히 사용되지 않더라도 Scheduler 관점에서는 이미 할당된 Capacity로 계산된다.

```text
Requests 과대 설정
      ↓
Scheduler가 사용 가능한 Capacity를 적게 판단
      ↓
Node Utilization 저하
      ↓
더 많은 Node 필요
      ↓
Infrastructure Cost 증가 가능
```

이것이 Over-Provisioning과 연결된다.

### Limits

Limits는 Container가 사용할 수 있는 Resource의 상한과 관련된다.

```text
CPU Limit 초과 시도
→ CPU Throttling 가능

Memory Limit 초과
→ OOM 발생
→ Container 종료 / OOMKilled 가능
```

---

## 24. Requests와 Limits에서 자주 틀리는 부분

기존 자료의 다음 설명은 수정해야 한다.

```text
Requests를 너무 낮게 잡으면
OOMKilled 또는 CPU Throttling이 발생한다.
```

정확하지 않다.

```text
CPU Request
→ Scheduling / Resource 보장 기준

Memory Request
→ Scheduling / Resource 보장 기준

CPU Limit 초과
→ CPU Throttling 가능

Memory Limit 초과
→ OOMKilled 가능
```

Requests를 실제 사용량보다 지나치게 낮게 잡으면 Node에 Workload가 과도하게 밀집되어 Node Resource Pressure, Performance 불안정, Eviction 위험 등에 영향을 줄 수 있다.

따라서 비용 관리의 핵심은 단순히 모든 Request를 낮추는 것이 아니라 **실제 Workload 특성에 맞게 Rightsizing하는 것**이다.

---

## 25. Rightsizing

Rightsizing은 Workload의 실제 Resource 사용량을 분석하여 CPU와 Memory 설정을 적절하게 조정하는 것이다.

```text
Too High
→ Resource 낭비
→ Over-Provisioning

Too Low
→ Resource 경쟁
→ Performance 문제
→ Memory Pressure / Eviction 가능

Appropriate
→ 안정성 + Resource 효율
```

Observability Data를 충분히 모아 `Requested CPU vs Actual CPU Usage`, `Requested Memory vs Actual Memory Usage`를 비교하면 Rightsizing에 도움이 된다. VPA의 Recommendation도 활용할 수 있다.

## 26. OpenCost와 Kubecost

Kubernetes 자체는 기본적으로 다음 질문에 직접 답해 주는 Cost Accounting System은 아니다.

```text
이 Namespace가 이번 달에 얼마를 사용했는가?
이 Team의 Kubernetes 비용은 얼마인가?
어떤 Workload가 가장 많은 Cost를 발생시키는가?
```

**OpenCost**는 Kubernetes Cost와 Resource Allocation에 대한 가시성을 제공하는 Open Source 프로젝트이다. Cluster, Node, Namespace, Pod, Workload, Label 같은 단위로 Cost를 분석하는 데 사용할 수 있다.

중요한 현재 상태도 수정해야 한다.

```text
기존 자료
OpenCost = CNCF Sandbox

현재
OpenCost = CNCF Incubating
```

OpenCost는 **2024년 10월 25일 Incubating Maturity Level**로 이동했다.

**Kubecost**는 Kubernetes Cost Monitoring 및 Optimization 제품으로, OpenCost와 함께 Kubernetes 비용 가시성 문맥에서 자주 등장한다.

현재 KCNA 공식 Competency에서는 이 부분보다 Observability 기본 Signal과 도구 역할 구분을 우선한다.

## 27. metrics-server와 Prometheus

Kubernetes를 공부하다 보면 `metrics-server`와 Prometheus가 모두 CPU/Memory Metric을 다루기 때문에 헷갈리기 쉽다.

### metrics-server

Kubernetes Resource Metrics API를 제공한다.

대표 사용처는 다음과 같다.

```text
kubectl top
HPA
```

즉 CPU와 Memory 같은 **현재 Resource Metric을 Kubernetes Autoscaling과 기본 Resource 조회에 제공**하는 것이 주된 목적이다.

### Prometheus

보다 일반적인 Application / Infrastructure Monitoring System이다.

```text
Time-Series 저장
PromQL
Application Metric
장기간 분석
Alerting
```

### 시험용 구분

```text
metrics-server
→ Kubernetes Resource Metrics API
→ kubectl top / HPA

Prometheus
→ Monitoring
→ Time-Series
→ PromQL
→ Alerting
```

> **KCNA 시험 함정**
>
> HPA가 CPU Metric을 사용한다는 설명만 보고 무조건 Prometheus를 선택하면 안 된다. 기본 Resource Metric 기반 HPA에서는 metrics-server가 제공하는 Metrics API가 흔히 사용된다.

## 28. kube-state-metrics

`metrics-server`와 이름이 비슷하지만 역할은 다르다.

**kube-state-metrics**는 Kubernetes API Server의 Object 상태를 읽어 Metric으로 노출한다.

예를 들어 다음과 같은 상태를 Metric으로 만들 수 있다.

```text
Deployment Desired Replicas
Deployment Available Replicas
Pod Status
Node Status
PersistentVolume Status
```

```text
metrics-server
→ 실제 CPU / Memory Resource Usage

kube-state-metrics
→ Kubernetes Object의 상태를 Metric으로 노출

Prometheus
→ 위 Metric을 포함한 다양한 Time-Series를 Scrape / 저장 / Query
```

세부 Metric 이름까지 외울 필요는 없지만 세 도구의 역할 차이는 알아두면 좋다.

## 35. 정리

Observability의 핵심은 단순히 Dashboard를 만드는 데 있지 않다.

Cloud Native 시스템은 수많은 Container와 Microservice가 동적으로 생성되고 사라지기 때문에 시스템 내부에서 무슨 일이 발생하고 있는지를 외부 Telemetry를 통해 이해할 수 있어야 한다.

가장 먼저 구분해야 하는 세 Signal은 다음과 같다.

```text
Metrics
Logs
Traces
```

Metrics는 시스템의 상태와 추세를 숫자로 보여 주고, Logs는 특정 Event의 상세 Context를 보여 주며, Traces는 하나의 Request가 여러 Service를 거치는 전체 경로를 보여 준다.

Metrics 영역에서는 Prometheus의 역할을 확실히 구분한다.

```text
Prometheus
→ Pull / Scrape
→ Time-Series
→ Label
→ PromQL
→ Alert Rule
```

주변 도구의 역할은 다음처럼 연결한다.

```text
Alertmanager
→ Alert Routing / Notification

Grafana
→ Visualization

OpenTelemetry
→ Vendor-Neutral Telemetry Instrumentation / Collection / Export

Jaeger
→ Distributed Tracing

Fluentd / Fluent Bit
→ Telemetry / Log Collection

Loki
→ Log Aggregation
```

신뢰성 영역에서는 다음 세 개를 혼동하지 않는다.

```text
SLI = 실제 측정
SLO = 목표
SLA = 계약
```

Kubernetes Resource 영역에서는 다음 차이를 구분한다.

```text
Request
→ Scheduling

CPU Limit
→ Throttling

Memory Limit
→ OOMKilled
```

그리고 현재 시험을 준비할 때 가장 중요한 변경 사항은 **Cloud Native Observability가 더 이상 별도의 8% Domain이 아니라 Cloud Native Architecture 12% 안의 공식 Competency로 통합되었다는 것**이다.

결국 KCNA에서 Observability 문제를 풀 때는 도구의 세부 설정값을 외우는 것보다 다음 질문에 답할 수 있어야 한다.

```text
어떤 Signal이 필요한가?

어떤 도구가 그 역할을 담당하는가?

수집, 저장, Query, Visualization, Alerting 중
어느 단계의 문제인가?
```

이 역할 구분이 정확하면 Observability 관련 시나리오 문제의 답을 빠르게 좁힐 수 있다.
